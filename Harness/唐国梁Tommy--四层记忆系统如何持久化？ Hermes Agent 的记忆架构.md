标题： 四层记忆系统如何持久化？ Hermes Agent 的记忆架构，有意思的地方不是"它能记住什么"，而是它怎么把长期事实、会话历史、外部记忆后端和上下文压缩拆成几套完全不同的机制。本期适合正在做 Agent、关心记忆/上下文工程的同学，看完你会知道一套能落地、能扩展的记忆基础设施到底该怎么分层。#Hermesagent #AIAgent #Agent记忆 #AI前沿技术 #harness
作者： 唐国梁Tommy
 
当 AI Agent 需要：
 
1. 记住你的偏好
2. 想起上次改了什么
3. 不打破 Prompt Cache
 
这次我想带你看懂 Hermes Agent 的记忆架构，因为它真正有意思的地方，不是它能记住什么，而是它怎么把长期事实、会话历史、外部记忆后端，还有上下文压缩，拆成了几套完全不同的机制，边界设计得非常克制。
 
很多 AI 产品一提到 memory，给人的感觉都像是在说一件事，好像只要有一个记忆模块，问题就解决了。但 Hermes 系统设计和源码一起看下来，你会发现真正能落地的记忆系统，往往不是一个模块，而是一套分层很清楚的组合结构。如果先给一个非常浓缩的结论，Hermes 的记忆至少有四层：
 
1. 工作记忆
2. 内建长期记忆
3. 会话历史
4. 外部 Provider
 
也就是 run conversation 模型这一轮看到的用户输入、工具结果、推理内容，先都在这里流动。第二层是内建长期记忆，也就是 MEMORY.md 和 USER.md。前者偏环境、项目、工具和约定，后者偏用户画像、偏好、Session 级快照。
 
第三层是完整会话历史，也就是 state 点 db、消息表，再加上 gateway 还保留的 JSON Lines。第四层才是可插拔的外部 memory provider，比如更专业的语义记忆后端。
 
它为什么要拆这么细？不是因为复杂，而是因为它必须同时满足几件本来互相冲突的事：
 
- 持久化：用户每次都要重复说明？不行
- 可控：memory 很快变成垃圾？不行
- Prompt Cache 稳定性：system prompt 一直变，后面的成本、时延、调试难度都会变差
 
所以 Hermes 最核心的判断，不是尽量多记，而是哪些东西该怎么记，才能既保留下来，又不把系统拖垮。在我看来，这就是它把长期事实和历史轨迹故意拆开的根本原因：
 
- 稳定事实选 curated memory
- 完整过程选 transcript
 
如果你把这两种东西混在一起，要么长期记忆会被大量过程信息污染，把会话日志也写入 MEMORY.md，memory 迅速膨胀，真正有价值的偏好和事实被淹没；要么你只剩下一点偏好描述，想不起来上次到底怎么修的那个问题。
 
更细一点看，Hermes 在 session 一启动的时候，就会把 memory 配置、字符预算、是否启用 MEMORY.md 和 USER.md 这些参数读出来。如果用了内建 memory，就创建 Memory Store，然后从磁盘加载两份文件，而且这里不是简单读一下就算了，system prompt snapshot 后面模型每一轮看到的长期记忆，其实都是这份冻结快照。
 
这就带出了整个设计里最反直觉、但也最能体现工程味道的一点：Hermes 的长期记忆不是强即时的。新内容会立刻写盘，但真正把这份新记忆注入 prompt，通常要到下一次 session 启动。为什么这么做？因为它非常明确地选择了另一件事：也要把 session 内的 system prompt 稳住。这不是功能没做完，这是一个清楚的成本决策。
 
如果你以前默认以为记忆写进去就应该马上生效，那你会在弹幕里扣 1，我完全理解。
 
而且 Hermes 不是只在原则上说长期记忆要精炼，它在机制上也把这件事做得很硬：直接用两份纯文本文件，给字符预算设了硬上限，MEMORY.md 默认两千两百字符，USER.md 默认一千三百七十五字符。单条 memory 的操作也刻意保持得很克制，只有 add、replace、remove 三种，没有花哨的知识图谱，也没有自动 embedding 索引。源码里这个工具的实现其实很说明问题。
 
memory 不是一个普通工具，它在 run agent 里被专门拦截，和 todo、session search 这种 agent level 能力放在同一层处理。这说明长期记忆在 Hermes 里不是外围插件，再比如 replace 和 remove 不是靠 entry id，而是靠一个短子串去匹配目标条目。如果匹配到多条而且内容又不完全一样，它就直接报错，让模型再说得更具体一点。这个设计看起来不高级，但它的好处非常明确：人能看懂，调试时也容易解释，而且 memory 文件依然可以手工编辑，不会被一套过度结构化的内部 id 体系绑死。
 
还有写入路径上的实现细节，我觉得也很值得讲，因为它体现出这套系统不是纸面设计。Hermes 每次写 memory 之前，会把别的 session 或别的进程刚写进去的变化吸收进来，然后再修改。真正落盘的时候，它不是直接 open w 覆盖，而是走 temp file 加 OS replace 的原子写入。这背后的原因也很现实，因为直接覆盖有一个典型的竞态窗口，读线程可能短暂看到空文件。源码现在这套实现，就是在避免这种你明明只是写一条记忆，却把别的会话读崩了的问题。
 
因为长期 memory 最终会被注入 system prompt，所以它在 Hermes 里本质上是一个持久化 prompt 入口。既然是 prompt 入口，它就不能按普通聊天文本那样对待，要做 prompt injection、角色劫持、密钥诱导、SSH 后门、隐形 Unicode 这些内容的安全扫描。这个逻辑非常合理，因为一段恶意内容如果只是出现在一次对话框，影响还有限；可一旦被写进 memory 文件，后面每个 session 都可能被污染。
 
说完长期记忆，再看 Hermes 的另一条主线：会话历史与检索回忆。Hermes 的思路不是把所有过去都编成记忆，而是先把完整会话轨迹老老实实存下来。state 点 db 里不只是 role 和 content，它还会存 tool call id、tool calls、finish reason、reasoning、reasoning details、codex reasoning items 这些字段。这就意味着，Hermes 保存的不是一份普通聊天记录，而是一份尽量完整的 agent 运行轨迹。为什么连 reasoning 都要存？因为在一些 provider 或模型接口里，你如果把 reasoning 在持久化层丢掉，下一轮恢复的时候，模型看到的上下文就会断层。所以 state 点 db 在 Hermes 里不是单纯的聊天历史备份。
 
底层的检索基座也做得很扎实：SQLite 开了 WAL 模式，支持多读单写；写事务立刻获取 RESERVED 锁，用 begin immediate 打散并发写锁竞争；同时还会定期做被动 checkpoint。这类实现细节平时不太会被用户看到，但它决定了 gateway、多 profile、同时跑的时候，这套记忆系统到底会不会因为竞争写入而卡顿。
 
messages_fts 这张虚表通过 trigger 跟 messages 表同步，搜索时不只是给一个命中片段，还会带上前后邻近消息。所以 Hermes 的 session search 是一个先粗搜、再重上下文的回忆管线。这里还有一个很容易被忽略，但特别能说明工程成熟度的细节：它不是优雅的统一设计，而是演进中真实的工程决策。为什么明明已经上了数据库，还保留 JSON Lines？因为这套系统是演进过来的，不是从第一天就只有 DB。加载 transcript 时会优先选消息更多的那个来源，避免迁移期间只读到最近几条消息，结果模型误以为历史只有一小段。
 
回到 session search 本身，它真正解决的是过去完整发生了什么、我现在怎么把它拿回来。它的流程大概是这样：先用 FTS5 搜关键词，拿到很多匹配消息；再把这些消息归并到各自所属的 session；读出来；最后交给辅助模型做 focused summary。而且它有几个处理做得很聪明：
 
1. 如果 query 为空，只返回最近会话的标题、预览和时间戳，几乎没有 LLM 成本
2. 真正做关键词搜索时，最多只总结五个 session，避免一次性触发太多 LLM 调用
3. 它会把当前 session 的 lineage 整条排除掉，这样做是为了防止模型把自己当前链路上的上下文又当成过去历史
 
在我看来，这一层的价值不只是能搜，而是它非常明确地把长期事实和历史轨迹分成了两种完全不同的信息资产：
 
- 像用户喜欢深色模式、项目约定、常用工具这类内容，适合写进 USER.md 或 MEMORY.md
- 但像上次为了解决某个 race bug 改了哪些函数、试过哪些失败方案这种事，明显是 episode，也就是事件流，而应该通过 transcript 保留下来，再在需要的时候被搜索和摘要
 
再往外一层，就是外部 Memory Provider。Hermes 在这部分没有直接把外部记忆后端写死在主循环里，而是抽象出 Memory Provider 和 provider 可以声明自己是否可用、提供静态 system prompt block、在 turn 结束后同步数据、也可以暴露自己的工具接口。团队并没有把记忆理解成只有一种实现方式，而是给未来接第三方后端留了很完整的生命周期接口。
 
不过从具体实现上看，Hermes 也没有为了统一去强行抹平所有差异，仍然走独立的 Memory Store 主线；外部 provider 则通过 Memory Manager 接入。这种半统一结构，在我看来反而很合理，因为内建记忆和外部后端本来就不是同一类东西，硬揉成一个抽象模型，不一定更干净，反而可能让成本和边界都变模糊。它还加了一个非常现实的限制：同一时间只允许一个外部 provider 生效。原因很直接，如果两个 provider 同时暴露工具、同时做 recall、同时想把自己的说明塞进 prompt，你几乎一定会遇到工具表面膨胀、召回结果冲突，所以它宁可收敛一点，也不去追求什么都能并联。
 
更值得注意的是外部 recall 的注入方式：Hermes 会在当前用户 turn 开始之前，特意用的是原始用户输入，而不是已经被技能说明、其他附加内容加工过的版本，因为后者会把 recall query 搞得又长又糊。拿到 recall 结果以后，不是在构造 API messages 时，临时把那段内容包进 memory context 标记，再拼到当前这轮的 user message 后面。调用时随时给模型的背景和真实会话历史。更关键的是，这点我真的建议所有做 agent 的人都重点看一下，那会 session search 再去搜的时候，就会把系统自己召回出来的内容误当成真实历史，这会导致一种非常糟糕的自我污染，时间久了，系统甚至分不清哪些是原始事实，哪些是以前某次临时插进去的解释。recall 包起来，我觉得这是整个记忆架构里最该保留的设计之一。
 
而 turn 结束之后，当前实现是拿到最终 response 以后，再统一做 sync all，为下一轮准备。下一轮开始前召回的松耦合模式，而不是每个 tool call 后都同步一次。这对延迟和成本都更友好。
 
说到这里，你其实会发现，所谓当前工作记忆这一层虽然不持久，但它反而是所有记忆机制真正汇合的地方：内建 memory 通过 system prompt、外部 provider recall 通过 API、历史 transcript 又可以通过 session search 变成当前上下文的一部分，服务的是当前这一轮推理。所以 Hermes 的记忆系统不是几个孤立小功能，而是一套围绕当前推理回合组织起来的上下文装配线。
 
接下来我觉得最精彩的部分，比如要做 context compression，或者 session 要 reset，普通系统通常就是直接压缩、直接清空、直接重建。但 Hermes 会先做一件事，这一步的实现其实很讲究。它会先在消息列表末尾追加一条系统风格的 user message，内容大概就是这段上下文马上要被压缩了，请优先保存值得长期记住的东西，特别是用户偏好、纠正和重复模式。但这次只开放 memory 这个工具，不让模型再去跑其他流程。就执行写入；最后再把刚才那条 flush message 以及相关临时痕迹从消息列表里删掉。连这一步它都尽量做了成本优化。源码里 flush memories 会先走，因为这类临时槽调用没必要总是占用主模型链路，而且这样做还能绕开一部分 API 兼容性麻烦。你从这程能看出来，Hermes 团队不是想到了要在压缩前记一下，而是真的把这件事当成通行边界上的一段独立工程流程来处理。
 
如果启用了外部 provider，也就是说，Hermes 认为压缩边界不是一个简单丢弃内容的操作，内建 memory 在这里做归档，也可以在这里抽取它认为必须保住的东西。而且 compression 本身也不是重写当前，Hermes 的做法是结束旧 session，创建一条带 parent session id 的新 session，再把压缩后的消息写进去。这样旧 transcript 仍在，新的对话又能继续，整个 lineage 也保住了。所以它不是压缩后覆盖旧历史，而是在历史之上开一个新分支，因为后续 session search 正是依赖，来避免把当前链路当成历史重复召回。
 
Gateway 场景下，记忆系统会更复杂，因为谁共享这份上下文本身就是产品设计问题。Hermes 在 build session key 不同场景下的 session 隔离策略：
 
- 私聊通常按 chat 隔离
- 群聊里如果开放了 group sessions per，默认又会共享一个 session
- 除非显式打开 thread sessions per user
 
这其实对应的是一种非常明确的产品判断：线程讨论默认是一条共享上下文，这和长期记忆的作用域又不是完全一回事。transcript 这一层通常按 session，但外部 provider 初始化时还能拿到 user id、agent identity，这就给了系统一个很大的自由度，同时又让某种用户偏好记忆保持 user scoped。这种会话共享和长期记忆可以分开治理的设计，我觉得是它很值得看的部分。
 
再看子代理，你会更清楚 Hermes 到底有多克制。child agent 默认没有 memory 工具，而且构造子代理时会显式传 skip memory 等于 True。不仅如此，子代理连 clarify、递归 delegation、跨平台消息发送这些能力也默认被摘掉。团队对谁有资格写长期记忆这件事是很保守的，因为子代理的上下文更窄，它很容易把局部偶然情况误当成长期事实；而且子代理往往嵌套执行，直接让它们去共享 memory，所以它宁可收敛一点，也不去追求什么都能并联。
 
Hermes 的做法是，子代理自己不写，delegation 完成后收到 task 和 result，也就是 on delegation 这个 hook。换句话说，探索和执行可以下放给子代理，但这件事值不值得进入长期记忆的判断，还是留给父级上下文去做。
 
自动化治理这部分也很有意思。Hermes 并不完全相信主代理每次都会自觉地调用，所以系统提示里一直在灌输 MEMORY GUIDANCE，提醒模型优先保存用户偏好、环境怪癖、稳定约定，不要把 task progress / completed work log 写进去。这是一层前置约束。但它还不止这一层，源码里 turns since memory 会持续计数。如果连续很多轮都没有发生 memory 写入，达到阈值以后，就触发 background review，默认阈值是十轮。这个 background review 会 fork 一个轻量 review agent，沿用当前模型，把刚刚这段会话快照再过一遍，然后附加一段专门的 review prompt，让它自己检查刚才有没有什么本该记住却没记下来的事实。是在用户已经收到最终回复之后才异步跑的，目的是不跟主任务抢注意力。
 
我很喜欢这个设计，因为它像一个会后秘书。主代理在前置把任务做完，后台再有人帮你检查刚才有没有什么值得长期沉淀的东西。这会让记忆系统从单次工具决策变成前置执行加后台复盘的双重机制，容错率会高很多。
 
如果让我概括 Hermes 当前这套记忆架构最大的优点，我会说它的优点不是某一个 memory backend 特别先进，而是边界真的划得很清楚。什么是稳定事实，什么是完整历史，什么是临时召回，什么是当前工作上下文，什么是压缩前必须抢救的信息，什么是子代理不该碰的共享长期记忆。很多 agent 系统最终不是输在能力不够，而是输在上下文层次混了，历史污染了，session 边界不清楚。Hermes 目前最大的价值，就是它没有在这些地方偷懒。
 
第一，内建 memory 下次 session 才生效，这会带来明显的体感滞后。
第二，curated memory 仍然只是文本条目，透明归透明，但结构化治理不强，不容易做冲突检测、字段合并和优先级管理。
第三，session search 更像摘要式回忆，但还不适合 agent 继续拿它做结构化执行。
第四，之间现在仍然是弱耦合，只能衔接，不是强一致。
 
我觉得重点不一定是再接一个新的 memory backend，更有价值的方向是：
 
- 加一点轻量结构化元信息，比如 scope、来源、更新时间、置信度
- 再就是做一个 session 内可见的 overlay 记忆层，这样一来，既能保持现在的缓存策略，又能缓解我明明刚记住、为什么当前 session 还看不到的体验问题
- 从摘要模式继续往前推一步，比如除了 summary，再加 artifacts、commands、decisions 这种结构化提取模式，因为 agent 真正需要的，很多时候不是上次聊了什么，而是上次到底执行了哪些命令、改了哪些文件、做了什么决定
 
这条演进路径其实是成立的。如果是你来继续做这套系统，你会优先补结构化 curated memory，还是补本 session 可见的 overlay 记忆？
 
Hermes 到底是不是有一个很强的记忆模块？我觉得更准确的说法是，它不是一个脑子，MEMORY.md 和 USER.md 是长期档案柜，state 点 db 是完整流水账，session search 是档案检索员，外部 provider 是可插拔的专业记忆后端，background review 则像事后复盘员。而 run conversation 真正做的事情，是在不同边界把这些角色调度起来。
 
从 agent engineering 的角度讲，这种设计不一定是最统一、最优雅的。它甚至保留了不少演进中的痕迹：JSON Lines 和 SQLite 并存、内建 Memory Store 和外部 provider 并行、多层生命周期共存。但也正因为它没有为了抽象统一去强行简化现实，所以它反而更接近一个真实复杂系统在生产环境里能长期工作的样子。我会把它看成一种很有意思的系统级折中。
 
如果你要用一句话总结 Hermes 的记忆架构，我觉得可以这么说：它不是在追求什么都记住，而是在追求把不同类型的记忆放进不同层次，用合适的生命周期和成本模型去管理它们。Hermes 的价值不只是做了一个 memory tool，而是把长期事实、完整历史、外部 recall，还有压缩和重置这些边界事件，真正组成了一套能落地、能扩展、也能自我约束的记忆基础设施。
