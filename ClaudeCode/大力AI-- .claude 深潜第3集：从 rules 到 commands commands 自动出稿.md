- 别再手打提示词了
- 第3集：commands 怎么从快捷键变成稳定入口
- 今天这集我们继续往下走，讲.claude 深潜的第三层，也就是 commands。
- 上集我们把 rules 拆开以后，Claude 已经知道不同目录该遵守什么规矩了。
- 但你真开始干活的时候，还是会遇到一个很烦的问题：每次开工都要重新组织提示词。
- 我最近反复用下来最大的感受就是，重复三次以上的提示词，就不该再手打了。
 
它到底解决什么问题
 
- commands 真正解决的，不是省几次复制粘贴。
- 临时 vs 固定
- 手打一段话：每次措辞都不同、容易漏要求、很难复盘为什么这次写偏了
- 做成 /command：入口固定、输出结构稳定、团队里的人都能复用
- 为什么它会省时间
- 需求来了→不再重写提示词→直接触发固定模板→输出更稳
- 它解决的是工作流入口不稳定。今天写方案你这样说，明天写需求你又换一套说法，Claude 每次理解都可能有点偏。
- 它不是省打字，而是把常用动作正式化，减少每次开工前的摇摆
- 把这类高频动作收成一条斜杠命令以后，入口就固定了。你不是在临场发挥，而是在触发一个已经验证过的模板。
- 适合命令化
- 固定格式出稿：比如 proposal、PRD、日报、回顾
- 固定检查动作：比如代码审查、风险检查、改写风格
- 固定收口动作：比如 next step、todo、handoff
- 这一步看起来小，但它其实是把临时提示词，变成项目里的正式接口。
 
现在的官方变化，要怎么理解
 
- 这里有个更新我觉得必须讲一下。
- 文档里的新说法
- 官方视角：custom commands 已并进 skills、更鼓励把复杂流程写成技能、统一放进更完整的扩展体系
- 项目里的现实用法：/proposal 这种快捷入口依然很值钱、轻动作不必全升级成 skill、命令层仍然适合高频手动触发
- 怎么理解这次变化
- 简单快捷动作保留 command → 复杂多步工作流升级成 skill → 不是二选一，而是按复杂度分层
- 如果你最近去看 Anthropic 的 Claude Code 文档，会发现 custom commands 这套概念，已经被并进 skills 了。
- 但这不代表项目里的 commands 这一层没用了。反过来我觉得，它更像一个很轻的本地快捷入口，尤其适合那些你想自己手动触发的动作。
- 今天这集的判断：command 不是过时，而是更应该被当成轻入口使用
- 这层最适合承接什么
- 输入：你已经有 rules、你知道自己高频会做哪几件事
- 处理：把高频动作收成固定命令、明确输入参数和输出格式
- 输出：团队可复用的 /proposal /review-prd /next-step
- 所以今天这集，不是教你守着旧概念不放，而是教你怎么把 command 当成一层很值钱的轻入口继续用。
 
教程一：先写一条真的能用的 /proposal
 
- 好，我们直接来做一个最值钱的命令：/proposal。
- 命令文件位置：.claude/commands/proposal.md
- 我的建议是，先不要追求万能命令，先把你最常用、最容易重复出错的那条写出来。
- 方案模板：
- 根据下面的客户需求输出项目方案：
- 客户需求：$ARGUMENTS
- 输出必须包含：背景、目标、方案、排期、风险、下一步建议
- 遵循项目里的 CLAUDE.md 和 rules 约束。
- 实际触发效果：
- /proposal 某零售企业要做会员系统数字化
- 正在生成项目方案：背景、目标、方案、排期、风险、下一步建议
- proposal 这类命令最关键的不是文字写得多漂亮，而是要把输出结构固定，比如背景、目标、方案、排期、风险这几块一定要出现。
- $ARG 复用：不是偷懒，而是让同一条命令在不同场景里复用
- 再加上 $ARGUMENTS 这一层，同一条命令就能适配不同客户和不同 brief。
 
教程二：别只写出稿命令，再补两条收口命令
 
- 很多人写 commands，第一反应都是写出稿命令。
- 审 PRD：
- 审查当前 PRD：
1. - 哪些需求不够具体
2. - 哪些验收标准不可测
3. - 哪些风险还没写
- 输入：$ARGUMENTS
- /next-step：
- 基于当前上下文，输出下一步执行清单：
1. - 今天做什么
2. - 哪些依赖还没确认
3. - 哪些风险需要先挡住
- 但我自己现在更看重的是第二类：收口命令。比如 /review-prd 和 /next-step。
- 三类命令最好一起配（不要只写出稿，也要配审查和收口）
- 出稿（/proposal）：生成第一版方案、把结构先立住
- 审查（/review-prd）：找模糊点、找验收漏洞
- 收口（/next-step）：拆下一步、明确谁先做什么
- 真正省下来的：不是一次触发，而是整套小工作流都不再需要临时发挥
- 因为真正拖时间的，往往不是第一稿写不出来，而是写完以后没人把问题收一遍，也没人把下一步拆出来。
- 命令成组配：一条出稿，一条审查，一条收口，效果比只写一条强很多
- 你把这两条也补上，command 这一层才会真正像一个工作流面板。
 
什么时候该停在 command，什么时候该升级成 skill
 
- 讲到这里，很多人都会问：那我是不是把所有动作都做成 command 就行了？
- 停在 command
- 适合保留在命令层：你已经知道要触发什么、动作单一、输出结构固定、需要你手动决定时机
- 升级成 skill：要自动识别场景、是多步流程、需要支持文件或模板、想让 Claude 自己判断是否触发
- 我的答案是不行。command 更适合你已经知道要触发什么动作，而且这个动作本身比较短、边界也很清楚。
- 一个很实用的判断顺序：先问它是不是固定动作→再问是否必须手动触发→如果都不是，就考虑升 skill
- 真正值钱的是边界感：command 做轻入口，skill 做自动工作流，不要混成一层
- 如果它开始变成多步工作流，需要自己判断时机、还要调用模板和参考文件，那就该升级成 skill 了。
 
这一集收口
 
- rules：解决不同场景读什么规则
- commands：解决高频动作怎么固定入口
- skills：下一集讲怎么让 Claude 自己跑流程
- 所以这一层最重要的不是多写命令，而是知道边界：什么该快捷触发，什么该交给工作流。
