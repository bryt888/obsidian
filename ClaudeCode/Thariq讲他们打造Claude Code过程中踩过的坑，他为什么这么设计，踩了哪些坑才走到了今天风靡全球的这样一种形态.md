Claude Code的核心开发者Thariq最近发了两篇技术博客，在讲他们打造Claude Code过程中踩过的坑，他为什么这么设计，踩了哪些坑才走到了今天风靡全球的这样一种形态。我觉得你要是只看Claude Code写代码的视频，就能帮你理解他的思路，优化你的Claude MD文件。但如果你自己在搭智能体、搭Agent，不管用什么样的Agent框架，这两篇文章对你的价值会放大十倍。我们来解读一下这两篇技术“爽文”。
 
Thariq上来就打了一个比方，他说想象你面前有一道很难的数学题，你会想用什么工具去解决？纸笔是最基础的，但算力有限；计算器稍好一点，但你得会操作；电脑肯定是最强的，但你必须要学会写代码。核心意思是工具要匹配Agent的能力，如果Agent能力不到，给再强的工具也白搭；但如果Agent能力足够了，之前那些简单的工具反而会成为累赘。而他们踩坑最多的地方浓缩成一个原则，叫做Progressive Disclosure（渐进式披露）。
 
什么意思呢？中文翻译过来就是“渐进式的披露”。一句话解释就是：别一次性把所有信息都塞给智能体，让它按需获取、分层展开。他们在三个方向上反复验证了这件事。
 
第一个方向：怎么让Agent获取上下文
 
Claude Code最早用的也是RAG，是当时很标准的做法：给代码库建立向量索引，用户提问时检索相关片段，把这些片段塞到上下文里。但后来这个方法被弃用了，为什么？原文有句很关键的话：Claude是被硬塞了这些上下文的。如果Claude能搜索网络，为什么不能搜索代码库？所以之后改成让Claude自己调用Grep搜文件工具，效果反而更好。因为Claude自己清楚自己缺什么，搜到的东西是它自己想要的、能接上上下文的。
 
后来Claude又加入了现在很火的Skills机制：Claude读一个Skill文件，如果里面引用了另外一个文件，就会自动跳过去读；如果还有再引用的文件，就会再跳过去读，这样逐层深入。
 
原文描述，一年前Claude完全不会自己找上下文，现在会多层嵌套搜索、精准定位。如果你现在准备搭自己的智能体，最核心的启发是：别替Agent决定它应该看到什么，给它搜索工具、入口文件、权限，让它自己去挖掘。替它找的人未必能完全理解，它自己找的推理链路才是最完整的。
 
第二个方向：怎么扩展Agent的能力
 
用户可能会问Claude Code类似“如何配置MCP server”的问题，但Claude的模型本身并不知道如何使用Claude Code，那要不要给它加文档工具？Thariq提到一个重要数字：Claude Code目前大约有20个工具，团队对新增工具的门槛卡得非常严格。为什么？因为每多加一个工具，模型每次推理就会多一个选项要权衡。
 
那要不要把使用文档塞到系统提示词里？肯定不行，因为99%的时间里没人会问文档相关的问题。但文档一旦被塞到系统提示词里，每轮对话都会加载，会造成严重的上下文污染，干扰模型干正事。
 
最终的方案是：搞了一个用来指导Claude Code工作的子代理，只有在问相关问题时才会启动，它有专门的搜索指令，找到答案就返回，不会把原始文档全部加载进来。
 
Thariq还写了一句很有启发的话：现在无需添加任何工具，就可以向Claude的操作空间里添加内容。不加工具、不改提示词，通过渐进式披露，照样拓展了Agent的行动空间。
 
如果你在搭智能体时遇到要不要加新工具的问题，先想想能不能用子代理、文件引用，能不能让Agent在需要的时候自己发现能力，而不是一开始就把所有选项、所有工具都摆在它面前。
 
第三个方向：旧工具什么时候该被替换
 
这个坑很隐蔽。早期Claude Code因为记性差，团队专门给它做了一个Todo List工具，相当于Claude Code自己的代办清单，每隔5轮对话还会插一条系统提醒，让它“别忘了刚刚的代办清单”。但模型升级后，这个设计反而害了它。
 
原文说，随着模型的改进，它不仅不需要再被代办事项提醒，反而会觉得这种提醒过于苛刻。收到代办清单的提醒，会让Claude觉得必须严格遵守清单，不能修改。更强的模型根本不需要提醒，而且这种提醒会让Claude Code不敢灵活调整。
 
之后团队改用了Task工具，它能设置依赖关系，多个子代理之间能共享进度，模型能自己改任务、删任务。
 
总结一下：所有自己搭智能体的人都应该记住，随着模型能力的增强，模型曾经需要的工具现在可能会变成限制它发展的障碍。模型能力在涨，给的工具却没跟上，这种工具就从辅助变成了枷锁。
 
三个方向讲完，回到我们自己。如果要搭智能体，第一点是工具要少而精。拥有20个工具的Claude Code团队都觉得工具多了，与其一开始塞50个、100个工具去覆盖所有场景，不如给核心工具加一个搜索或发现机制。
 
他们团队做了一个叫**defer loading（延迟加载）**的设计：工具里只放一个轻量级的“钩子”，智能体需要时，会通过搜索工具去发现并加载定义更完整的工具。
 
扩展能力优先考虑子代理和文件引用，而不是一直往里面加工具。还要定期审视工具集，三个月前模型可能需要的工具辅助，现在可能就成了负担。
 
如果平时你在用Claude Code做开发、写代码，你的Claude MD文件（系统提示词）要控制好，别写成繁琐的操作手册。在MD里只放框架性的核心内容，比如项目简介、技术栈、三五条最关键的规则。把详细规范独立到其他文件中，把文件路径留在MD里。比如可以写“提交规范见docs/commit-convention.md”，Claude真正要提交时，会自己去那个文件里读详细规范。
 
提问时也一样，别把所有相关文件都贴到提问窗口里，要给方向、给入口。比如“token刷新失败，报错xxx，从auth模块开始查”，让它自己去定位。
 
Thariq在文章结尾说的一句话很有道理：给Agent设计工具，既是一门科学技术，也是一门艺术。没有一套公式能覆盖所有工具，要多试、多观察、多迭代，找到自己的感觉和品味。
 
而渐进式披露是他们团队验证下来最有效的主线——塞得越多，Agent反而越受限；给得越克制，它发挥得反而越好。
