深度拆解 Claude Code 架构原理 - 工具使用篇
 
上一期我们讲了 Agent 循环的核心原理，message 经过模型输出，再带着 string 回流到下一轮。今天我们来看一个更具体的问题，怎么给这个循环加上工具？很多人以为加工具很复杂，要改循环、加判断，其实完全不是这样。关键洞察就一句话，加工具不需要改循环。
 
说到底，如果如果你的 agent 只有 bash 能力，会遇到三个致命问题：
 
- 第一， cat  和  sed  这些命令遇到特殊字符就崩溃，可预测性很差。
- 第二，每次 bash 调用都是不受约束的，安全层面你想限制它能访问什么目录，很难。
- 第三，所有操作都走 shell，没有任何结构化管理。专用工具（ read_file 、 write_file 、 edit_file ）就不一样了，它们可以在工具层面做路径沙箱，直接在源头把安全性卡住。
 
怎么设计这个工具系统？答案是 Dispatch Map，也叫 Handler Map，它本质上就是一个字典，把工具名映射到处理函数。之前硬编码 bash 调用，全靠  if-else  判断是哪个工具，现在变成了一个查表操作，一个  lookup  替换掉整个判断链。
 
架构图很简单：用户 prompt 进来，大语言模型（LLM）决定调用哪个工具，到 Dispatch 查表找到 Handler，执行完返回 to Resume，整个流程完全没变，变的只是 Dispatch 多了一个工具分发表。
 
具体怎么写？三步走：
 
1. 定义工具处理器：每个工具对应一个函数。
2. 注册到字典：把这些函数注册到  TOOL_HANDLERS  字典里。
3. 循环查表执行：在 Agent 循环里，遍历模型响应，当遇到  tool_use  块时，从字典里查 Handler 并执行。
 
这个循环本身跟之前完全一样，一行都没改，加工具 = 加 Handler + 加 Schema，循环永远不动。
 
说到文件操作，Handler 里有个函数必须重点讲—— safe_path 。它干的事很简单：拿到一个路径，先  resolve  成绝对路径，然后检查它是否在安全工作目录（WORKDIR）以内。如果路径逃逸了，直接抛异常。为什么要这么干？因为 LLM 生成的路径可能是相对路径，可能是穿越路径，不做检查就能读到工作区外面的任何文件。 safe_path  就是这道安全门，把路径逃逸的可能性彻底堵住。但这只是基础层。
 
系统复杂了，还有一层不能忽视——消息规范化。内部  messages  列表是系统的内部表示，但 API 只能接受特定格式。这里有个关键洞察： messages  列表是内部表示，API 看到的是规范化的副本，两者不是同一个东西。
 
规范化要做三件事：
 
- tool 匹配：每个  tool_use  必须有匹配的  tool_result 。
- 消息交替： user  和  assistant  消息必须严格交替。
- 字段过滤：只发送协议定义的字段。内部可以加元数据、加标记，但发给 API 之前全部要清理干净。
 
记住这一章最重要的三个稳定点就够了：
 
- tool_schema：是给模型看的说明，决定了模型知不知道这个工具怎么用。
- handler_map：是代码里的分发入口，决定了工具调用谁来处理。
- tool_result：是结果回流到主循环的统一出口。
 
把这三点吃透，你就能在不改主循环的前提下，新增任何工具、权限、hook、并发、流式。这些后续层次当然重要，但都应该建立在这个最小分发模型之后。
 
核心公式记一下：加工具 = 加 Handler + 加 Schema，循环永远不变。Dispatch Map 是那个分发表，查表执行替代硬编码判断；路径安全靠  safe_path  从源头卡住； messages  内部可以复杂，但发给 API 必须规范化。
