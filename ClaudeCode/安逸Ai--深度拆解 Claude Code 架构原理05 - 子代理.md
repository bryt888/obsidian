这期讲 Claude Code 里最实用的设计：子代理。很多人在写 AI Agent 时，容易把什么都塞进一个对话里，结果上下文越来越长，答案越来越差。子代理就是来解决这个问题的。
 
当一个 Agent 连续做很多事时，messages 会越来越长。比如用户只问“这个项目用什么测试框架”，但 Agent 为了回答这个问题，可能要读很多文件、搜很多信息，最终答案可能只有一句“用 Python”。问题在于这些中间过程如果都堆在对话里，后面的问题会越来越难回答，因为上下文被大量局部任务的噪声填满了，这就是子智能体要解决的问题。
 
说到底子代理的解决方案很简单，把局部任务放进独立上下文里做，做完只把必要结果带回来。这里有三个核心概念：
 
- 父智能体：就是当前和用户对话、持有主 messages 的 Agent，是任务的发起者和协调者。
- 子智能体：由父智能体临时派生出来，专门处理某个子任务的 Agent。
- 上下文隔离：父智能体有自己的 messages，子智能体也有自己的 messages，子智能体的中间过程不会自动写回父智能体。
 
记住了吗？子智能体的价值不是多一个模型实例本身，而是多一个干净上下文。
 
那子代理的最小实现怎么写？分四步：
 
- 第一步：给父智能体一个 task 工具，让模型可以主动说“这个子任务我想交给一个独立上下文去做”。
- 第二步：子智能体使用自己的 messages 列表，从一份新的列表开始，而不是共享父智能体的 messages，这是隔离的关键。
- 第三步：子智能体通常不需要拥有和父智能体完全一样的能力，只给它文件读取、搜索、bash 之类的基础工具，不给它继续派生子智能体的能力，这样防止它无限递归。
- 第四步：子智能体做完事后，不把全部内部历史写回去，而是返回一段总结。
 
理解了这个原理，具体怎么用代码实现呢？最关键的数据结构是  semantic context ，它包含 message、智能体自己的上下文、工具、智能体可以调用哪些工具、这些工具对应哪些 Python 函数、max turn（防止智能体无限运行）等。
 
但这只是表面，真正面试官追问的时候，会问子代理和 Fork 有什么区别？普通的子任务有时必须知道父智能体之前在聊什么，比如“基于我们刚才讨论的方案去补测试”，这时可以用 Fork，不是从空白 messages 开始，而是先复制父智能体的已有上下文，再追加子任务 prompt。但要记住，Fork 是“下一步”，不是“起步”，要先做隔离，再做高级化。
 
说到这你可能会问，为什么要这么强调隔离？说到底很多新手踩坑，是因为没想清楚子代理的核心价值。
 
- 第一个坑：炫技式并发。把子智能体当成了“为了炫技的并发”，忘了子智能体首先是为了解决上下文问题，不是为了展示有很多 Agent。
- 第二个坑：全量历史回灌。把父历史全部原样灌回去，如果最后又把子智能体全量历史恢复到对话里，那隔离价值就几乎没了。
- 第三个坑：过度角色设计。一上来就做特别复杂的角色系统，比如 explorer、reviewer、planner、tester，这些都可以做，但不应该先做，应先把一个干净上下文的子任务执行器做对，后面角色化只是在它上面再包一层。
- 第四个坑：忘记停止条件。忘记给子智能体设置停止条件，否则子智能体很容易无限循环。
 
所以记住了吗？子智能体的核心不是多一个角色，而是多一个干净上下文，实现顺序也很重要。要先做空白上下文的子智能体，加上 task 工具、run submission 函数、自己的 message、返回摘要，这已经够了；然后限制工具集，只给它读文件、搜索、bash 之类的基础工具，不给它 task 能力；接着加入最大轮数和失败保护；最后才考虑 Fork，只有当你已经稳定跑通前面三步，才考虑 Fork。基础打牢了，后面做 Agent 团队、自主代理这些高级协作，才会有扎实的基础。
