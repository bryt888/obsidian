# Claude Code 上下文(Context)与费用管理新手指南

> 整理自实际的usage排查对话,面向刚开始关注token消耗、想搞懂"为什么账单突然变高"的用户。

---

## 一、核心概念速览

在深入细节之前,先把几个最容易混淆的词捋清楚。

| 概念 | 是什么 |
|---|---|
| **Context(上下文)** | 这一轮请求发给模型、参与生成回答的**全部内容**——system prompt、工具定义、memory文件、skills索引、以及到目前为止的完整对话历史。每一轮都要整个重发一遍,不是只发新增的那一句话。 |
| **Cache(缓存)** | 针对context里"跟上一轮完全没变"的那部分内容给的**计费折扣机制**,不是"免费",而是打折(通常10%价格)。 |
| **Session(会话)** | 一次持续的对话进程。不等于"打开的窗口",而是底层那条连续的对话线;真正终止(比如`/exit`)和只是暂停/挂起(比如Ctrl+C、关闭窗口但被恢复)是两回事。 |
| **`/compact`** | 把当前对话历史**总结**成一段结构化摘要,替换掉原始逐字记录,但保留关键信息(意图、改过的文件、遇到的错误和修法、待办事项)。 |
| **`/clear`** | 完全清空对话历史,不做任何总结,成本为零。 |
| **CLAUDE.md** | 你手写的、持久化的项目/个人指令文件,每次session启动自动加载。 |
| **Auto memory(MEMORY.md)** | Claude自己在过去session里学到的东西(建置命令、踩过的坑等),自动写下来,每次session启动自动加载(有行数/大小上限)。 |
| **Skill** | 按需加载的"技能包"。启动时只加载一行描述当索引,真正被调用时才整个加载进context。 |
| **Subagent** | 有自己独立context窗口的子任务执行者。它读的文件、跑的探索都留在它自己的context里,只有最后的摘要传回主对话——这是省你主对话token的关键手段。 |

## 二、Token是怎么计价的:Context的构成与计费逻辑

### 2.1 `/context`里能看到的各个分类,分别是什么

以实际截图为例(`462.2k / 967.0k tokens`),`/context`把context拆成这几类:

- **System prompt** —— Claude Code自带的核心行为指令,**你改不了**,是固定开销。唯一能间接影响的方式是`--append-system-prompt`这类CLI参数或output style,这些是"追加",不是替换。
- **System tools** —— 内置工具(Bash、Read、Edit、Grep、Glob、WebFetch、WebSearch等)的定义,同样是**固定开销**,你控制不了这部分占多少token,只能通过permission规则限制哪些工具可用。
- **Memory files** —— 你**可以主动管理**的部分,包括:
  - 用户级`~/.claude/CLAUDE.md`(对所有项目生效)
  - 项目级`CLAUDE.md`(只对当前项目生效)
  - Auto memory的`MEMORY.md`(Claude自动写的学习记录,最多加载前200行或25KB)
  - 这三者每次session启动**自动加载**,想精简就直接编辑这些文件,或用`/memory`命令查看编辑。
- **Skills** —— 启动时只加载每个skill的**一行描述**当索引,完整内容只有在实际被调用时才整个加载进来。你可以自由添加更多skill。
- **Messages** —— 你和Claude之间**实际的对话往来记录**,包括你发的每一句话、Claude的回复、以及Claude展示出来的工具调用结果(文件内容、命令输出等)。这是**只涨不消**的一块,细节见下一节。
- **Autocompact buffer** —— 不是你产生的内容,而是Claude Code**预留**出来的缓冲区,专门留给自动压缩发生那一刻需要的空间。
- **Free space** —— 剩余真正可用的空间。一般建议这个数字掉到30%以下就该主动`/compact`或换新session了。

MCP相关工具(如果你连了外部服务)有单独的明细,可以用`/mcp`看每个server具体占多少token;想更细致地看内置System tools的实际内容(不是配置,是debug用途),可以用`claude --debug api`或`--debug-file <路径>`把实际发给API的请求内容记录下来查看,或者去`~/.claude/projects/`下面翻原始session的JSONL记录。

### 2.2 Messages是怎么"存"的:只涨不消,直到触发压缩

这是最容易理解错的一点。Messages的运作机制**不是**"从下往上挤,老的自动被踢出去"这种滑动窗口:

- **只涨不消**:从session开始到现在,所有往来记录原样累加,不会自动丢弃旧的部分,不管context涨到多大。
- **直到触发压缩才整体替换**:当Messages+其他部分逼近上限,Claude Code会自动跑一次相当于`/compact`的动作——不是删掉最老的几条,而是把**整个**对话历史**一次性**总结成一段结构化摘要,原始逐字记录被这份摘要整体替换。是"批量置换",不是"渐进式遗忘"。

### 2.3 每一轮到底怎么计费:Context与Cache的关系

先纠正一个最常见的误解:

> ❌ "context里的内容一直在,是不是只收一次钱,后面就不再收了?"

**不是。** Claude是无状态API,模型不记得上一次请求发生过什么,所以**每一轮都要把完整context从头到尾重新发一遍**,你每一轮都要为这些内容付费——只是付费的"价格档位"不同:

| 情况 | 计费方式 |
|---|---|
| Cache write(首次写入缓存) | 按正常input价格的**1.25倍**收 |
| Cache read / cache hit(命中缓存) | 内容跟上一轮**一字不差**、缓存还没过期 → 按正常input价格的**10%**收 |
| 普通未缓存input | 这轮新增的、没被缓存覆盖的内容(你的新问题、新读的文件),按**全价**收 |
| Output(输出) | **跟cache命中与否完全无关**,永远按标准output价格收 |

**关键结论**:即使context高达几十万甚至上百万token,只要大部分内容命中了缓存,实际账单也不会那么离谱——真正决定成本的是**缓存命中率**,不是context的绝对大小。

**缓存靠"前缀匹配"工作**:缓存覆盖的是从头开始连续没变的那一段。前面任何一个地方发生变化(不管是CLAUDE.md被改、模型被切换、还是MCP server被连接/断开),**从那个点往后**,哪怕后面内容本身没变,也会被当成新内容重新计算、重新写入缓存。以下操作都会触发这种失效:切换模型、改effort level、开关fast mode、连接/断开MCP server、装卸插件、彻底禁用某个工具、执行`/compact`、升级Claude Code版本。

**`/compact`本身也在这份"会打破缓存"的清单里**——即便压缩后重新注入的CLAUDE.md、auto memory内容跟压缩前一字不差,也不能沿用之前的缓存,这部分要按写入价(1.25倍)重新算一遍。这也是为什么"压缩本身是笔不小的开销",不建议无限拖到context爆满才做。

**`/compact`具体保留/丢弃了什么**(压缩之后):

| 内容 | 压缩后怎样 |
|---|---|
| System prompt | 不受影响,压根不属于对话历史 |
| CLAUDE.md(用户级+项目级) | 从磁盘重新注入 |
| Auto memory | 从磁盘重新注入 |
| Skill的一行描述索引 | **不会自动恢复**,除非你重新调用它 |
| 已实际调用过的skill完整内容 | 重新注入,但有上限(每个skill最多5000 token,总共最多25000 token,超了先丢最早调用的) |

## 三、怎么省token、怎么用得更聪明

### 3.1 `/compact` vs `/clear`,具体怎么选

- **同一个任务、只是对话变长了** → 用`/compact`,最好带聚焦指令:`/compact 保留XX的修改细节和还没解决的YY问题`
- **要切换到不相关的新任务** → 用`/clear`。先`/rename`给session起个名字方便以后找,再`/clear`,旧上下文对新任务只是噪音。
- **判断时机看`/context`或status line**,不要等到自动触发才处理——自动压缩用的是通用摘要逻辑,不一定抓得住你真正关心的重点。一般建议Free space掉到30%以下就该主动处理。
- **别等到context爆满再压缩**:上面提过,压缩本身要读一遍全部对话,在一个巨大又早已过了缓存有效期的context上跑`/compact`,本身就是一次很贵的请求。"频繁小步压缩"通常比"攒到最后一次性压缩"更省钱。

### 3.2 写HANDOFF.md/log,是不是在增加token消耗?

**几乎不增加,反而是目前最推荐的做法。** 原因:

- 写一次总结到文件,只是一次性的、很小的写入开销。
- 换来的是:下次开新session,Claude只需要**读这一个文件**(可能几百token)就拿到关键信息,而不是要么让你重新粘贴大段背景,要么自己重新翻文件、重新探索代码库(这个探索过程可能读几千甚至上万token)。
- 更重要的是,这让你可以**放心地`/clear`**——项目状态不再依赖脆弱的对话记忆,而是持久化在磁盘上,随时可以廉价重新加载。

**注意**:这里省的不是"缓存复用"(因为跨session之后旧对话内容不会被当缓存复用),而是"用一次很小的读取,替代了一次很大的读取/探索"。

**具体建议的固定流程**:
1. 项目根目录维护一个`HANDOFF.md`,任务收尾时更新:当前状态、刚改了什么、还有什么坑没填、下一步该干嘛。
2. 设个硬指标触发这套动作:**切换到不相关任务前**,或**`/context`显示超过60-70%时**,就"总结写入HANDOFF.md → `/clear`",而不是任其增长到150k+。
3. 可以在CLAUDE.md里加一段默认compact聚焦指令,让自动压缩也不会瞎总结。

### 3.3 其他省token的手段

- **重活交给subagent**:大量文件读取、跑测试、处理日志这类,委托给subagent,详细内容留在它自己的context里,只有摘要传回主对话。简单的子任务还可以配置成用更便宜的模型(Haiku)跑。
- **选对模型**:Sonnet应付大多数编码任务足够,Opus留给真正复杂的架构决策。
- **精简MCP server**:MCP工具定义即使deferred也占一点索引空间,不用的server用`/mcp`直接禁用。
- **CLAUDE.md控制在200行以内**:细分、不常用的说明挪到skill里按需加载,而不是每次都塞进启动context。

## 四、Session启动与企业版缓存时长

- **缓存活多久取决于你的登录方式**:
  - 用**Claude订阅账号登录**(Pro/Max/Team/Enterprise seat,走`claude.ai`账号)→ 自动申请**1小时**TTL
  - 用**裸API key或第三方provider**(Bedrock/Vertex/自建gateway)→ 默认**5分钟**TTL
  - 如果你的`Account & Usage`里"Auth method"显示的是"Claude AI"、Plan是Enterprise,大概率你是1小时TTL(可以自己验证:等5分钟以上再发消息,看`/usage`里这次请求是cache write还是全价,如果还能命中就是1小时)。
- **Session不等于"关掉的窗口"**:是否算真正结束(触发`SessionEnd`)还是只是暂停/挂起,取决于是主动`/exit`终止,还是被中断后恢复(比如Ctrl+C挂起后resume)。VS Code扩展支持恢复过去的对话,具体关窗口后底层进程是否保留、重开是否自动接上,建议自己实测一次(开对话→关窗口→重开看是接着走还是全新空白)。
- **不管session算不算"新的",时间才是第一决定因素**:如果关闭超过1小时才重开,缓存本来就自然过期了,这时候讨论"git状态一不一致"没有意义;只有在缓存有效期内重开,git状态是否一致才会真正影响能不能接上缓存。
- **Git快照是怎么来的**:Claude Code是跑在你本地电脑上的程序,**每次session启动那一刻**,在本地执行一次`git status`等命令,把结果当纯文本拼进system prompt。这只发生在启动那一刻,不是持续监控——session内部你手动改文件不会让它重新去读取。真正起作用的场景是**跨session对比**:两次session启动时git状态文本不一样(比如中间提交过commit),前缀就对不上,缓存没法跨session复用。模型本身完全不知道你文件变了,它只是"看到"了Claude Code选择塞给它的这段文本。

## 五、其他要点补充

- **"Context和Cache是不是一回事"** —— 不是。Context是这一轮发送的全部内容;Cache是针对这份内容里"没变的那部分"给的计费折扣机制,二者是"内容"和"计费方式"的关系,不是同一样东西。
- **Output token的计价永远不受cache影响**,不管你的input命中率多高,output都按标准价全额计费。
- **`/context`里分类展示的先后顺序,不等于底层实际拼接context的物理字节顺序**——它更像是为了方便阅读做的逻辑分组,不建议拿这个顺序做精确的字节级推算。
- **Agent teams(多个teammate并行跑)token消耗会明显更高**(官方口径大约是标准session的7倍左右,因为每个teammate都有自己独立的context窗口),团队规模要控制、任务要拆小。
- **`/usage`和`/context`的数字都是本机session的近似估算**,不包含其他设备或claude.ai上的用量,精确账单以Console/组织后台的usage页面为准。
