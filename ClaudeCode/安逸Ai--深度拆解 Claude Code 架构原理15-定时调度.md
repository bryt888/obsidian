深度拆解 Claude Code 架构原理（14）定时调度
 
我是安逸，这期聊定时调度。看名字感觉挺简单，但它是 Claude Code，只能响应现在，升级到能安排未来的关键一步。我会先说清楚定时调度要解决什么问题，再讲 cron 表达式和持久化的核心概念，然后带你过一遍 3 组件最小模型和数据结构。最后还有新手最容易踩的 5 个坑，特别是最后那个坑。
 
很多人在实现调度时理解偏了，把调度触发做成了另一条执行链路。记住这期能帮你少走很多弯路。后台任务已经能让慢命令不阻塞主循环了，但它是现在就开始，结果稍后回来。可真实场景不是这样的，用户会说每天晚上跑一次测试，半小时后提醒我继续。这些都不是现在做，而是未来某个时刻出发。
 
所以定时调度要解决的问题是先把一条未来要执行的意图记下来，等时间到了再出发。没有这个能力，系统看起来就永远只能想应当下。定时调度先要把三个概念弄清楚。
 
- 第一是调度器，它专门负责看时间、查任务，决定是否触发，是整个机制的核心。
- 第二是 cron 表达式，这是最常见的定时写法。5 字段版本是分时日月周，比如  0 9 * * 1  表示每周一早上 9 点。不过这里重点不是背语法，而是理解系统怎么记住任务并在合适时刻触发。
- 第三是持久化，意思是程序重启后调度记录还在，这是真正可用的调度系统的必备能力。
 
定时调度的最小心智模型可以拆成三个部分：调度记录、定时检查器、通知队列。整个链路是这样走的：
 
- 首先调用  schedule create  创建一条调度记录，写入列表或文件保存。
- 然后后台检查器每分钟扫描一次，看现在的时间是否匹配某条记录。如果匹配就把对应的 prompt 放进通知队列。
- 最后主循环下一轮，把这条通知当成新的用户消息喂给模型。
 
这条链路说明了一个关键点，定时调度不是另一套 agent，它最终还是回到同一条主循环。来看调度记录的核心数据结构。一条完整的  ScheduleRecord ， id  是唯一编号，用来标识每条任务； cron  字段存定时规则； prompt  存的是时间到了之后要注入主循环的内容； cron  字段表示这条任务是反复触发还是只执行一次； durable  决定是否落盘保存； last_fired_at  记录上次触发时间。这个字段很多人会漏掉，但没有它系统很容易在短时间内重复触发同一条任务。
 
最小实现分四步：
 
- 第一步允许创建调度记录，核心就是把任务信息组装成一条记录加到列表里。
- 第二步写一个定时检查循环，在  while  循环里每分钟检查一次当前时间是否匹配。
- 第三步是匹配成功就发通知，把  prompt  封装成通知结构放进队列，同时更新  last_fired_at  防止重复。
- 第四步最关键，主循环像处理后台通知一样处理定时通知，把通知内容转成用户消息格式注入，这样定时任务最终还是由模型接手继续执行。
 
定时调度和后台任务是两兄弟，解决的问题很接近，但不是同一件事。后台任务回答的是已经启动的慢操作结果什么时候回来，定时调度回答的是一件事应该在未来什么时候开始。正因为顺序是先等结果回来，再理解未来触发新意图，性质上更顺。两者最好的统一方式是都走通知队列，在下一次模型调用前统一注入，这样主循环结构不会越来越乱。
 
这一章新手最容易踩的 5 个坑一定要避开：
 
- 第一个是沉迷 cron 语法细节，这章主线是调度记录怎么进通知队列，不是研究表达式。
- 第二个是漏掉  last_fired_at ，导致任务短时间内被重复触发。
- 第三个是只放内存不支持落盘，用户刚说完“明天提醒我”程序就关了。
- 第四个是把调度触发结果直接在后台默默执行。正确做法是时间到了先发通知，让主循环决定怎么处理，这样系统行为更透明。
- 第五个是误以为定时任务必须毫秒级精准，其实分钟级检查就足够了。
 
最后记住这句话就够了：后台任务是在“等结果”，定时调度是在“等开始”。调度器做的是“记住未来”，不是取代主循环。
 
教学版只需要看清 3 点： ScheduleRecord  负责记住未来何时开工，真正执行时仍然回到任务系统和通知队列。它只是多了一种开始入口，不是多了一条新的主循环。把这些吃透，你就真正理解了定时调度的本质。
