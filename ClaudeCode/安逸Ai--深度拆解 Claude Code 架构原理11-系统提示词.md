先说清楚一个基础概念：system prompt，就是给模型的系统级说明。它负责告诉模型4件事：你是谁？你能做什么？你应该遵守什么规则？你现在处在什么环境里？很多人一开始把它当成一整段固定文本塞进去，这样在小demo里确实能跑，但一旦系统开始整功能，问题就来了。
 
所以到了这个阶段，system prompt不再是死字符串，而是一条构建流水线。它由6个部分按顺序拼接：core核心身份和行为说明、tool工具列表、skills原信息、memory内容、CLAEMED指令链、Dynamic context动态环境信息。这6段各管各的事，最后拼成一份完整的系统输入。
 
这里的核心思想是把不同来源的信息分成独立的模块来组装，每个模块有自己专门的构建方法。比如build TOOLS只负责生成工具说明，build memory只负责拿记忆内容，build code MD只负责读指令文件。这样做的好处是每一段职责很清晰，随时知道哪一段来自哪里，该改哪一部分。
 
还有一个关键边界要搞清楚：稳定说明和动态提醒必须分开处理。core、TOOLS、skills、memory、CLAUDE.md这些属于相对稳定的内容，而day day、current问题、current model这些每轮都可能变一个。实用的做法是加一个边界标记Dynamic boundary，上面更稳定，下面更容易变。这么一分就知道哪些该缓存，哪些该实时更新了。
 
再说一个容易混淆的点：system prompt和system reminder是两码事，prompt是合放身份、规则、工具，长期约束这些不变的东西；reminder则专门处理每轮临时需要的补充上下文和当前变动状态。所以更清晰的做法是主prompt保持稳定，每轮额外变化的内容用reminder单独追加，而不是全搅在一起。
 
很多初学者会把memory、skills、CLAUDE.md混成一回事，它们的区别其实很清楚。skills是可选的能力或知识包，memory是跨会话仍有价值的信息，CLAUDE.md是长期规则说明，它们都可能进入prompt，但来源和职责完全不同。memory的本质是把跨会话仍有价值的信息重新带回当前工作环境。
 
为什么不能把所有东西硬塞进一个大字符串？原因有三个：
 
- 第一不好维护，你不知道哪段来自哪，改哪一段。
- 第二不好测试，你没法单独验证工具说明对不对，memory有没有拼进去。
- 第三不好缓存和动态更新，稳定内容每轮都重算很浪费，临时内容又该只活一轮。
 
把这三种问题分开处理，系统才能真正长大。
 
总结一下这章的核心，system prompt关键不是写一段很长的话，而是把不同来源的信息按清晰边界组装起来，你需要理解6个组成部分各自负责什么，稳定部分和动态部分怎么分界。memory、skills、CLAUDE.md虽然都进prompts，但不是一回事。这一章先建立这个心智模型就够了，其他复杂的section、注册缓存预算那些后面再慢慢展开。
