上期视频分析了一个“hello”请求的全部细节，发现消耗近3万个token。有朋友问连续聊10条是否会消耗30万token，答案是否定的，本期就详细讲解Prompt Cache提示词缓存的工作原理。
 
上期介绍的claude-trace是在代码里打补丁，但最新的2.1.119版本已不能用，官方也不再支持npm安装。为解决这个问题，新工具claude-tap应运而生。它在本地起一个代理服务器，启动后自动启动Claude Code，所有API流量经代理转发，退出后生成html文件，打开浏览器即可查看。
 
生成的html中，左边导航栏列出每一次API请求，右边最底部是原始请求的JSON数据，和claude-trace生成的网页类似。但claude-tap更出色的是将tool、messages、system等重要数据字段抽离成独立模块显示，还对每一块进行分行渲染，让原本满是 \n 分行符、读起来头疼的原始请求变得整齐易读。它还有“对比上次”的杀手功能，可将相邻两次请求放在一起对比，新增内容高亮，未变内容灰色。
 
使用claude-tap很简单，用 claude-tap --tap-live 收集所有请求，启动claude，发送三条消息“hello”“fine”“thank you”，退出后就能看到收集的提示词用于分析。
 
在看数据前，先讲Prompt Cache的核心概念，其正式名称是前缀缓存（prefix caching）。每次发消息，Claude Code会把完整请求发给API，请求包含工具定义、系统提示词、用户注入的上下文、对话历史，服务器按固定顺序排列这些内容，组成缓存的查询键。前缀缓存逻辑很简单，若两次请求前缀相同，第二次就不用重新推理，直接从缓存读结果；若前缀不同，缓存全部失效。这里的“相同”是指服务器对前缀做哈希，一个字符不差才算命中。
 
打开抓取的html结果里的第一个请求，按前缀顺序看：最前面是包含31个工具定义的工具部分；中间是Anthropic写的三段系统提示词，规定了Claude Code的身份、做事方式和行为准则；最后是消息部分，消息被包装成5个block，前4个是Claude Code注入的hook配置、MCP指南、skills列表、CLAUDE.md等，最后才是用户写的“hello”。要记住，用户输入永远在最末尾，前面内容只要不变，就可直接复用缓存里已推理好的结果。
 
现在看关键数据，打开第一个请求的返回值，找到 usage 字段： input_tokens 等于6，对应“hello”本身； cache_creation_input_tokens 为48000，将近5万个token，这是工具定义、系统提示词、用户注入上下文等内容首次写入缓存的量； cache_read_input_tokens 为0，说明第一条消息没有缓存可读，这就是冷启动。
 
继续看第二个请求，用“对比上次”功能发现，消息从1条变成3条，新增了assistant的回复和用户消息“fine”，系统提示词和工具定义都没变，只有用户消息变化。再看 usage 字段： cache_creation 为24， cache_read 为48000，和上一轮的 cache_creation 完全一样，证明缓存完全命中。这里的 cache_creation 24对应新增的assistant回复和用户新消息“fine”，只有这两条新增消息需要加入缓存。
 
再看第三个请求，对比上次发现，又多了两条消息，assistant回复“Got it. Let me know when you have something to work on.”，用户回复“thank you”，其他内容依旧未变。看 usage 字段的 cache_read 为48678，这个数值是上一次的 cache_read 48654加上24得到的，说明上一次所有写入的缓存全部命中。这次写入的29个token对应新增的回复和“thank you”。
 
把三轮数据放一起，规律很清晰：每一轮的 cache_read 等于上一轮的 cache_read 加上上一轮的 cache_creation ，缓存像滚雪球一样越滚越大，但每轮新增的只有几十个token。三轮下来，总的上下文只多了53个，信息从1条涨到5条，新增计算量几乎可忽略不计。工具定义、系统提示词、用户注入上下文每次每轮都要带上，但只有第一次做了真正的推理，后面全部走缓存。
 
从费用角度看，缓存有三种计费方式：普通输入是正常价；cache写入比正常价贵一点，5分钟缓存写入是1.25倍，一小时缓存是两倍；而缓存读取只有正常价的1/10。第一轮冷启动将近5万个token按两倍写入，看起来不划算，但从第二轮开始，这5万个token几乎全部走cache读取，只花正常价的1/10。第3轮、第10轮、第50轮都是如此， cache_read 越来越大，但每个token只花1/10，所以对话越长，缓存的优势越明显。
 
总结来说，Prompt Cache是前缀的复用，工具定义、系统提示词、对话历史只有在第一轮计算，后面每轮新增的只有几十个token，对话越长，cache省的越多。
