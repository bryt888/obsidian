深度拆解 Claude Code 架构原理16-团队协议
 
大家好，我是安逸。在《Claude Code团队协议》的团队架构里，队友之间已经能互相发消息了，但光靠自由文本聊天，系统很难稳定协作。今天这期我们讲团队协议，这是整个多智能体协作体系里的关键一层。我会从为什么需要协议讲起，拆解协议、request_id和请求追踪表这两个核心概念，再带你实现优雅关机和计划审批两个实际协议，最后讲清楚协议消息和普通消息到底有什么区别。搞懂这套结构化协作框架，你对agent团队的理解会更上一个台阶，主页有更多Claude Code架构解析，点个关注不迷路。
 
上一期我们讲了GPS团队如何让队友之间互相发消息，但只靠自由文本聊天会有两个明显问题。首先，某些动作必须得到明确批准或拒绝，比如关机请求，你不能只回一句“好的”，系统根本没法判断你是同意还是拒绝。其次，一旦多个请求同时存在，没有编号的话，系统根本不知道这条回复对应哪一件事。所以这一章要加的不是更多的自由聊天，而是一层结构化协议。
 
理解团队协议之前，有三个概念必须先搞清楚。第一个是“协议”，可以简单理解成双方提前约定好消息长什么样，收到以后怎么处理。第二个是“request_id”，也就是请求编号，它让每个请求都有唯一身份，后续的批准、拒绝、驳回都能准确指向这个请求。第三个是“请求-响应模式”，一方发起请求，另一方明确回答同意还是不同意。这一章做的就是把这个模式从口头表达升级成结构化数据。
 
从教学角度，你可以先把协议看成两层。第一层是“协议消息层”，它本质上是一个带类型的消息对象。第二层是“请求追踪表”，就是一个字典，记录每个请求的状态。这两层配合起来，系统就能同时回答两个问题：现在发生了什么，以及这件事目前走到哪一步。这是最核心的心智模型，后面的所有实现都建立在这个基础之上。
 
实际实现中有三个关键数据结构。第一个是 ProtocolEnvelope ，带类型和编号的消息。第二个是 RequestRecord ，记录请求状态和收发方。第三个是“状态机”，这里只有三种状态切换：pending→approved/rejected/expired。状态机不是复杂理论，只是状态之间如何变化的一张规则表。
 
第一个实际协议是“优雅关机协议”。“优雅”的意思不是直接把线程硬砍掉，而是先发关机请求，队友明确回复同意或拒绝，同意的话先收尾再退出。实现起来就是三步：发起请求时生成request_id，写入追踪表；同时投递一条带编号的shutdown_request消息到对方邮箱；收到回复时，根据参数更新请求状态为approved或rejected。这就是完整的一次协议交互。
 
第二个协议是“计划审批协议”。这和关机其实是同一个模板，队友想做高风险改动时提交计划请求，Lead收到后进行审批。代码结构完全一样：生成request_id，写入追踪表，投递消息。区别只是消息里的payload是计划内容，审批通过就把状态改成approved，不通过改成rejected，还可以附带反馈意见。这个例子告诉我们，协议模板是可以复用的，不同业务场景用同一套结构，这一点一定要搞清楚。
 
虽然都叫消息，但现在已经分成两类。第一类是“普通消息”，适合讨论、提醒、补充说明这些场景。第二类是“协议消息”，适合审批、关机、交接、签收这些需要明确结果的动作。协议消息至少要带type、request_id、from、to和payload这几个字段。最简单的记法是：普通消息解决“说了什么”，协议消息解决“这件事走到哪一步了”。
 
协议真正接入团队系统后，形成一条完整的协作回路，流程是这样的：某个队友发起请求，同时写入request record；然后把protocol envelope投递进对方邮箱；对方下一轮处理时，按request_id更新请求状态，必要时再回一条response；请求方收到回复后，根据approved或rejected决定后续动作。如果少了这条结构化回路，团队虽然能沟通，但无法稳定协作。
 
 MessageEnvelope 、 ProtocolEnvelope 、 RequestRecord 、 TaskRecord 这四个对象很容易搞混。 MessageEnvelope 回答“谁跟谁说了什么”，字段是from、to、content。 ProtocolEnvelope 回答“这是不是一条结构化请求或响应”，额外带type、request_id。 RequestRecord 回答“这件协作流程现在走到哪一步”，记录kind、status、from、to。 TaskRecord 回答“真正的工作是什么？谁在做？还卡着谁”，有action、logic、knowledge、by、owner。要记住，协议只负责协作流程，任务系统才负责真正的工作推进。
 
学协议实现最容易犯四个错误。第一是忘掉request_id，没有编号，多个请求同时来就全乱了。第二是收到请求只回一句自然语言，比如“好的，我知道了”，人类看得懂但系统没法处理。第三是没有请求状态表，协议就等于没真正落地。第四是把协议消息和普通消息混成一种结构，这样后面逻辑会越来越乱。避开这四个坑，你的协议实现就基本没问题了。
 
教学版这一章只实现了两类协议：shutdown和plan_approval。为什么只讲这两类？因为它们已经足够讲清楚结构化消息、request_id、请求状态表，以及为什么协议不是自由文本。这套模板学稳了，你可以自己扩展更多协议类型，比如任务交接、资源申请、状态通报，但所有扩展都应该建立在本章的统一模板之上，不要另起炉灶。
 
学完这一章，你应该能独立复述四件事。第一，团队协议的核心是“请求-响应 + request_id + 状态表”三要素。第二，协议消息和普通聊天消息不是一回事，解决的问题完全不同。第三，关机协议和计划审批虽然业务不同，但底层模板完全可以复用。第四，团队一旦进入结构化协作，就要靠协议，而不是只靠自然语言。如果这四点已经非常清晰，说明这章真正学透了。
