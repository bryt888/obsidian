深度拆解 Claude Code 架构原理17- 自主代理
 
我是安逸，今天聊自主代理。这是call the code团队协作体系里很关键的一章，我会先讲清楚为什么要自治，再带你理解work和IDLE切换逻辑，然后重点拆解任务认领的判定条件和实现流程。自治听起来复杂，但核心就一句话：让空闲队友在规则下自己接住下一份工作。
 
直接开始，上一章团队协议建立了结构化协作，但还剩一个明显瓶颈，很多事情仍然要靠lead手动分配。任务板上有10条可做任务，lead就得一个个点名，团队规模一大，lead直接变成卡点。所以这一章的核心目标就是让空闲队友自己扫描任务本，找到可做的任务并认领，把lead解放出来，让其做更重要的决策。
 
再说实现之前，先把3个关键名词理清楚。自治不是完全没人管，而是在提前给定规则的前提下，队友可以自己决定接哪份工作。认领就是把原本没人负责的任务标记成现在由我负责。空闲阶段更不是关机，它表示这个队友当前手头没活，但仍然“活着”，随时准备接新任务。
 
这三个概念组合起来就是自治的基础语义。最清楚的理解方式是把每个队友想成在两个阶段之间切换。当前轮工作做完或主动进入idle后，队友会看两样东西：邮箱有新消息就回到工作流程，任务板有可认领任务就认领，然后回到工作流程。如果长时间什么都没有就shut down退出。
 
这里的关键不是让队友永远不停想，而是空闲时按规则检查两类新输入：邮箱和任务板。和任务系统一样，这里最重要的是判定什么任务算当前可被这个队友安全认领。教学代码里有几个条件，必须同时满足：
 
- 条件一：status = pending（未开始）
- 条件二：owner = 空（无人认领）
- 条件三：blockedBy = 无（无前置阻塞）
- 以及队友角色满足任务的claim role或required role
 
最后这条很关键，因为现在任务可以指定角色条件，不是谁空着谁就拿，必须先过角色过滤。认领成功后，要记录完整过程，任务记录会发生几个关键变化：
 
- owner字段写入队友名字
- status → in_progress
- 新增claimed_at记录认领时间
- claim source标记是auto还是manual
 
但更值得单独记住的是事件日志，每条认领动作都会追加到特定日志文件，日志回答的是系统刚刚做了什么，包括是谁什么时候自动认领，还是手动调用认领任务，这些信息只看最终任务文件是看不出来的。
 
自治认领的完整实现流程分五步：
 
1. 循环 WORK→IDLE：队友在工作和空闲状态间循环
2. 邮箱优先：任务认领前先查邮箱，优先处理明确发给自己的工作
3. 角色过滤扫描：如果邮箱没消息，再按当前角色扫描可认领任务
4. 补身份：认领后先补身份上下文，再把任务提示塞回主循环
5. 长时间没事就退出
 
特别注意认领不是无差别扫任务，而是带着角色过滤，不是空闲了就乱抢一条。
 
为什么认领必须是原子动作？原子动作的意思是认领要么完整成功，要么不发生，不能一半成功一半失败。这是因为两个队友可能同时扫描到同一个可做任务，如果没有锁，两人可能同时把自己写成owner，导致状态混乱。所以最小实现也必须加锁，在认领时检查任务是否已被认领，确保并发安全。
 
当上下文压缩发生后，队友可能丢掉关键身份信息，比如自己的名字、角色、所属团队等。如果没有这些信息，队友后续行为很容易偏离设定。最小补法是重新注入身份提示，包括角色和团队信息，再补一条确认语，让下一轮继续知道自己的身份。这里可以理解成一条恢复规则，任何一次从idle恢复或任何一次压缩后恢复，只要身份上下文可能变薄，就先补身份，再继续工作。
 
这层边界很容易被混淆：自治的执行者是长期的agent队友，有名字、有角色、有邮箱、有idle阶段，可以反复接活，他不是那种接一条子任务，做完返回摘要，然后立刻消失的一次性subagent。同样，这里认领的是任务系统里的工作图任务，而不是后台任务里的后台执行槽位。自治是在长期队友和工作图任务这两条已存在的主线上，用认领连接起来。
 
来总结一下这章的核心心智。自主代理其实是在已有团队协议之上，额外获得空闲时自己找活的能力。协议系统继续存在，自治扫描与认领开始存在，这两条线一起存在，团队才像一个真正的平台。自治不是让agent乱跑，而是让他在清晰规则下，自己接住下一份工作。记住这句话，你就真正理解了自治是什么。
