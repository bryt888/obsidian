我是安逸，今天聊agent和团队这个话题。这章要解决的核心问题是怎么让AI代理不再是干完活就消失的一次性工具，而是能长期在线反复接任务的稳定队友。
 
我会从teammate的定义说起，讲清楚名册和邮箱这两个核心组件，再帮你理清它和Subagent、Runtime Task的本质区别，特别是最后那个对比表，很多人之前一直搞混这三种机制。
 
首先说清楚为什么单靠Subagent不够用？Subagent的生命周期是创建、执行、返回摘要，然后消失，这适合一次性的小委派。但如果想让一个测试agent长期待命，让两个agent长期分工，或者让某个agent未来收到新任务后继续工作，Subagents就力不从心了。
 
系统现在缺的不是再开一个模型调用，而是一批有身份能长期存在、能反复协作的队友。这个转变非常关键，它决定了多agent最后能不能真正跑起来。理解agent团队只需要搞懂三个概念：
 
- 第一，队友（Teammate）：它是一个拥有名字、角色、消息入口和生命周期的持久agent。
- 第二，名册（Roster）：这是团队成员列表，回答现在队伍里有谁，每个人是什么角色，当前是空闲还是工作中。
- 第三，邮箱（Inbox）：每个队友都有自己的收件箱，别人把消息发到这里，队友在下一轮工作前先去收消息。
 
把这三个概念串起来，名册告诉你队伍里有哪些人，邮箱让消息有地方可去，队友在这个基础上独立运转。最小实现里需要三个核心数据结构：
 
- 第一个，TeamMember：包含name（名字）、role（角色）、status（状态）三个字段。
- 第二个，TeamConfig：它管理整个团队的名册，通常放在team config的json文件里，这很重要，因为有了名册，系统重启后仍然知道团队里曾经有谁。
- 第三个，MessageEnvelope：是消息的信封，把消息正文和原信息包起来，包含type（消息类型）、from（发送方）、content（消息正文）、time stamp（时间戳）这几个字段。理解这三个结构怎么配合，就理解了整个团队系统的骨架。
 
具体怎么实现一个最小可用的agent团队，分四步走：
 
- 第一步，建立名册并持久化存储：这是整个系统的起点，没有名册就没有真正的团队实体。
- 第二步，Spawn队友，构建持久生命周期：关键是它一旦被创建，就不只是工具调用，而是一个有持续生命周期的成员。
- 第三步，建立邮箱，实现异步消息：最简单的做法是用jsonl文件，每条消息追加一行，队友下一轮先处理收件箱再继续工作。
- 第四步，循环处理，持续监听：队友在自己的循环里持续处理消息，靠检查邮箱来接收新任务，而不是被重新创建。
 
这三个概念特别容易混淆，直接说清楚：
 
- Subagent：像一次性外包助手，干完就结束，核心价值是隔离一小段探索性上下文，适合“帮我查一下再回来汇报”的场景。
- Runtime Task：是正在运行的后台执行槽位任务，跑完或取消就结束，核心价值是处理慢任务，“稍后回来通知”，不是长期身份。
- Teammate：是长期在线队友，可以反复接任务，核心价值是有名字、有邮箱、有独立循环，适合长期负责某个方向。记住口诀：“Subagent查完就走，后台跑着等，Teammate长期在线接活”。
 
最后说几个初学者常踩的坑：
 
- 第一个，Subagent思维：把队友当成名字不同的Subagent，如果生命周期还是执行完就销毁，那本质上还是Subagent，不是真正的团队。
- 第二个，Messages共用：队友之间共用同一份message，导致上下文互相污染，每个队友都应该有自己的对话状态。
- 第三个，没有持久名册：系统关掉后完全不知道团队里曾经有谁，很难做长期协作。
- 第四个，没有邮箱：靠共享变量直接喊话，把队友通信和进程内部细节绑得太死。建议开始就按“名册+邮箱”的结构来做，为后续扩展留好空间。
 
总结这章的关键知识点：Teammate的核心不是多一个模型调用，而是多一个长期存在的执行者；团队系统至少需要名册、邮箱、独立循环这三样东西；每个队友都应该有自己的messages和inbox；Agent和Teammate的根本区别在生命周期，而不是名字。
 
如果这几点你都能说清楚，说明你已经真正理解了多agent团队是怎么从单agent演化出来的。
