#### 10.1 Cost Control: Let Tokens Work for You, Not Burn Money.

"How exactly are the fees for Claude Code calculated?" Xiao Bing asked. This problem is far more complex than it appears on the surface. The API call fees for Claude Code are essentially token-based, meaning the sum of the number of Prompt Tokens sent in each call and the number of generated response Tokens is multiplied by the unit price of the corresponding model. However, behind a single user request, Claude Code might initiate a dozen or even dozens of API calls, including reading files, executing searches, logical reasoning, generating code, and secondary verification, with each call incurring a fee.

##### 10.1.1 Understanding the Pricing Structure.

The pricing of Claude models at the end of 2025 is shown in Table 10-1.

**Table 10-1 Claude Model Pricing (Unit: USD/Million Tokens)**.

|Model|Input Price|Output Price|Cache Write|Cache Read|
|---|---|---|---|---|
|Haiku 4.5|1.00|5.00|1.25|0.10|
|Sonnet 4.6|3.00|15.00|3.75|0.30|
|Opus 4.6|5.00|25.00|6.25|0.50|

Several key insights can be drawn from Table 10-1.

- **Output costs are much higher than input costs**. Taking Opus as an example, its unit output price is 5 times its unit input price. This means that compared to controlling the input length, strictly controlling Claude's output length can reduce costs much more significantly.
- **The price difference between different models is huge**. Opus is priced up to 5 times that of Haiku. Therefore, not all tasks require calling the strongest model; they should be selected on demand according to the scenario.
- **Cache reading has a significant cost advantage**. Its price is only one-tenth of the normal input price. Whenever possible, the cache hit rate should be maximized to save expenses.

There is also an easily overlooked source of cost—Extended Thinking. By default, Claude Code's thinking budget is set to 31,999 Tokens, and the Tokens in the thinking process are billed at the output price. For Opus, a single deep thought could consume tens of thousands of output Tokens—the cost of which even far exceeds the finally generated code itself. In scenarios that do not require deep reasoning, users can limit the thinking budget by setting the environment variable `MAX_THINKING_TOKENS=8000`, thereby significantly saving costs.

##### 10.1.3 Context Management is the Core of Cost Control.

Why repeatedly emphasize sub-agents and context isolation?. Aside from the technical benefits of improving the signal-to-noise ratio, there is also a purely economic motivation. The Claude API is stateless; every call must carry the complete dialogue history. Imagine if a 5000-line log file is directly read into the main dialogue, these 5000 lines of content will be repeatedly sent in every subsequent API call, which means that for every decision step Claude executes, you are paying again for those 5000 lines of logs. Conversely, if log analysis is delegated to a sub-agent, the massive log content is isolated within the child process's context, and the main dialogue only needs to receive a few lines of key conclusions. Therefore, sub-agents are by no means a luxury to merely "ice the cake," but rather a crucial economic decision-making tool. The same logic applies to streamlining `CLAUDE.md`. This file is automatically loaded during every API call, and a bloated `CLAUDE.md` (for example, stuffed with a full API document up to 45,000 Tokens long) will result in persistently high base costs for every dialogue. The official recommendation is to keep `CLAUDE.md` under 500 lines; for detailed documents, they should be moved to separate files to be read on demand, or transformed into Skills to be triggered only in specific scenarios.

#### 10.2 Debugging: Opening the Black Box.

"Why did Claude do this?" This is one of the most frustrating questions when using AI tools. When Claude produces unexpected results (such as repeatedly reading the same file, executing uninstructed operations, or consuming massive amounts of Tokens in a loop without yielding any output), traditional debugging methods (such as setting breakpoints, viewing call stacks, or checking variable values) are often helpless. This will allow you to inspect the specific information Claude received at that moment, as well as to review the judgments and tool-calling logic Claude made based on that information.

##### 10.2.5 Diagnostic Approach for Claude's Anomalous Behaviors.

The vast majority of Claude's anomalous behaviors can be attributed to the following 3 categories of reasons. It is recommended to troubleshoot in this order, which usually helps quickly locate the core of the problem.

**Category One, Context Missing.**. Root cause: Claude cannot obtain the key information needed to complete the task. Typical symptoms: repeatedly reading the same file, answering questions vaguely, or noticeably lacking contextual basis. Diagnostic method: use `--debug` to check the file contents and context scope that Claude actually received. Solution: supplement clear project navigation guidelines in `CLAUDE.md`, or directly provide necessary context information and code snippets within the Prompt.

**Category Two, Instruction Conflict.**. Root cause: There are two or more contradictory rules in `CLAUDE.md`. Typical symptoms: behavior fluctuates between two modes, or directly ignores some established rules. Diagnostic method: comprehensively review all rules in `CLAUDE.md` to identify points of logical mutual exclusivity. Solution: clarify rule priorities. Use explicit declarations to resolve ambiguities, such as "When rule X conflicts with rule Y, prioritize following rule X.".

**Category Three, Insufficient Tool Permissions.**. Root cause: Claude attempts to execute an operation but lacks the corresponding tool support or permission authorization. Typical symptoms: fails after repeatedly attempting an operation, or is forced to use inappropriate alternative tools to complete the task. Diagnostic method: check the `--allowedTools` configuration and review the Hook's interception logs to confirm if any requests were blocked. Solution: open necessary tool permissions, or adjust the task description to guide Claude to use currently available alternatives.

**Brother Ka's Remarks** The essential difference between debugging Claude and debugging code: code execution is deterministic, where the same input inevitably produces the same output; whereas Claude's behavior is probabilistic, and the same Prompt in different contexts might trigger completely different reactions. Therefore, you cannot rely on the traditional "bug reproduction" mode to solve problems; you must instead rely on log analysis, audit trail backtracking, and `CLAUDE.md` rule reviews to infer the root cause of the problem.

#### 10.3 Security Guidelines: Least Privilege is the Baseline.

"Although Claude Code is powerful, it might also generate high-risk operations," Xiao Bing asked, "How can we effectively constrain it to prevent it from executing non-compliant operations?". There is no perfect, once-and-for-all answer to this; it relies solely on rigorous engineering discipline. Security is by no means reliant on a single simple switch, but depends on a layered, defense-in-depth system.

##### 10.3.5 Trust Assessment of MCP Servers.

Each MCP server acts as an agent for Claude to interact with external systems. If an MCP server has malicious intent or security vulnerabilities, attackers might exploit it to transform Claude's tool-calling capabilities into unauthorized access to intranet resources. Therefore, when introducing an MCP server, a strict review checklist must be executed, including source credibility (confirming whether it comes from an official or well-known developer), code transparency (ensuring the code is open source and open to auditing), and permission rationality (evaluating whether its requested permission scope conforms to the **principle of least privilege**). A highly overlooked risk: once an MCP server is authorized, the system will not seek user consent again during subsequent updates. This means that an initially safe MCP server could have malicious code implanted during a certain automatic update.

Version pinning is a necessary defense measure. You can mandatorily specify and use a verified specific version to prevent automatic upgrades to untrusted versions. In automated environments like CI/CD, the `--strict-mcp-config` parameter must be used. This parameter ensures that the system only loads pre-specified MCP configurations and ignores all other sources, thereby eliminating unauthorized service access.

##### 10.3.6 API Key Lifecycle Management.

With the deep integration of Claude Code in development workflows, references to `ANTHROPIC_API_KEY` in projects are increasingly growing. To ensure security, a strict API key lifecycle management mechanism must be established. Core management principles are as follows.

- **Isolation**: Assign independent API keys for different projects and environments (such as development, testing, and production), avoiding a "one key fits all" approach.
- **Regular rotation**: Formulate plans to regularly update keys to reduce the risk of long-term leakage.
- **Emergency response**: Establish a rapid response mechanism; the moment a key leak is suspected or confirmed, revoke and regenerate it immediately.

A single measure is insufficient to guarantee security; it is recommended to implement the following 4 layers of protection simultaneously.

- **Storage isolation**: Strictly store keys in the `.env` file.
- **Version control exclusion**: Explicitly exclude the `.env` file in `.gitignore`.
- **Runtime blocking**: Configure `permissions.deny` rules in `.claude/settings.json` to explicitly forbid Claude from reading `.env` and its related files.
- **Pre-commit interception**: Deploy a `PreToolUse` Hook to scan before code submission or executing related commands, detecting and intercepting any behavior that attempts to accidentally commit a key.

#### 10.4 Large Codebases: Navigating Millions of Lines of Code Within a Limited Context Window.

The larger the scale of a codebase, the more severe the challenges Claude Code faces. This is not because Claude lacks capability, but because it is restricted by a limited context window. Although Claude's standard context window is 200,000 Tokens, this does not mean you can cram in an equivalent amount of code. After deducting the System Prompt (about 5,000 Tokens), the `CLAUDE.md` configuration file (about 2,000 Tokens), the dialogue history (about 20,000 Tokens), tool definitions and return results (about 10,000 Tokens), and the necessary safety margin (about 20,000 Tokens), the actual space available to carry code leaves only 143,000 Tokens, which translates to 35,000 to 40,000 lines of code. However, the code volume of a medium-sized e-commerce backend system easily exceeds 50,000 lines, and enterprise-level SaaS projects often exceed 200,000 lines. The conclusion is obvious: for large projects, it is impossible to load them entirely into the context all at once; a chunking strategy must be adopted.

##### 10.4.1 Hierarchical `CLAUDE.md`.

In a Monorepo architecture, the hierarchical layout of `CLAUDE.md` is the core infrastructure for managing large codebases. In contrast, the `CLAUDE.md` in parent directories will recursively search upwards starting from the current working directory, accumulating loads layer by layer.

This mechanism makes the configuration management of a Monorepo extremely flexible: the `CLAUDE.md` in the root directory can define the overall architecture and cross-module specifications, while the `CLAUDE.md` under each sub-module directory focuses on describing internal module details. #### 10.5 Instructions: Writing Good `CLAUDE.md` and Prompts.

"For the exact same task, why can someone make Claude give a perfect answer in one go, while I have to go back and forth changing it several times?" Xiao Bing asked. The answer usually does not lie in a difference in Claude's capabilities, but in the quality of the instructions. Excellent instructions are like a perfect requirements document: clear, specific, and unambiguous.

##### 10.5.1 Principles for Writing `CLAUDE.md`.

`CLAUDE.md` is the most core configuration file in Claude Code. Actual measured data shows that optimizing this file can bring more than a 5% improvement in general coding performance, and the increase can even reach 11% in specific repositories. It is recommended to include the following content.

- **Key commands**: Specific instructions for building, testing, and deployment (Claude cannot deduce this type of information on its own).
- **Custom specifications**: Code style rules that differ from the default settings.
- **Architectural constraints**: Project-specific architectural decisions and design limits.
- **Environmental requirements**: Special configurations of the development environment (such as necessary environment variables, non-standard toolchains, etc.).
- **Pitfall avoidance guides**: Common traps and imperceptible system behaviors.

The following content should be avoided.

- **Deducible information**: Content Claude can infer on its own by reading code.
- **Common conventions**: Standard language specifications (Claude already has related knowledge built-in).
- **Volatile information**: Frequently changing content (such information causes cache invalidation).
- **File detailing**: Code descriptions of files (this should be handed over to search tools).
- **Vague advice**: Self-evident principles like "write clean code".

A counter-intuitive principle: less is more. `CLAUDE.md` follows the principle of "the more concise, the more effective.". **A bloated configuration file not only increases the cost of every API call (because it needs to be fully loaded) but also causes key rules to be drowned out in informational noise**. Detailed knowledge in specialized domains should be migrated to the Skills module to achieve on-demand loading. This architectural design can significantly improve efficiency.

##### 10.5.2 Precise Expression Techniques.

The core of instructions lies in **conveying the most complete information with minimal Token consumption**. Here are 3 practical techniques. **1. Quantify Everything**. Avoid vague descriptions, and make sure to use specific data. For example, "process a large amount of data" can be written as "process 1 million records", "response should be fast" can be written as "P99 response time < 200 ms", and "code should be concise" can be written as "functions should not exceed 20 lines, parameters should not exceed 4". **2. Example-Driven**. For complex requirements, one example is worth 10 sentences of description. **3. Clear Boundaries**. Defining "prohibited items" is equally as important as defining "execution items" to prevent Claude from overstepping.

##### 10.5.3 Step-by-Step Confirmation.

For complex tasks, step-by-step execution is far superior to a one-time submission. ##### 10.6.4 Progressive Capability Building Roadmap.

Compared to a "Big Bang" full-scale rollout, a phased implementation strategy can better ensure the robustness and effectiveness of the deployment. According to practical observations, a team's engineering maturity with Claude Code usually goes through the following **4 evolutionary stages**.

**Stage One, Individual Exploration** (First two weeks after kickoff): Engineers spontaneously figure things out and unearth high-value application scenarios; systematic specifications haven't formed yet. The strategic goal is to accumulate empirical cases. Free experimentation is encouraged in this stage, aiming to gather real usage feedback and successful paradigms, avoiding stifling innovative thinking due to premature standardization.

**Stage Two, Project-Level Unity** (First month after kickoff): Standardize the best practices validated by the team (including `CLAUDE.md` rules, common Skills, and basic Hooks), and settle them into the project's `.claude/` directory, putting them under version control (Git). The strategic goal is publicizing assets. Transforming dispersed individual "private experiences" into "public assets" shared by the team.

**Stage Three, Automated Integration** (Second month after kickoff): Utilize Hooks and Headless mode to deeply integrate Quality Gates like code reviews, test runs, and format checks into CI/CD pipelines. The strategic goal is process automation. Driving Claude Code's transition from a "tool assisting human work" to an "automated link within the R&D process.".

**Stage Four, Organizational Scalability** (Third month after kickoff): Promote mature capabilities to multiple teams or even the entire engineering organization via unified Plugin distribution, deployment of organizational-level MCP servers, and implementation of managed policies. The strategic goal is global scalability. Breaking down team barriers to achieve group-wide unification of tech stacks, security policies, and collaboration specifications.

#### 10.7 Integration of SDD Ecosystem and Workflows.

After deeply exploring the previously introduced independent mechanisms, a core question naturally surfaces: how to connect these scattered components into a complete set of workflows?. Currently, the open-source community has shown explosive growth at the workflow level. A large number of plugins and frameworks based on Claude Code have emerged on GitHub, all attempting to answer the same proposition: What should software engineering methodologies look like in the AI era?. Despite their different paths, the answers converge to the same destination, namely SDD (Specification-Driven Development): define specifications first, then write code.

##### 10.7.1 The 4-Tier Ecosystem Architecture of SDD.

These tools are naturally divided into 4 tiers, each dedicated to solving a specific core problem.

**Tier One, Atomic Skills.**. A typical representative is `grill-me`, open-sourced by Matt Pocock. This project consists of only 6 lines of Markdown code, yet it transforms Claude from an "obedient executor" into a "relentless interviewer," forcing the user to scrutinize every pending matter and implicit assumption. This is the ultimate manifestation of the power of Skills described in Chapter 3: reshaping AI behavioral patterns using declarative Markdown.

**Tier Two, Context Persistence.**. This tier aims to solve the problem of context loss in long-cycle tasks. _Planning with Files_ adopts the most rustic strategy: writing plans into files (such as `task_plan.md`, `findings.md`, `progress.md`). After the dialogue context is cleared, Claude can resume progress by re-reading these files. _Trellis_ goes a step further, achieving cross-platform standardization through the `.trellis/` directory structure, allowing the same set of specifications to be universally used across over a dozen platforms like Claude Code, Cursor, and OpenCode.

**Tier Three, Specification Generation Framework.**. This tier provides a complete pipeline from specification definition to code generation. _Spec-Kit_ (an official GitHub project) defines the full flow from "constitution" to code, with its 9 commands covering the entire development lifecycle, though it is slightly cumbersome for small projects. In contrast, _OpenSpec_ (produced by Fission AI) is more lightweight, requiring only 4 core commands to reach the goal in one step; while _cc-sdd_ introduces EARS requirement syntax, achieving an extremely simplified SDD process.

**Tier Four, Complete Methodology.**. This tier integrates a complete system of engineering practices. _Superpowers_ (included in Anthropic's official plugin market) packages 14 composable Skills, defining 7 standard phases: Brainstorming $\rightarrow$ Create Git Worktree $\rightarrow$ Formulate Plan $\rightarrow$ Execute Plan $\rightarrow$ Test-Driven Development (TDD) $\rightarrow$ Code Review $\rightarrow$ Wrap-up and Merge. It mandatorily enforces TDD principles (if a user writes code first and tests later, the system will automatically delete the code) and utilizes sub-agents to distribute tasks in parallel; this is the practical application of the sub-agent mechanism described in Chapter 4. Furthermore, _Compound Engineering_ focuses on the "learning" dimension that other frameworks often ignore: after every iteration, it settles experience into the `docs/solutions/` directory via the `/ce:compound` command; when encountering similar problems next time, the Agent prioritizes retrieving historical solutions, achieving continuous evolution.

#### Chapter Summary.

As the final chapter of the book, this chapter does not merely list technical inventories, but deeply refines engineering methodologies. The core of **Cost Control** lies in grasping 3 key dimensions: flexibly scheduling Haiku, Sonnet, and Opus based on task complexity to achieve optimal balance between performance and cost; effectively lowering Token consumption through context isolation via sub-agents, streamlining `CLAUDE.md` contents, and optimizing caching strategies; and establishing hard budget limits by using the `--max-budget-usd` parameter to set an insurmountable cost red line. To this end, we built a multi-dimensional observability system: utilizing the `--debug` flag to obtain real-time logs; outputting machine-readable execution trajectories via `stream-json`; generating persistent audit records with the `PostToolUse` Hook; and retaining session files as raw data to provide a complete basis for deep post-mortem analysis. For common anomalous behaviors, their root causes can usually be attributed to three major categories: missing context information, instruction logic conflicts, and insufficient runtime permissions.

The core of **Security Guidelines** lies in strict adherence to the principle of least privilege. We built a tiered defense system: providing 5 permission modes to precisely match scenarios of different complexities; achieving atomic-level control over tool calls through a 3-tier rule system of deny, allow, and ask; utilizing the `PreToolUse` Hook to intercept potential dangerous behaviors before operations are executed; issuing non-overrideable global security policies via Managed Settings; and for MCP servers, mandatorily implementing version pinning and strict code reviews.

Regarding **Large Codebases**, the core strategy lies in substituting "guided search" for "full reading". Utilize a hierarchical `CLAUDE.md` and the `.claude/rules/` directory structure to achieve on-demand loading and scenario adaptation of rules; dispatch the Explore sub-agent to execute deep searches and file traversals within independent contexts; and apply intelligent compression technologies to refine key information, significantly extending effective working time.

The soul of **Instructions** lies in ultimate precision. To construct highly reliable interactive paradigms, the following guidelines must be followed: strictly limit `CLAUDE.md` to under 500 lines; migrate specialized knowledge of vertical domains to Skills; quantify Prompts, reject vague descriptions, provide high-quality examples, clearly define task boundaries; and confirm complex tasks step by step.

**Team Implementation** requires steady advancement in phases: Individual Exploration $\rightarrow$ Project-Level Unity $\rightarrow$ Automated Integration $\rightarrow$ Organizational Scalability. Throughout this process, sharing the `.claude/` directory is the cornerstone of collaboration, governing `CLAUDE.md` via PR processes ensures specification quality, and Managed Settings serve as the ultimate defense line guarding security.
