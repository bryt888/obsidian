#### 8.1 The Positioning of the Agent SDK: From Tool to Component

The mechanisms introduced earlier in this book (including CLAUDE.md, sub-agents, Skills, Hooks, MCP, and Headless mode) all take "using Claude Code" as their core perspective. Under this paradigm, developers, acting as users, expand its behavioral boundaries through configuration within the established framework of Claude Code.

The starting point of the Agent SDK is completely different. It presupposes that the developer is an application builder, aiming to deeply embed the core capabilities of Claude Code into their own applications. When to start Claude, what parameters to pass in, how to orchestrate intermediate execution steps, and how to manage the state of multi-turn dialogues—all of this is entirely and autonomously controlled by the developer's code. At this point, you are no longer "using" a ready-made product, but "building" a brand-new application with Claude as its intelligent engine. ##### 8.4.1 Detailed Explanation of Permission Modes

The permission mode is the core of the Agent SDK application's security defense line. It determines Claude's behavioral logic when encountering potentially risky operations (such as writing files or executing commands) (see Table 8-2 for details).

**Table 8-2 Agent SDK Permission Modes and Applicable Scenarios**

|Mode|Behavioral Logic|Applicable Scenarios|
|---|---|---|
|default|Standard interaction. When encountering dangerous operations (like writing files, running Shell), waits for external confirmation (usually via callbacks or manual intervention)|User-facing Web applications, interactive CLI tools|
|acceptEdits|Semi-automatic. Automatically accepts file editing operations, but still asks for confirmation for executing commands (Bash), network requests, etc.|Automated fix scripts, code formatting pipelines|
|plan|Read-only/planning mode. All modifications are prohibited. The model can only read files, analyze code, and output plans, but cannot execute write operations or commands|Code reviews, architecture analysis, vulnerability scanning|
|bypassPermissions|Complete trust. Skips all permission checks and automatically executes all operations (including high-risk commands like `rm -rf`, `curl`, etc.)|Strictly isolated CI containers, sandbox environments|

"In CI/CD pipelines, `bypassPermissions` seems convenient—after all, it requires no manual confirmation," Brother Ka said. "But please keep in mind that this means granting Claude the permission to execute arbitrary commands, including deleting files, modifying configurations, and even making network requests. Therefore, this option should only be enabled when you ensure the execution environment is completely isolated (such as containerized deployments, read-only file systems, and no network connections)."

#### 8.8 The 4 Lines of Security Defense

The Agent SDK constructs a **defense-in-depth system composed of 4 lines of security defense**, as shown in Figure 8-2. ![[Pasted image 20260701150356.png]] _(Figure 8-2 Defense-in-depth System of the Agent SDK)_

#### 8.11 Agent SDK vs. Headless CLI: How to Choose

Although both the Agent SDK and Headless CLI allow Claude to run in unattended environments, there is a clear demarcation in their applicable scenarios (see Table 8-4 for details). Choosing the wrong tool often leads to overly complex architectures or limited functionality.

**Table 8-4 Scenario Selection Comparison Between Agent SDK and Headless CLI**

|Scenario|Recommended Method|Reason|
|---|---|---|
|Single-step tasks in CI/CD pipelines|Headless CLI|Zero-dependency deployment, directly embeddable into YAML configuration, no need to install Python/Node runtimes|
|Shell script automation|Headless CLI|Perfectly fits pipeline combinations, simple and direct|
|Building Web/Desktop AI applications|Agent SDK|Supports streaming output (SSE), fine-grained state management, and frontend interaction|
|Custom tools required|Agent SDK|Supports the `@tool` decorator for registering local functions, achieving a closed loop for complex business logic|
|Multi-turn dialogue/Continuous session|Agent SDK|Built-in session management, automatically maintains context history, no need to manually concatenate messages|
|Fine-grained control of message flow required|Agent SDK|Based on asynchronous generators, allows intercepting, modifying, or routing messages piece by piece|
|Managing multiple instances concurrently|Agent SDK|Programmatic concurrency control (like `asyncio.gather`), easily handles high-concurrency requests|

An interesting rule of thumb: **If your logic can be described in a single Shell command line, please choose the CLI**; if you need to write if/else judgments or loops, please choose the Agent SDK.

**Brother Ka's Remarks** The Agent SDK lowers the threshold for building Agents, but "easy" absolutely does not equal "simple". When embedding Claude into actual products, developers must properly resolve the following key issues: error retries (coping with network fluctuations and API rate limits), cost tracking (monitoring Token consumption for each call), user isolation (ensuring dialogues of different users do not interfere with each other), response timeouts (formulating interruption strategies for long tasks), and circuit breaker mechanisms (automatically stopping calls upon continuous failures). Mastering these engineering details is a mandatory course for upgrading an Agent SDK demonstration prototype into a production-grade Agent.

#### Chapter Summary

The Agent SDK transforms Claude Code from a single terminal tool into an AI component that can be embedded into any application. This transformation relies on two major core APIs—the `query` function and `ClaudeAgentOptions`.

The `query` function is the entry point for the Agent SDK; its functionality parallels the `claude -p` command of the Headless mode, but it returns a message stream in the form of an asynchronous generator, supporting real-time processing of every step of Claude's output. This message stream contains 5 types:

- system/init (Initialization signal),
- assistant (Claude's response, which may contain text content and tool call requests),
- user (Feedback results after tool execution) and
- result (Task termination signal, carrying metadata such as cost, turns, and time consumed).

`ClaudeAgentOptions` provides a programming interface equivalent to the Headless CLI parameters, covering functionalities such as model selection, tool permissions, permission modes, Prompt control, session continuation, and structured outputs. Compared to the command line, the core advantage of the programming interface lies in its dynamic configuration capability: developers can dynamically adjust permission modes based on user roles, flexibly switch models according to task types, or optimize the next round's Prompt in real time based on the execution results of the previous round.

Custom tools are implemented via the `@tool` decorator and in-process MCP servers, granting Claude the capability to call any custom function, whether it's querying a database, calling an internal API, or sending a notification. At the same time, the 4 lines of security defense (Permission Mode, Tool Whitelist, `canUseTool` callback, and PreToolUse Hooks) ensure that Claude only does what it is supposed to do within the application.

From `CLAUDE.md` configuration and Skills definitions, to Hooks interception and MCP integration, all the way to comprehensive mastery of the Headless mode and Agent SDK, every deeper layer means we are one step closer to building a mature "product" rather than a single "tool".
