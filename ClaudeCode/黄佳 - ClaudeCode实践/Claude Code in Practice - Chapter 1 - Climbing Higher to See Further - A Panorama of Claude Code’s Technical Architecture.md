#### 1.1 From Command-Line Assistant to Agent Framework

The issues Xiao Bing experienced with Claude Code—memory loss, erratic styles, and context overflow in long tasks—are bottlenecks that almost all developers applying it in real engineering will encounter. These phenomena may seem like 3 independent bugs, but they actually point to the same fundamental crux: mistakenly treating an Agent framework as a simple chat tool. The essence of Claude Code is a programmable, extensible, and composable Agent framework. This is by no means an empty marketing phrase, but corresponds to the core engineering capabilities of Claude Code.

- **Programmable**: Means you can use Python or TypeScript code to directly drive Claude Code, seamlessly embedding it into CI/CD pipelines or automated scripts, completely liberating human labor without requiring a human to monitor the terminal.
- **Extensible**: Means you can inject memory systems, Skills, Hooks, and other capabilities into it through configuration files without touching or modifying its core code.
- **Composable**: Means these extension modules can be flexibly orchestrated, assembled freely like Lego bricks, thereby constructing complex and efficient workflows.

The integration of the three no longer outlines a single tool, but a solid infrastructure framework—a cornerstone for developers to build their exclusive AI work systems. ##### 1.2.1 Memory Layer — CLAUDE.md

The foundation of a building determines the load-bearing limit of the entire skyscraper. The memory layer of Claude Code is exactly the same—it directly defines the depth of Claude's "understanding" of the project. Fundamentally, Claude is a stateless model. Whenever a new conversation is opened, it knows nothing about the project background, tech stack choices, code conventions, and team agreements. Without any configuration, developers would need to repeatedly reiterate basic settings such as "use TypeScript instead of JavaScript", "prefer pnpm over npm", and "the testing framework is Vitest". The inefficiency of this mode, like having to introduce oneself every day at work, is imaginable. The memory layer completely solves this pain point through `CLAUDE.md`. `CLAUDE.md` is essentially an "employee manual for AI" that can be automatically loaded into Claude's context every time a conversation starts. ##### 1.2.2 Extension Layer — Four Major Components

If the memory layer is compared to the foundation, the extension layer is the main floor of the building—it gives Claude the richest capabilities in daily use. This layer consists of four major components: Commands (slash commands), Skills, SubAgents, and Hooks. They can operate independently and be flexibly combined. Among them, **Commands** are the most intuitive way of extension. When you enter instructions like `/review`, `/commit`, or `/deploy` in the terminal, Claude will execute a set of standardized workflows based on predefined templates. Its essence is to encapsulate highly repetitive, fixed-step operations into "one-click trigger" shortcuts—just like shortcuts on a mobile phone, where a single click can trigger a series of preset actions.

Looking from the perspective of design patterns, Commands are exactly a typical application of the Command Pattern: it encapsulates a "request" as an "object", enabling clients to process different requests in a parameterized way. The definition files for Commands are stored in the `.claude/commands/` directory, and each Markdown file represents an independent command. For example, a file named `review.md` can contain a code review checklist and output formatting specifications; simply by typing `/review`, Claude will strictly follow this checklist to review the current code item by item. ![[Pasted image 20260701083914.png]] _Brother Ka's Remarks_: As of the completion of this book, in the latest evolution of Claude Code, Commands have been officially merged into the Skills system and redefined as a kind of "task-oriented Skill"—a skill triggered by the user via `/command`. This book still retains it as an independent module in the architecture diagram to emphasize its unique trigger paradigm: the fundamental difference between manual explicit triggering and semantic automatic triggering. Deeply understanding this distinction is still valuable for mastering the design philosophy of the entire extension system. **Skills** follow a completely different design path. It does not require manual triggering by the user; instead, Claude automatically judges and loads the corresponding skills based on the semantic context of the current task. Each Skill is essentially a directory containing `SKILL.md`. In this file, the skill's name, description, and list of allowable tools are declared through YAML Frontmatter. Claude uses the content of the `description` field to dynamically decide "whether the current task needs to activate this Skill." This implicit triggering mechanism makes Skills an ideal carrier for domain knowledge—whether it's financial analysis methods, API design specifications, or best practices under a specific framework, all can be encapsulated within.

For example, when you discuss financial indicators with Claude, it will automatically load the "Finance Skill"; and once the topic shifts to code architecture, this Skill will quietly exit. This mechanism of "loading on demand, remaining silent when idle" greatly enhances the fluency and intelligence of interactions. Below is a typical `skill.md` example: ![[Pasted image 20260701084012.png]] **SubAgents** aim to solve a deeper bottleneck: the finite nature of the context window. Claude's context window is like a fixed-size office desk: the desk space is limited, and the more files are piled up, the easier it is to become cluttered. When a task involves a massive amount of files (for example, reviewing the code changes of an entire PR), forcibly stuffing all the details into the context of the main conversation will quickly lead to a "full desk", causing Claude to lose sight of things or even miss key information. The solution of sub-agents is to open up an independent context space for specific tasks—this is equivalent to setting up a new workbench next to the main desk and assigning dedicated personnel to handle sub-tasks there. Once the sub-task is completed, only the conclusion (a concise report) needs to be fed back to the main desk, rather than moving all the work drafts over entirely. This is much like how corporate managers delegate tasks to subordinates: managers do not need to delve into the details of every line of code, but only need to focus on the review conclusions and improvement suggestions. The definition files for SubAgents are located in the `.claude/agents/` directory, and each Markdown file details the role positioning, authority scope, and behavioral guidelines of a sub-agent. More crucially, you can set strict tool permissions for sub-agents, for example, stipulating that a "code reviewer" only has permission to read files and is strictly forbidden from modifying any content. This design profoundly embodies the core application of the Principle of Least Privilege in the AI Agent architecture.

**Hooks** are the only modules among the four major components with "interception" capabilities. If Commands define "what" Claude does, and Skills guide "how" Claude does it, then Hooks determine "whether" Claude can do it. They trigger automatically at specific event nodes, including before tool use (`PreToolUse`), after tool use (`PostToolUse`), and before the response generation stops (`Stop`); developers can insert checking, interception, or enhancement logic at these critical moments. This mechanism is similar to the concept of Middleware in Web frameworks. For example, by configuring a Hook in `.claude/settings.json`, you can achieve the following: whenever Claude attempts to execute `git commit`, it automatically runs a lint check; if the check fails, the commit operation is directly blocked. This "invisible guardian" role makes Hooks a powerful tool for ensuring code quality and security compliance. This event-driven guardian mechanism has mature counterparts in software engineering—whether it's Git Hooks, database triggers, or consumers of message queues, their essence follows a unified pattern: automatically executing preset logic when specific events occur. These four major components jointly construct the core cornerstone of Claude Code's extension capabilities. It is worth emphasizing that they exhibit orthogonality: they support both independent learning and separate use, while also allowing flexible combination to build more powerful workflows. This orthogonal design profoundly follows the Single Responsibility Principle (SRP) in software engineering: each component focuses on solving a specific type of problem ("doing one thing well"), and through organic combination, it can stimulate an "omnipotent" system efficiency. ![[Pasted image 20260701084427.png]] _Brother Ka's Remarks_: In the beginner stage, do not rush for success by trying to master all 4 components at once. Every time you master a component, please be sure to practice it in a real project for two weeks, and only move on to the next stage after thoroughly understanding it. After all, the principle of "biting off more than you can chew" applies equally here.

##### 1.2.3 Integration Layer — Connecting the External World

In the skyscraper of the four-layer architecture, the integration layer is the "water and electricity network" that keeps it running—it extends Claude Code's core capabilities to external systems, making it truly integrate into the development ecosystem. Among them, **Headless Mode** is the key. It enables Claude Code to break away from interactive terminals and run automatically in unattended environments. By passing in the task description via the `-p` parameter and standardizing the output format with `--output-format json`, Claude Code can be seamlessly embedded into any CI/CD pipeline such as GitHub Actions, Jenkins, or GitLab CI. A typical application scenario is automated PR review: whenever a developer submits a Pull Request, the CI pipeline automatically calls Claude Code for code review, and writes the results directly back to the PR page in the form of comments. The entire process requires no human intervention, realizing true "unattended" automated collaboration. **MCP** opens up another dimension of integration capabilities—it endows Claude with the ability to interact deeply with external tools and data sources. If Headless mode is about letting Claude "go out" to integrate into pipelines, then MCP is about letting external capabilities "come in" to empower the model. Simply by configuring the MCP server in the `.mcp.json` file in the project's root directory, you can easily expand Claude's capability boundaries: whether it's accessing databases, calling third-party APIs, operating GitHub Issues, or querying Jira tickets, everything can be connected with one click. This has the same transformative effect as REST APIs unifying frontend and backend communication in the Web era—standardization brings not limitation, but the prosperity of the ecosystem. Headless mode and MCP constitute the two major pillars of the integration layer.

Headless mode faces automated pipelines, seamlessly embedding Claude Code into existing CI/CD systems. MCP faces the tool ecosystem, introducing external data and services into Claude Code's capability toolbox. Together, they drive Claude Code to evolve from an independently running terminal tool into a foundational component that can be flexibly integrated into any tech stack. If the extension layer is strengthening Claude Code's core functions "inside its body", then the integration layer is building a connection network "outside its body"—the two complement each other and are indispensable.

##### 1.2.5 Underlying Perspective: Harness and Agentic Loop

After understanding the "external perspective" of the four-layer architecture, let's go deep into the bottom layer to explore a more fundamental concept — **Harness**. Anthropic's official documentation defines it as follows: "Claude Code serves as the **agentic harness** around Claude: it provides the tools, context management, and execution environment that turn a language model into a capable coding agent." In short, Claude Code is an Agent orchestration framework wrapped around the Claude model. The native model only has the ability to generate text. It is the Harness that endows it with the "hands and feet" to read files, write code, search codebases, and execute commands in the terminal. Without the Harness, Claude is but an "intellect" unable to move a single step.

The original meaning of the word Harness is 'horse gear', which includes the harnesses and reins put on a horse. Although a horse has strength, without the guidance of harnesses, it cannot pull a carriage. What the Harness changes is not the horse's strength itself, but the way the strength is transmitted and controlled. If expressed as a formula, it is **Agent = Model + Harness**. If the model is likened to an engine, the Harness is all the infrastructure built around the engine: tool systems, permission controls, context management, session persistence, event hooks, and the core loop driving all of this — the **Agentic Loop** (see Figure 1-4). This loop mechanism profoundly reveals the source of Claude Code's core capabilities. When you submit a bug, Claude Code doesn't simply "take a glance and guess the answer." Instead, it goes through a process of repeated observation, hypothesis, and verification: it first consults error logs, then searches related code, deeply understands the context, and finally sets out to fix it. ![[Pasted image 20260701085400.png]] When does the loop terminate? It depends on two conditions: first, the model actively stops (i.e., it believes the task is completed and no longer initiates tool calls); second, it reaches the maximum turn limit (set by the `--max-turns` parameter, aiming to prevent the program from entering an infinite loop). In 2026, a key insight emerged in the industry: **The performance difference of the same model under different Harnesses is far greater than the performance difference of different models under the same Harness.**

In the TerminalBench benchmark test, purely by optimizing the Harness, the same model leaped from below baseline to the Top 5 ranks. In other words, the Harness is more important than the model itself. Every link in the four-layer architecture you learned previously, whether it's writing `CLAUDE.md`, setting tool permissions, connecting Hooks, or connecting MCP, is essentially finely crafting the **Harness**. Xiao Bing suddenly realized upon hearing this: "I previously thought Claude Code was merely a shell for the Claude model. It turns out this 'shell' is where its true value lies."

After deeply understanding each part of the four-layer architecture, a more crucial question follows: how do they work together? How should one choose which to use in different scenarios? And how does a real task flow through this system?

##### 1.3.1 Comparison of Trigger Mechanisms

The most confusing aspect of the four major components in the extension layer is their trigger mechanisms. Table 1-1 compares them from 5 dimensions.

|Component|Trigger Method|Triggered By|Needs Memory|Typical Scenarios|Engineering Analogy|
|---|---|---|---|---|---|
|Commands|Manual user input|Human|Yes (Needs to know command name)|`/review`, `/deploy`|CLI Commands|
|Skills|Claude automatically matches based on semantics|AI|No (Automatically discovered)|Financial analysis, API design|Strategy Pattern (Auto-select algorithm)|

Intuitive memory mnemonics are as follows.

- _Commands_: "You tell it to do it" (Responds to user instructions).
- _Skills_: "It knows what to do itself" (Autonomously judges and executes).

After seeing the above summary, Xiao Xue incisively pointed out: "Both Commands and Hooks belong to deterministic triggering—the former is explicitly triggered by user instructions, and the latter is automatically triggered by specific events; whereas Skills and SubAgents embody the AI's autonomous judgment—the former relies on the AI to judge whether to enable it, and the latter relies on the AI to judge whether to delegate tasks." Brother Ka nodded approvingly: "This dichotomy of 'deterministic vs. AI judgment' is indeed another key perspective for understanding the differences among the four components. In actual engineering, for scenarios with extremely high security requirements (such as intercepting sensitive information), Hooks with deterministic triggering should be prioritized; whereas for scenarios requiring high flexibility (such as matching domain knowledge), Skills based on AI judgment are more suitable."

##### 1.3.3 Plugins: Packaging and Distribution of Combinations

"Xiao Bing, you once asked me: 'What exactly is the relationship between Skills and Plugins?'" Brother Ka drew a large box on the whiteboard and then revealed the answer, "It's very simple—Plugins are not a new capability, but a packaging mechanism." Imagine you spent 3 weeks carefully building a Claude Code extension system for your team: including two Skills (Code Review, API Design), one SubAgent (Security Reviewer), and 3 Hooks (Pre-commit Lint Check, Format on Save, Sensitive Information Interception). Now a new colleague joins and urgently needs to reuse this setup. If you adopt the method of manually copying files, just figuring out "which files go in which directory" is enough to waste half a day's energy. The Plugins mechanism elegantly solves this problem. It is essentially a standardized packaging format: through a `plugin.json` manifest file, Skills, Commands, SubAgents, Hooks, and MCP configurations are uniformly encapsulated. Once packaged, all configurations can be automatically deployed in place with just a single installation command. This is just like npm for Node.js, or Docker for container images—the core value of Plugins lies in distribution and reuse, rather than creating new capability dimensions. Clarifying this concept is crucial. Beginners often mistake Plugins for "more advanced Skills", but in fact, the two are in completely different dimensions: Skills define the type of capability, while Plugins define the form of distribution.

A Plugin is like a container, inside which Skills, Commands, Hooks, SubAgents, and other multiple components can be encapsulated. Its core focus is not "what task to execute", but "how to package and share". For individual developers, there may be no need to deliberately create Plugins; directly configuring each component locally in the project is sufficient. For team leaders, Plugins are a powerful tool for standardizing best practices and realizing "one-click configuration" for onboarding new employees.

Faced with numerous components, a core question follows: for a specific requirement at hand, which one should be chosen? To this end, a Claude Code component selection decision tree (see Figure 1-6) and application scenario comparison (see Table 1-2) are provided here to help you quickly make judgments. ![[Pasted image 20260701085711.png]]

|Application Scenario|Recommended Component|Core Reason|
|---|---|---|
|Executing a fixed checklist every time a new version is released|Commands|Steps are clear and fixed, suitable for one-click manual triggering via commands|
|Automatically getting professional guidance when discussing financial issues|Skills|Automatically matches domain knowledge based on semantics, loads on demand, does not require manual user specification or memorization of commands|

|Enabling Claude to operate GitHub Issues|MCP|Seamlessly connects external systems (like GitHub API) via standard protocols, extending the model's tool boundaries|

Regarding the decision tree, please follow this path to ask yourself. First, ask yourself, "What is the trigger method for this task?" If human triggering is required, then ask, "How complex is the logic?" If the steps are fixed, choose Commands; if Claude's judgment is needed, choose Skills. If Claude triggers it automatically, then ask, "Is it triggered at a specific event node, or in a CI/CD pipeline?" If it's an event node, choose Hooks; if it's a CI/CD pipeline, choose Headless mode. Second, ask yourself, "What is the runtime environment?" If the task volume is large or context isolation is needed, stack the use of SubAgents. If access to external systems (such as tools or data) is required, stack the use of MCP. If code-level programming control is required, use the Agent SDK. It is worth noting that in actual use, these components are often stacked collaboratively rather than mutually exclusive single choices. A mature team configuration usually coordinates all components to build a rigorous automation system.

- _CLAUDE.md_ establishes the fundamental context.
- _Skills_ inject domain expertise.
- _Commands_ provide standardized manual operation entrances.
- _Hooks_ build automated security defense lines.
- _SubAgents_ break down and process highly complex tasks.
- _MCP_ breaks down the data barriers of external systems.
- _Headless Mode_ seamlessly embeds capabilities into CI/CD pipelines.

This is just like a highly efficient enterprise: each role (component) performs its own duties with clear boundaries, yet collaborates closely to jointly achieve the ultimate goal. _Brother Ka's Remarks_: The core principle of technology selection is always "use the simplest solution to solve the current problem." Do not fall into the trap of "when you have a hammer, everything looks like a nail": do not delegate tasks everywhere just because you learned sub-agents, nor add guards to every minor operation just because you mastered Hooks. Over-engineering is just as harmful as under-engineering. Excellent architects understand the balance: they know when to introduce a layer of abstraction to improve extensibility, and when `CLAUDE.md` alone is enough to perfectly solve the problem.

#### Chapter Summary

This chapter starts with a key cognitive shift: Claude Code is not a command-line version of ChatGPT, but a programmable, extensible, and composable Agent framework. Regarding the iceberg of Claude Code, the conversational interaction above the surface is just the entrance; the memory systems, four major components, integration mechanisms, and Agent SDK hidden beneath the surface constitute its true technical depth. Understanding this is the first step from "passive use" to "active orchestration." The four-layer architecture draws a clear blueprint for the entire system. The memory layer is the foundation, giving Claude Code the ability to understand project context; the extension layer is the main body, providing 4 orthogonal extension methods: Commands, Skills, SubAgents, and Hooks; the integration layer is equivalent to the "water and electricity network", connecting the external world through Headless mode and MCP; and the programming layer is the "top floor", helping developers leap from users to builders. These four layers progress step by step, yet also support independent study—you do not need to comprehensively master everything to start your practical journey.

Clarifying the relationships between components is the core knowledge that needs to be internalized most in this chapter. Commands represent explicit instructions, Skills carry implicit knowledge, SubAgents achieve isolated delegation, and Hooks act as automatic guardians. These 4 trigger mechanisms cover the complete spectrum from human intervention to automatic execution, and from explicit calls to implicit responses. They can operate independently or be combined and orchestrated. And Plugins, as a standardized encapsulation mechanism, enable these combined solutions to be efficiently distributed and reused. In Chapter 2, we will dive into the cornerstone of the four-layer architecture—the memory system (`CLAUDE.md`), which is both the foundation of the entire building and your best starting point for practicing Claude Code's framework capabilities.
