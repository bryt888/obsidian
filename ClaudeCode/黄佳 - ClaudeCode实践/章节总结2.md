# Claude Code 完整学习指南 - 详细章节总结

## 前言

**主要议题**: Claude Code的本质与学习路线

**关键观点**:
- Claude Code不只是一个ChatGPT的CLI版本，而是**Agent编排框架(Agentic Harness)**
- Anthropic官方定义：提供了工具、上下文管理、执行环境的完整体系
- 同一模型在不同Harness下的表现差异**远大于**不同模型在同一Harness下的表现差异
- Harness比模型本身更重要

**核心启示**:
- 2026年行业洞察：优化Harness的收益比等待更强模型更显著
- OpenAI在4个月内宣布采纳MCP，确立其行业标准地位
- 本书将Claude Code的90%隐藏能力交到你手中

**为什么Harness比模型更重要**：
- TerminalBench基准测试中，仅通过优化Harness就使模型从基线以下跃升至Top 5
- Vercel团队发现：剔除80%工具后，流程更精简、Token消耗更少、速度更快
- OpenAI案例：3名工程师，0行手写代码，产生100万行产品级代码（因为工程师构建的是Harness，不是代码本身）

## 第1章：登高望远—Claude Code技术架构全景

**主要议题**: Claude Code的整体架构与四层模型

**关键场景**：小冰的困境
- 第一周用Claude Code效率提升，但两周后问题集中爆发
- PR审查3次被回退、上下文窗口溢出、无法跨会话记忆
- 最终意识到：问题不在Claude模型本身，而在于没有建立Harness框架

### 从命令行助手到Agent框架

**冰山模型**：
- 表面（10%）：终端对话、代码生成、命令执行
- 深层（90%）：记忆系统、Skills、子智能体、Hooks、MCP、Headless、Agent SDK、Plugins

**可编程、可扩展、可组合的三个维度**：
- **可编程**：用Python/TypeScript直接驱动Claude，无缝嵌入CI/CD
- **可扩展**：通过配置文件注入记忆、Skills、Hooks等，无需修改核心
- **可组合**：各模块灵活编排，如乐高积木般自由拼装

### 四层架构模型

#### 第一层：记忆层(CLAUDE.md) — 地基
- **作用**：根治"失忆"问题，提供项目上下文
- **实现**：给AI的"员工手册"，每次会话自动加载
- **5层级记忆体系**：
  - 企业级(managed-settings.json) — 组织安全底线
  - 用户级(~/.claude/CLAUDE.md) — 个人编码偏好
  - 项目级(./CLAUDE.md) — 团队共识
  - 规则级(.claude/rules/*.md) — 条件化按需加载
  - 本地级(./CLAUDE.local.md) — 私人备忘

#### 第二层：扩展层（四大组件）— 主体楼层

**1. Commands（斜杠命令）**
- 触发方式：用户手动输入 `/review` / `/commit` / `/deploy`
- 本质：命令模式的典型应用，将操作封装为对象
- 存储位置：`.claude/commands/`目录下的Markdown文件

**2. Skills（技能）**
- 触发方式：Claude基于语义自动匹配（或用户显式调用）
- 本质："工作操作手册"，承载领域知识和标准工作流
- 关键特性：
  - 渐进式披露：description→SKILL.md→reference文件
  - 预算机制：description总共享16,000字符预算
  - 两种模式：参考型(自动)/任务型(手动)
  - 允许进程内脚本执行

**3. 子智能体(SubAgents)**
- 核心价值：解决上下文窗口限制问题
- 机制：为特定任务开辟独立的上下文空间
- CEO委派模式：主智能体负责协调，子智能体处理细节，仅返回结论
- 支持5种模式：只读型、执行型、并行型、流水线型、团队型

**4. Hooks（事件钩子）**
- 工作层面：系统执行层而非认知层
- 本质：事件驱动的自动拦截与约束
- 触发时机：工具调用前(PreToolUse)、调用后(PostToolUse)、响应生成前(Stop)
- 与中间件的类比：Web框架的Middleware机制

#### 第三层：集成层(MCP & Headless) — 水电管网

**Headless模式**：
- 定义：Claude Code脱离交互式终端，在CI/CD等无人值守环境中运行
- 参数传入：`-p "任务描述"` 激活Headless模式
- 核心参数：`--output-format json --max-turns 10 --allowed-tools "Read,Grep,Glob"`

**MCP（模型上下文协议）**：
- 比喻："AI时代的USB-C"标准化接口
- 三大能力：Tools(函数) / Resources(只读数据) / Prompts(提示模板)
- 从$M \times N$问题简化为$M + N$问题

#### 第四层：编程层(Agent SDK) — 顶楼工作室

- 定义：从Claude Code使用者转型为Agent构建者
- 入口：`query()`异步函数，返回消息流而非最终结果
- 应用场景：Web应用、嵌入式系统、自定义工作流

### Agentic Loop（Agent的心脏）

**完整流转**：
```
用户输入(Prompt)
    ↓
Claude分析意图
    ↓
调用工具（Read/Grep/Bash等）
    ↓
获取工具反馈
    ↓
基于反馈继续推理
    ↓（循环直到任务完成或达到max-turns）
输出最终结果
```

**循环终止条件**：
- 模型主动停止（认为任务完成）
- 达到`--max-turns`限制
- 达到`--max-budget-usd`成本限制

**行业洞察**：2026年关键认知
- "同一模型在不同Harness下的表现差异，远大于不同模型在同一Harness下的表现差异"
- 这打破了"等待更强模型"的幻想
- Claude的能力边界由Anthropic划定（不可改变），但Harness配置完全掌握在开发者手中

**核心公式**：
```
Agent = Model + Harness
```
- Model：Anthropic提供的语言模型
- Harness：工具调用引擎、权限控制、上下文管理、子进程管理

### 组件关系与数据流

**一个请求的完整旅程**（审查PR示例）：
1. 用户请求：" 帮我审查src/payment/目录最近的代码变更"
2. CLAUDE.md加载：项目技术栈上下文
3. Skills匹配：检测"审查"关键词，自动加载代码审查Skill
4. 子智能体分治：5个文件分配给5个子智能体并行处理
5. Hooks守护：PreToolUse检查安全，PostToolUse记录审计
6. MCP扩展：可能调用GitHub获取PR详情
7. 最终返回：结构化的审查报告

## 第2章：温故知新—记忆系统工程实践

**开篇困境**：
- 小冰每次都要手动告诉Claude"我们用Fastify不用Express，用pnpm不用npm"
- 新会话开启，Claude又"失忆"，需要重复解释
- 根本问题：Claude是无状态模型，每轮对话都从零开始

**核心洞察**：
- 不是Claude的能力缺陷，而是缺少"入职手册"
- Package.json能告诉Claude依赖，但无法传达架构决策与团队约定
- CLAUDE.md的作用：将隐性知识显性化，一次写入，永久生效

### 五层记忆体系（CSS层叠优先级思想）

| 层级  | 位置                        | 范围     | 优先级      | 典型用途                        |
| --- | ------------------------- | ------ | -------- | --------------------------- |
| 企业级 | managed-settings.json 或后台 | 全员     | 最高(绝对强制) | 安全底线、合规策略、禁止事项              |
| 用户级 | ~/.claude/CLAUDE.md       | 个人所有项目 | 高        | 交流语言、Git格式、编程范式             |
| 项目级 | ./CLAUDE.md               | 当前项目团队 | 中        | 技术栈、目录结构、API约定              |
| 规则级 | .claude/rules/*.md        | 按条件加载  | 中(条件化)   | 特定领域规则(如测试规范仅在*.test.ts时加载) |
| 本地级 | ./CLAUDE.local.md         | 个人当前项目 | 低        | 私人备忘、临时配置(不提交)              |

**优先级合并原则**：
- "叠加而非覆盖" — 读取所有层级，合并为完整上下文
- 具体性优先 — 项目级规则优先于用户级通用设置
- 例外：企业级拥有绝对强制力，下层无法绕过

**文件引用机制**：
- 任何层级都支持`@path/to/file`语法
- 自动加载并解析被引用文件
- 支持5层嵌套递归
- 示例：项目CLAUDE.md中`@docs/api-conventions.md`

### CLAUDE.md写作范式

**"少即是多"原则**：
- System Prompt已有50条内核指令
- 自定义指令超过150条就会显著衰减效果
- 每行都是Token成本，需精打细算

**指令密度与遵循质量的反比关系**：
- 超出最优密度 → 模型对每条规则的"深度关注"概率下降
- 类比：员工手册厚到无人通读，不如A4纸摘要

**"三问框架"内容筛选**：

1. **WHY（为什么这样做）** — 赋予Claude举一反三能力
   - 揭示决策背后的底层逻辑
   - 例："选择Fastify而非Express，因为'类型安全优先'战略"
   - 效果：即便未明确规定某处，Claude也会基于原则推导正确选择

2. **WHAT（做什么、不做什么）** — 划定行为边界
   - 最直接、最刚性的指令
   - 不需解释原因，要求绝对执行
   - 例："必须使用pnpm作为包管理器；禁止npm或yarn"

3. **HOW（如何一步步做）** — 固化标准作业程序
   - 适用于常用命令、固定流程
   - 模型不需理解背景，只需准确执行
   - 例："执行数据库迁移：pnpm db:migrate；填充测试数据：pnpm db:seed"

**反面案例 vs 正面范例**：

反面（模糊的"正确的废话"）：
```
这是一个电商平台的前端服务，我们团队有5个人，
项目从2024年3月开始开发。代码要写得好一些，注意性能。
测试要全面。请遵循最佳实践。
```
问题：好到什么程度？全面到什么程度？谁的最佳实践？

正面（精准的"操作手册"）：
```
## 技术栈
- Node.js 20 + TypeScript 5.3 (严格模式)
- Fastify 4 框架 (不使用 Express)
- Prisma ORM + PostgreSQL 15
- pnpm 8 包管理 (不使用 npm/yarn)

## 项目结构
- src/routes/ - 路由定义，只做参数解析和响应构造
- src/services/ - 业务逻辑层，所有核心逻辑在此
- src/repositories/ - 数据访问层，封装Prisma调用

## 关键约定
- API 统一返回格式：{ success: boolean, data?: T, error?: { code: string, message: string } }
- 错误码使用UPPER_SNAKE_CASE，如 ORDER_NOT_FOUND
- 数据库表名snake_case复数形式，主键UUID，必带created_at和updated_at

## 常用命令
pnpm dev         # 启动开发服务器，端口 3000
pnpm test        # 运行全部测试(vitest)
pnpm build       # TypeScript编译+类型检查
pnpm db:migrate  # 执行Prisma数据库迁移
```

### 条件化规则系统（.claude/rules/）

**核心机制**：
- 将庞大的规则集拆解为多个主题文件
- 通过YAML Frontmatter的`paths` Glob模式进行条件激活
- 只有匹配的规则被加载，其他保留在磁盘上（零Token消耗）

**示例：测试规范**.
```yaml
<!-- .claude/rules/testing.md -->
---
paths:
  - "**/*.test.ts"
  - "**/*.spec.ts"
  - "tests/**"
---

# 测试规范
- 采用vitest作为测试框架，禁用jest
- 每个测试文件必须包含describe代码块
- 模块模拟统一使用vi.mock()，禁止手动Mock
- 异步测试一律采用async/await语法，禁止使用done回调
- 测试数据需要通过factory函数生成，严禁硬编码
```

**条件化的力量**：
- Claude编辑`src/services/order-service.ts`时，测试规范不会加载
- 转向`tests/order-service.test.ts`时，规范立即自动生效
- "按需加载"思想：不需要在启动时预载所有潜在资源

### 辅助工具

**1. /init命令**：
- 自动扫描项目结构、依赖配置、关键文件
- 生成CLAUDE.md初稿（包含技术栈、目录结构、命令）
- 手动审查和补充"隐性知识"（分层约束、API格式、命名规范）

**2. /memory命令**：
- 在对话过程中动态编辑记忆文件
- 实现"犯错→纠正→记忆写入→避免再犯"的良性闭环
- 支持选择编辑项目级、用户级或本地记忆

### 三类项目的CLAUDE.md示例

**React前端项目重点**：组件粒度、状态管理、样式方案
- 问题：Hooks、Redux、Context混用导致架构割裂
- 决策树：服务器数据→TanStack Query / 全局状态→Zustand / 局部状态→useState

**Node.js后端项目重点**：分层架构职责、数据格式统一
- 问题：route层直接调用Prisma，业务逻辑泄漏
- 铁律："分层架构(严格单向依赖)" 与 "严禁其他层直接调用Prisma"

**Python数据项目重点**：数据处理流程严谨性
- 问题：混用None与pd.NA，inplace=True破坏可追溯性
- 规范：统一pd.NA、datetime64转换、category优化、禁inplace=True

## 第3章：授人以渔—Skills工程实践

**开篇困境**：
- 每次都要重新向Claude解释"API文档应该遵循OpenAPI 3.0格式，包含错误码标准，中英双语"
- CLAUDE.md已经膨胀，加入这些领域知识会让每次对话都浪费Token
- 需要"工作操作手册"而非"公司规章制度"

### CLAUDE.md vs Skills的本质区别

**类比（企业组织）**：
- CLAUDE.md ≈ 公司规章制度（贴在办公室墙上，人人可见，时刻生效）
- Skills ≈ 部门SOP手册（存放在文件柜，特定部门/时机需要时翻阅）

**对比表格**：

| 维度 | CLAUDE.md | Skills |
|-----|-----------|--------|
| 承载内容 | 项目通用规范 | 专业工作流、领域知识 |
| 生效范围 | 当前项目，始终生效 | 可跨项目，按需激活 |
| 触发方式 | 始终加载 | Claude自动匹配或用户显式触发 |
| 加载策略 | 每次全量加载 | 渐进式按需(description→SKILL.md→reference) |
| 类比 | 企业规章制度 | SOP操作手册 |
| Token消耗 | 固定开销 | 用时才付"按需支付" |

### Skill的完整架构

**目录结构**：
```
api-doc-generator/                    # Skill名称(kebab-case)
├── SKILL.md                          # 【核心骨架】必需，大小写精确
├── scripts/                          # 【手脚】可选，可执行脚本
│   └── detect-routes.py              # 自动扫描代码库发现路由
├── reference/                        # 【记忆库】可选，按需加载参考文档
│   ├── openapi-patterns.md           # 仅生成文档时读取的规范
│   └── error-codes.md                # 仅处理错误时查阅的码表
└── templates/                        # 【模具】可选，输出模板
    └── endpoint-doc.md               # 定义API文档长什么样
```

**关键命名规则**：
- 文件名SKILL.md：必须全大写，精确匹配。skill.md / Skill.md 统统无效
- 目录名：kebab-case(全小写+短横线，如api-doc-generator)，至多64字符，字符集[a-z0-9-]
- 禁入README.md：避免Claude激活时加载人类导读文档而混淆指令

### YAML前置元数据（三大逻辑组）

**1. 身份字段（触发机制）**：
- `name`: 最多64字符，若省略默认使用目录名
- `description`: 最多1024字符，是Claude判断何时调用该Skill的**唯一信号**
  - 包含功能定义(做什么)
  - 包含触发场景(何时用)
  - 包含核心能力(能做什么)
  - 例："Generate API documentation from Express, FastAPI, or Spring Boot source code. Use when user asks to 'write API docs', 'document endpoints', 'create OpenAPI specs', or mentions 'Swagger'. Supports route detection, request/response schema extraction, and authentication requirement marking."

- `argument-hint`: 参数提示，在"/"菜单中显示
- `disable-model-invocation`: true时禁用Claude自动触发，必须由用户/skill-name手动调用
- `user-invocable`: false时从"/"菜单隐藏，但Claude仍可自动调用

**2. 权限字段（权限控制）**：
- `allowed-tools`: 工具白名单，遵循最小权限原则
  - 例如审查Skill：仅`[Read, Grep, Glob]`(只读)
  - 支持模式匹配：`Bash(git log*)` 仅允许git log命令
  
- `model`: 指定该Skill使用的模型
  - Haiku：简单格式检查(快速、低成本)
  - Sonnet：深度分析(高质量、高成本)
  - Fallback：主模型过载时自动降级

**3. 执行字段（运行时环境）**：
- `context`: fork时在隔离的子智能体中执行
- `agent`: 指定子智能体类型(Explore、Plan等)
- `hooks`: 生命周期事件钩子(PreToolUse、PostToolUse等)

### 渐进式披露（三层）

**核心机制**：最小化Token消耗，最大化知识覆盖

三层递进式加载：
1. **扫描阶段** — 仅description（约100字符）
   - Claude判断"这个Skill与当前任务是否相关？"
   - Token成本：极低

2. **激活阶段** — SKILL.md主文件（约800 Token）
   - Claude加载完整指令，理解"如何执行该任务"
   - Token成本：中等

3. **执行阶段** — 按需加载reference文件
   - 仅读取当前任务所需的参考资料
   - 其他文件保留磁盘，零消耗
   - Token成本：精确匹配任务需求

**实际案例（财务分析Skill）**：

| 文件 | Token数 | 说明 |
|-----|--------|------|
| SKILL.md | 800 | 主逻辑与路由指引 |
| reference/revenue.md | 1500 | 收入分析公式和行业基准 |
| reference/costs.md | 1200 | 成本结构 |
| reference/profitability.md | 1000 | 利润率公式 |
| templates/report.md | 800 | 报告模板 |
| **总计** | **5300** | 全量加载 |

**Token节省对比**：

| 场景 | 传统全量加载 | 渐进式披露 | 节省比例 |
|-----|-----------|---------|--------|
| 不激活Skill | 0 | 0 | - |
| 扫描阶段(仅判断相关性) | 5300 | ~100 | **98%** |
| 简单请求(仅需SKILL.md) | 5300 | 800 | **85%** |
| 中等请求(需一个reference) | 5300 | 2300 | **57%** |
| 复杂请求(需所有资源) | 5300 | 5300 | 0% |

**经验法则**：绝大多数请求仅需部分资源，粗放式全量加载极不经济

### Description预算机制

**核心约束**：
- 总预算上限：上下文窗口的2%（默认16,000字符）
- 分配机制：由所有已安装Skill平分（非按需分配）
- 计算公式：单个Skill可用字符数 = 总预算 / Skill总数

**实例**：20个Skill安装，默认16,000字符预算
- 每个Skill平均可用 = 16,000 / 20 = **800字符**
- 若某Skill description超过800字符 → 静默排除（Claude不知道它存在）

**三大应对技巧**：
1. 在Skill配置中设置`disable-model-invocation: true` → description不注入上下文
2. 运行`/context`诊断命令 → 查看是否有超预算的Skill被排除
3. 通过环境变量`SLASH_COMMAND_TOOL_CHAR_BUDGET`手动扩大预算

**关键启示**："少而精"的Skill架构
- 当超过20个Skill时，是重新审视架构的信号
- 合并同类项、隐藏纯内部调用、追求高ROI

### 两种触发模式

**1. 显式调用（用户手动）**：
```
/skill-name arg1 arg2
```
- 用户必须知晓Skill名称
- 指令明确、直接、无歧义
- 与终端命令类似

**2. 语义匹配（Claude自动）**：
- Claude理解用户意图后，自主研判哪个Skill最合适
- 基于description字段的语义相似度
- 用户无感，流程自动化

**自动触发的关键**：
- description必须清晰包含触发关键词（用户可能说的话）
- 例如："生成API文档" / "写接口文档" / "输出OpenAPI规范" / "帮我写Swagger"
- 同义词库越丰富，匹配精度越高

### 触发准确率问题

**欠触发（应触发但没触发）**：
- 现象：Skill本应被调用，但Claude没看出来
- 数据：Vercel评测显示，缺乏明确指引时，Agent有56%的概率完全不查看可用Skills
- 根因：description写得过技术化/学术化，与用户的口语化表述产生语义鸿沟
- 修复：在description中大量加入用户常用的表达词汇、同义词、口语说法

**过触发（不应触发却被触发）**：
- 现象：Skill在不该被调用的场景下被错误激活
- 根因：description定义过于宽泛，包含了太多高频词汇
- 修复：通过"Not for..."句式明确排除干扰项

**验证方法**：构建10-20个测试用例
```
应该触发的测试用例:
- "帮我生成src/api/的接口文档"           -> 期望触发
- "写一份OpenAPI规范"                    -> 期望触发
- "document the REST endpoints"          -> 期望触发
- "帮我写Swagger"                        -> 期望触发

不应该触发的测试用例:
- "帮我debug这个API调用"                 -> 不应触发
- "这个接口为什么返回500？"              -> 不应触发
- "优化一下这个API的性能"                -> 不应触发
```

**验收标准**：
- 相关任务触发率 ≥ 90%
- 无关任务误触发率 ≤ 5%

### Skill内部结构——SKILL.md的设计

**核心设计思想**：SKILL.md是"路由器"
- 通过快速参考表格向Claude指引5个关键维度的路由条件
- 使Claude快速定位任务所需的资源，避免逐行扫描

**快速参考表(Quick Reference)示例**：
```markdown
## Quick Reference

| 分析类型 | 触发关键词 | 参考资源 |
|------------------------|---------------------------|----------------------|
| 收入分析(Revenue)      | 收入、营收、销售额        | `reference/revenue.md` |
| 成本分析(Cost)         | 成本、费用、支出          | `reference/costs.md`   |
| 盈利分析(Profitability)| 利润、毛利率、净利率      | `reference/profitability.md` |
```

**信息密度**：3行仅需50 Token，但能指引10倍的信息检索效率

**契约式引用**：明确的条件+路径+预期
```markdown
## Revenue Analysis
When the user asks about revenue growth, ARPU, or revenue
composition:
→ Load `reference/revenue.md` for calculation formulas and
industry benchmarks.
```
vs 弱引用（无上下文）：
```markdown
See `reference/revenue.md` for more details.
```

**500行法则**：
- SKILL.md篇幅控制在500行以内
- 约2000-3000 Token（合理的上下文开销）
- 超过时应重构：
  - 大段公式→reference/
  - 多个示例→examples/
  - 多个模板→templates/
  - 独立逻辑→拆分为新Skill

### Allowed-tools：知识约束行动

**核心原则**：知识应当约束行动

**权限设计示例**：
- **审查Skill**：仅`[Read, Grep, Glob]`(只读，不修改)
- **生成Skill**：`[Read, Grep, Glob, Write]`(读+写，不修改)
- **分析Skill**：`[Read, Grep, Glob, Bash(python:*)]`(仅Python脚本)
- **执行Skill**：`[Read, Bash(git diff *), Bash(git log *)]`(仅特定命令)

**Bash的精细控制**：
```
Bash(git:*)               # 允许所有git子命令
Bash(git log:*)           # 仅git log及其参数
Bash(npm test:*)          # 仅npm test命令
Bash(python:*)            # 允许所有Python脚本
Bash(./scripts/*:*)       # 仅scripts/目录下的脚本
```

**安全检查流程**：
1. 提取命令前缀
2. 匹配配置规则
3. 执行/拒绝

**经验教训**：
```
# 过度授权
allowed-tools:
  - Bash(*)                # 等同于放弃所有防线

# 精确授权
allowed-tools:
  - Bash(git status:*)
  - Bash(git add:*)
  - Bash(git commit:*)
```

## 第4章：分而治之—子智能体与任务委派的艺术

**开篇困境**：
- 小冰用Claude审查大型PR，一次性投入500行日志、200行测试输出
- Claude在第四个文件时"遗忘"了前序逻辑，最后产出代码前后矛盾
- 根本原因：上下文污染，信噪比严重失衡

### 上下文窗口的困境

**问题所在**：
- 500行日志中真正有价值的可能仅3行
- 200行测试输出中关键信息可能仅一句话
- 其余都是"噪声"

**后续影响**：
- 5轮对话中，这些噪声被重复传输5次
- 累计浪费大量Token和上下文空间
- 关键信息权重被稀释，Claude注意力分散

### 子智能体的本质

**定义**：
独立上下文窗口 + 受限工具权限 + 明确任务范围 = 一个mini-Claude

**CEO委派模型**：
```
主Claude(CEO)
    ├─ 日志分析器(分析员1)：处理500行日志，仅返回3行核心结论
    ├─ 代码审查员(分析员2)：审查代码，仅返回问题清单
    └─ 测试运行器(分析员3)：执行测试，仅返回通过/失败汇总

主Claude接收：3条精炼结论 → 综合决策
```

### 3大核心价值

**1. 隔离** — 独立上下文窗口
- 500行日志的"噪声"完全被隔离在子智能体内
- 主对话不受污染，聚焦于真正重要的3行结论
- 类比：操作系统的进程隔离，单一进程内存泄漏不影响全系

**2. 约束** — 工具权限白名单
- 代码审查员：仅`[Read, Grep, Glob]`(观察，不修改)
- Bug修复员：`[Read, Edit, Write, Bash]`(可以改代码)
- 物理层面的安全保障，不依赖Prompt建议

**3. 复用** — 标准化模块
- 定义一次，团队全员使用
- 新员工入职，直接共用团队的子智能体定义
- 精心设计的子智能体可作为知识资产跨项目复用

### 5种子智能体模式

#### 模式1：只读型（安全的观察者）

**特征**：
- 仅具备观察权，不可修改
- 用于分析、审查、架构评估

**工具权限**：`[Read, Grep, Glob]`

**典型场景**：
- 代码审查 — 指出问题但不修改
- 安全审计 — 发现漏洞但不触发
- 架构分析 — 评估结构但不重构

**安全价值**：
- 类比Linux的`chmod 444`(只读权限)
- 即使Claude产生幻觉也无法造成破坏

#### 模式2：执行型（高噪声任务处理器）

**特征**：
- 输入海量(如500行日志)，输出精简(如5行摘要)
- 核心价值在"信噪比优化"

**工具权限**：`[Read, Grep, Glob, Bash]`（受限）

**典型场景**：
- 测试运行：上千行日志 → 通过/失败汇总
- 日志分析：万条记录 → 5条异常
- 代码格式化：数百文件 → 修改清单

**经济学**：
```
传统（无子智能体）：
5轮对话 × 10,000行日志 = 50,000行 Token开销

使用子智能体：
子智能体：5,000行日志处理，仅返回100行摘要
主对话×5轮 × 100行 = 500行 Token开销

节省：99%
```

#### 模式3：并行型（多专家工作流）

**特征**：
- 3个独立子智能体同步工作，互不干扰
- MapReduce思想在Agent中的应用

**典型场景**：PR的多维度审查
```
main智能体
    ├─ 安全审查员：检查OWASP Top 10
    ├─ 性能分析员：找N+1查询、内存泄漏
    └─ 代码质量员：评估命名、DRY原则
    
各自独立上下文，并行处理
最后在main汇总：3份报告 → 综合建议
```

**效率提升**：
- 串行执行：A完→B完→C完 = 3X时间
- 并行执行：A/B/C同步 = 1X时间

**设计原则**：
- 子任务完全独立，无数据依赖
- 各自输出结构化报告，便于汇总

#### 模式4：流水线型（串行处理链）

**特征**：
- 多阶段顺序处理，上游输出 = 下游输入
- Bug修复全流程最典型

**完整流程**：
```
阶段1(bug-locator): 定位问题 →
阶段2(bug-fixer): 修复代码 →
阶段3(bug-verify): 验证修复 →
阶段4(bug-report): 生成报告
```

**权限动态调整**：
| 阶段 | 权限 | 原因 |
|-----|-----|------|
| bug-locator | Read, Grep, Glob | 仅观察，不修改 |
| bug-fixer | Read, Edit, Write, Bash | 可编辑代码、运行编译 |
| bug-verify | Read, Grep, Glob, Bash(npm test*) | 仅执行测试，不修改 |
| bug-report | Read, Grep, Glob | 仅分析，不修改 |

**交接契约**（流水线的关键）：
```
bug-locator输出：
{
  "root_cause": "src/payment/charge.ts:89",
  "description": "缺少空值检查",
  "call_chain": "...",
  "fix_direction": "添加null guard"
}

↓ 精确指引下游

bug-fixer输入：上述JSON
bug-fixer输出：
{
  "modified_files": ["src/payment/charge.ts"],
  "suggested_tests": "npm test -- src/payment"
}
```

**每个阶段的输出格式必须与下游输入要求严格匹配**

#### 模式5：团队型（长期协作）

**特征**：
- 子智能体不是一次性的，而是长期存在
- 成员间可相互通信
- Task List + Mailbox机制

**适用场景**：
- 大型重构，需要多周协作
- 跨模块的深度改造
- 需要多次迭代的复杂设计

**协作模式**：
1. **竞争假设**：多个Agent基于不同假设并行调查，Team Lead汇总最优方案
2. **并行审查**：同一代码同时进行安全审查和功能审查
3. **模块归属**：不同Agent各司其职（前端Agent管UI，后端Agent管API）
4. **方案审批**：提议Agent vs "魔鬼代言人"Agent对抗式评审

### 子智能体与Skills的协作

**两种组合方向**：

#### 方向A：子智能体预加载Skill
```
子智能体 ← Skill
```
- 子智能体=执行者，Skill=操作手册
- bug-fixer预加载"secure-coding" Skill → 获得安全编码清单
- 设置在子智能体frontmatter的skills字段

#### 方向B：Skill派生子智能体
```
Skill → 子智能体
```
- Skill通过`context: fork`自动派生子智能体
- 确保中间过程不污染主对话
- 例："codebase-health-check" Skill的context: fork

**职责划分**：
- **子智能体定义**："谁、做什么、如何报告结果"(战略层)
- **Skill定义**："具体方法、标准、工具清单"(战术层)

### Token经济学

**不使用子智能体**：
```
System Prompt:        5,000 Token
既有对话历史:         8,000 Token
测试输出(噪声):      10,000 Token

第5-9轮: 每轮 = 5,000 + 8,000→12,000(历史增长) + 10,000(噪声) = 23,000-27,000

5轮累计: 125,000 Token
```

**使用子智能体**：
```
子智能体(隔离):
- System Prompt: 5,000
- 任务描述: 500
- 测试运行: 3,000
小计: 8,500 Token → 仅返回100行摘要

主对话(5轮):
第5轮 = 5,000 + 8,000 + 100(摘要) = 13,100
第6轮 = 5,000 + 9,000 + 100 = 14,100
... (类似)
主对话小计: 75,500 Token

总开销: 41,000(子) + 75,500(主) = 116,500 Token
**节省: 125,000 - 116,500 = 8,500 Token (6.8%)**
```

**关键发现**：
- 短期看，节省有限(6.8%)
- 长期看，随对话轮数增加，节省比例提升至50%+
- 最大收益：**防止上下文压缩导致的信息丢失**(无法用Token衡量)

### 启用决策

**高体量场景**(输入>>输出)：启用子智能体
- 分析500行日志 → 5行结论
- 审查10个文件 → 3个问题

**低体量场景**(输入≈输出)：直接处理
- 修改单个函数
- 编写一段注释

**4个启用维度**：
1. 大规模文件读取(>5个文件) → 隔离输入噪声
2. 高频输出生成 → 过滤输出噪声
3. 上下文完整性保护 → 为后续多轮留余量
4. 操作权限与安全边界 → 严格权限隔离

## 第5章：防微杜渐—Hooks事件驱动自动化

**开篇困境**：
- 小张深夜提交代码，Claude误提交了.env文件(包含3个环境的数据库连接、API密钥、支付网关密码)
- 团队被迫半天内完成密钥轮换、访问日志排查、所有引用位置修正
- 根本问题：没有自动化守护机制

### Hooks的定位：策略与机制的分离

**核心思想**：
- CLAUDE.md & Skills = 策略("应该怎么做")，依赖Claude的理解和自觉
- **Hooks = 机制**("一旦违反就被物理阻止")，不依赖Claude的配合

**对比表**：

| 机制 | 工作层面 | 约束性质 | 对Claude的控制 | 类比 |
|-----|--------|--------|--------------|------|
| CLAUDE.md | 认知层 | 建议性 | 引导行为 | 交通标志 |
| Skills | 认知层 | 指导性 | 规范工作流 | 驾驶手册 |
| **Hooks** | **系统执行层** | **强制性** | **拦截/阻止** | **路障** |

**根本区别**：
- CLAUDE.md/Skills："请你注意..." → 依赖自觉
- Hooks："不允许做这件事" → 物理强制

### 17个事件全景

**会话级事件(3个)**：

1. **SessionStart** — 会话启动时触发
   - 用途：通过CLAUDE_ENV_FILE注入环境变量
   - 示例：自动设置NODE_ENV=development, DEBUG_LOG=true
   - 时机：最早执行，影响整个会话

2. **SessionEnd** — 会话终止时触发
   - 匹配器：区分clear(用户清除) / logout(登出) / prompt_input_exit(退出输入)
   - 用途：清理临时资源、记录会话统计
   - 时机：最后执行

3. **PreCompact** — 上下文压缩前触发
   - 匹配器：manual(用户主动/compact) / auto(窗口满自动压缩)
   - 用途：压缩前备份完整对话记录
   - 时机：需要腾出空间时

**工具调用事件(5个)** — 最核心的事件类别：

1. **PreToolUse** — 工具执行**前**（最强大的事件）
   - 支持3种操作：
     - allow：绕过权限检查直接执行
     - deny：阻止执行
     - updatedInput：调整参数后执行（秘密武器）
   - 示例：`rm -rf /tmp/test --dry-run`(强制加--dry-run)
   - 用途：阻止危险命令、修正不安全参数

2. **PostToolUse** — 工具执行**后**
   - 支持2种操作：
     - additionalContext：反馈额外信息给Claude
     - updatedMCPToolOutput：替换MCP工具输出(仅MCP适用)
   - 无法撤销已执行操作，但可提供反馈
   - 用途：格式化、Lint反馈、日志记录

3. **PostToolUseFailure** — 工具执行**失败**后
   - 用途：错误告警、提供纠正建议
   - 时机：工具返回错误时

4. **PermissionRequest** — 权限对话框即将弹出时
   - 关键区别于PreToolUse：
     - PreToolUse：每次工具调用前无条件触发
     - PermissionRequest：仅当Claude需用户手动确认权限时触发
   - 用途：以编程方式自动批准或拒绝权限
   - 示例：特定白名单工具自动放行，其他工具拒绝

5. **UserPromptSubmit** — 用户提交输入后、Claude处理前
   - 用途：输入预处理、上下文注入
   - 示例：每次用户消息自动附加当前Git分支信息

**子智能体事件(2个)**：

1. **SubagentStart** — 子智能体启动时
   - 支持按子智能体类型筛选(如code-reviewer)
   - 无法阻止启动，但可通过additionalContext注入上下文
   - 用途：每当启动审查员时自动加载团队编码规范

2. **SubagentStop** — 子智能体完成时
   - 支持按子智能体类型筛选
   - 支持质量门控：可通过decision: block强制继续
   - 输入数据包含：transcript_path(主会话) + agent_transcript_path(子会话)
   - 用途：复盘子会话，验证输出质量

**完成事件(2个)**：

1. **Stop** — Claude完成整轮响应时
   - 核心用途："质量门控"机制
   - 支持操作：decision: block → 强制继续修改
   - 场景：发现输出未通过测试、未符合规范
   - 例：测试失败 → 阻止完成 → 强制Claude继续修复

2. **Notification** — Claude发送系统通知时
   - 匹配器：permission_prompt(权限请求) / idle_prompt(空闲) / auth_success(认证)
   - 用途：自定义通知渠道(Slack、钉钉、桌面弹窗)

**较新事件(5个，2025年新增)**：

1. **TeammateIdle** — 队友智能体即将空闲
   - 用途：多智能体协作场景的状态管理
   
2. **TaskCompleted** — 任务被标记为完成
   - 用途：触发后续流程或通知

3. **ConfigChange** — 配置文件变更
   - 用途：审计与合规，追踪设置变化历史
   - 防止未授权的配置修改

4. **WorktreeCreate** — Git Worktree创建
   - 用途：自定义初始化设置(如安装依赖)

5. **WorktreeRemove** — Git Worktree删除
   - 用途：自定义清理逻辑(如删除临时构建产物)

### 能否阻止的维度

**具备阻止能力**(9个事件)：
- PreToolUse, PermissionRequest, UserPromptSubmit, Stop, SubagentStop
- TeammateIdle, TaskCompleted, ConfigChange, WorktreeCreate

**只读模式**(8个事件)：
- PostToolUse, PostToolUseFailure, Notification, SubagentStart, SessionStart, SessionEnd, PreCompact, WorktreeRemove

### 3种处理器类型

| 类型 | 确定性 | 灵活性 | 延迟 | 决策成本 | 场景 |
|-----|--------|--------|------|--------|------|
| **command** | ★★★★★ | ★ | ~0ms | 无 | 模式匹配、文件检查、正则表达式 |
| **prompt** | ★★★ | ★★★ | ~2s | 单次LLM调用 | 需要语义判断但输入充分 |
| **agent** | ★★ | ★★★★★ | ~30s | 多轮LLM对话 | 需要深度代码分析、多文件检索 |

**降级原则**：
能用command就不用prompt，能用prompt就不用agent。规则明确(如模式匹配、文件名检查、正则)永远比大模型判断更可信。

### 3种处理器的完整示例

**Command处理器(最常用)**：
```bash
#!/bin/bash
# .claude/hooks/block-dangerous.sh

set -e
INPUT=$(cat)

COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // ""')
echo "DEBUG: Checking command: $COMMAND" >&2

# 危险模式列表
DANGEROUS_PATTERNS=(
    "rm -rf /"
    "rm -rf ~"
    "chmod -R 777 /"
    "> /dev/sd"
    "mkfs."
    ":(){:|:&};:"               # Fork炸弹
    "curl.*| sh"
)

for pattern in "${DANGEROUS_PATTERNS[@]}"; do
    if [[ "$COMMAND" == *"$pattern"* ]]; then
        echo "BLOCKED: $pattern" >&2
        cat <<EOF
{
    "hookSpecificOutput": {
        "hookEventName": "PreToolUse",
        "permissionDecision": "deny",
        "permissionDecisionReason": "拦截危险命令模式: $pattern"
    }
}
EOF
        exit 2  # 2表示"有意阻止"
    fi
done

echo '{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow"}}'
exit 0
```

**Prompt处理器(语义判断)**：
```json
{
  "type": "prompt",
  "prompt": "评估这段代码修改是否引入了安全漏洞：$ARGUMENTS",
  "model": "claude-haiku-4-5",
  "timeout": 30
}
```
大模型判断，返回`{"ok": true/false, "reason": "..."}`

**Agent处理器(深度分析)**：
```json
{
  "type": "agent",
  "prompt": "检查所有修改的文件是否通过了单元测试。运行测试套件并验证结果。$ARGUMENTS",
  "timeout": 120
}
```
完整子智能体，可使用Read/Grep/Bash进行多轮验证

### 设计方法论："三步走"

1. **先观测** — 部署PostToolUse审计日志Hook
   - 记录Claude的真实工具调用模式

2. **后管控** — 基于审计数据设计PreToolUse拦截规则

3. **逐步收紧** — 同时保留审计日志
   - 监控Hook触发频率
   - 及时发现并修正误拦截

## 第6章：海纳百川—MCP（模型上下文协议）

**开篇困境**：
- 需要让Claude访问公司内网的Jira
- Claude部署在云端，Jira在公司内网 — 两个世界之间有网络隔离墙

### MCP解决的根本问题

**问题空间**：从$M \times N$到$M + N$

在MCP前：
```
5个AI客户端 × 100个数据源 = 500个定制化适配器
每新增1个AI → 需要100个新适配器
每新增1个数据源 → 需要5个新适配器
```

MCP后：
```
5个AI客户端 + 100个数据源 = 105个标准实现
新AI只需1次MCP实现，复用100个现有数据源
新数据源只需1次MCP实现，兼容5个现有AI
```

**类比**：USB-C出现前，每种设备都有专用充电线；USB-C后，所有设备共用一种接口标准。
