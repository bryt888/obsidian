anthropic刚刚向我们介绍了顾问策略，这让你可以将opus作为顾问，与像sonnet或haiku这样更便宜的模型作为执行者进行搭配。这样做的好处是你可以用很低的成本让你的智能体拥有接近opus级别的智能。
 
因为问题并不是哪个模型最好，显然opus四点六是最强大的，所以问题在于对于这个具体任务我应该用哪个模型。因为如果有一个包含三个步骤的任务a、b和c，但只有a步骤足够困难，需要像opus这样昂贵的推理模型时，那为什么还要浪费钱让opus去做b和cc步骤？如果haiku可以用三分之一的成本同样高效地完成b和c步骤，那为什么还要浪费钱让opus去做b和c步骤？
 
所以顾问策略会自动帮你完成这些分配，你甚至不用去考虑。我们有执行者，可以是sonnet或haiku，只有在真正需要顾问级别智能时才会调用顾问。在anthropic的评测中，sonnet以opus作为顾问在SWE-bench Multilingual测试上表现提升了2.7个百分点，这基本上是AI模型解决编程问题的标准评测。相比单独使用sonnet，这样做还将每个agentic任务的成本降低了近12%。
 
正如你在图标中所看到的，你还可以更进一步用haiku作为执行者，然后让opus担任顾问。同样，他们观察到在这种配置下它在BrowseComp上的得分为41.2%，是其单独得分19.7%的两倍还多。在这种情况下，这确实比单独使用haiku成本更高，但你能获得更好的性能，而且它的花费仍然比只用opus来完成这个任务要低。

在开始之前，有几件事我想先给大家展示一下。第一，这些模型最新版本之间的实际成本差异，包括opus、sonnet和haiku。如果你们听到背景里有敲打声，很抱歉，楼上的公寓似乎正在建一个水上乐园。所以在最左边的opus，你可以看到我们每一百万输入要支付5美元，每百万输出则是25美元，这里用绿色表示输出，紫色表示输入。
 
需要注意的是，几乎所有AI模型中输出tokens的成本都远高于输入tokens。sonnet输入是3美元，输出是15美元。haiku的输入是1美元，输出是5美元。希望这能让你看到如果你真的开始实施advisor策略，你将能够节省多少钱。
 
首先，我想谈谈Messages API和云代码之间的区别，因为实际的advisor策略函数只存在于Messages API中，它是一个HTTP端点，让我们的自动化可以在云端调用并使用相同的模型opus、sonnet和haiku。所以人们可能会用它来构建自己的应用程序、聊天机器人、工具和自动化流程。而云代码实际上是建立在API之上的成品，它是你在终端中使用的AI编程助手，它可以访问你的本地文件、编辑代码等事情。它们很相似，但用途不同，云代码更像是一个成品。
 
那么Messages API能做什么？它可以发送一个问题，获取一个答案，可以发送图片、PDF和文档让Claude进行分析。但它不仅仅是一个聊天机器人，还可以定义工具，这些工具其实就是Claude可以运行的脚本，但它不能做的是读取你电脑上的文件、编辑代码、运行终端命令或者浏览网页。它也是无状态的，所以每次请求之间不会记住任何内容。所以如果想要实现这些功能，你可以做到，但你得自己拼凑出一个解决方案，自己动手搭建。
 
那么这和Claude Code有什么相似之处？其实它们当然都使用相同的模型，都具备理解和生成文本、代码以及推理的核心能力，而且都可以调用工具，因为API允许你定义这些工具，Claude Code显然内置了一些工具，你也可以为它们两个都添加更多工具。
 
所以我知道这有点让人困惑，现在有了Messages API、Claude Code和Agent SDK，Claude刚还推出了托管代理功能。Messages API适合在应用、自动化流程中使用AI，且需要完全控制体验的场景。若已有软件，只想实现如点击按钮向云端发消息并获响应的功能，你们其实都已经知道什么时候该用Claude Code了，所以我就把这些要点留在这里。
 
现在还有像Agent SDK这样的东西，它也有点不一样，但基本上我喜欢这样想，如果我有自己的应用，并且想要把类似Claude Code的东西嵌入进去。好了，那我们来进入有趣的部分。
 
我先给大家展示一下我在这里准备的内容，这样可以让我们对顾问策略的实际运作有一个直观的了解。所以我启动了这个Claude Code项目来帮助我构建一个应用，也就是一个前端，通过它与Messages API进行交互。如果你去查看关于这个实际工作原理的文档，在向Messages API端点发起请求时，基本上你需要添加以下内容：
 
- 一个是type，这里你要填写advisor_20260301。
- 然后你还要定义name为wayadvisor，你还可以设置类似max_uses这样的参数，基本上就是限制自动化调用advisor的最大次数，这样你就可以更好地控制你的费用，确保不会过度使用opus。
 
现在我们有了一个非常酷的仪表盘，在这里我可以在上方切换我想要的战略顾问类型，无论是haiku加opus，还是sonnet加opus，或者仅用sonnet，或者仅用opus。我会用这些不同的组合运行一些示例，这样你们就能看到我们到底节省了多少钱，当然这一切都不会牺牲质量。
 
我在下面准备了一些提示词，绿色是简单题，难度随之递增，在顾问模式下只有意识到问题变难时才会调用顾问。现在我用的是haiku加opus，我随便问一句，比如“你们的营业时间是什么？”这其实是在后台调用消息API，你可以看到我们在这里得到了这个答案，而且它是用haiku 4.5回复的。在活动记录这边，我们可以看到这两次请求几乎没花多少钱，分别是0.0016美元和0.0020美元。这里就是它调用了一个工具，也就是搜索知识库，而这里很可能就是它直接回复了我们。
 
现在如果我用同样的问题只用opus来问，比如“你们的营业时间是什么时候？”很明显这样做的成本会高很多，而且答案很可能还是一模一样。用opus得到的这个结果其实比haiku贵了21倍，那可以说opus在这里表现得更好，因为在这两种情况下知识库里都没有相关信息，但opus做了什么？它调用了搜索知识库工具，但也调用了创建工单工具。从某种意义上来说这对客户来说其实是更好的结果。
 
然后我回到我的项目里查看知识库里到底有什么，确保它没有编造内容，结果发现确实知识库里没有关于营业时间的条目，所以这些回复都是准确的。再用haiku和opus问一个新的问题，“你们支持哪些集成？”你可以看到haiku能够搜索知识库并做出回应后返回了正确的答案，而且再一次这个问题足够简单，不需要调用顾问。
 
如果我们用sonnet solo做同样的请求，发送完全一样的问题，它给出的答案和haiku完全一样，唯一的区别其实就是表情符号。但同样这样做的成本会高很多，这次用sonnet的运行成本大约是只用haiku的2.8倍。不过不管怎样，我们先把这些清除掉，接下来我们来做一些更难的问题，这样就能看到顾问被引入进来了。
 
所以我刚刚让这个项目给我出一个难题，并说明正确的回答应该包含哪些内容。问题是“我三周前买了一个硬件设备，还购买了一个软件许可证，现在我想把这两样都退掉，我有哪些选择？”我们应该注意到硬件设备可以在30天内退货，需要原包装，联系支持部门获取退货标签，退款将在5-7个工作日内到账；软件许可证不可退款等信息。
 
那么我们首先尝试用haiku加opus，然后把这个问题发出去。很有意思，它最后并没有调用顾问，回复中提到“在30天的退货期内，您需要保留原包装，可以联系我们获取退货标签，软件许可证不可退款”，这些都看起来没问题。
 
让我们看看如果用sonnet加opus做同样的事情会怎样？这真的很有意思，在这种情况下不知为何sonnet决定调用顾问，而haiku却没有。所以你会想是不是因为haiku没有意识到这个问题的难度，可能理解错了，而sonnet能够明白需要调用顾问，因为这个答案再一次是正确的，30天退货期必须用原包装退回。
 
不过我得说这个答案可能更符合我想发给客户的内容，相比于前一个答案这个答案看起来更清晰一些。好，我们来试另一个问题，首先是haiku加上opus顾问，因为你们可能会怀疑这个功能到底有没有正常工作，这个开关直接指向了haiku和opus的顾问策略，所以我们只需要提出一个足够难的问题让haiku意识到它需要顾问的帮助。
 
好了，我们开始吧，我们可以看到顾问已经和opus一起被调用了，它调用了两个工具，但调用工具的是haiku本身，一个是基于知识搜索的工具，另一个是创建工单的工具。最后的回复是“我已经创建了工单，以便将你转接到企业销售团队”。
 
那么现在我们用同样的问题来试一下sonnet加opus，看看会不会得到不同的答案，回复基本一致，“工单已创建，团队会跟进”。有趣的是我更喜欢haiku的回复，因为它承诺1-2个工作日内联系你，而不是只是说“我们的团队很快会跟你联系”。再一次你可以看到这里调用了opus 4.6作为顾问，sonnet也使用了知识库搜索和创建工单的工具。
 
所以我们用haiku和opus得到了更好的答案，而且成本也低得多，比起sonnet和opus。好吧，因为我很好奇我又分别用sonnet solo和opus solo试了一下，sonnet给了我一个相当有趣的回复，它给了我更多的细节，并且最后建议我联系销售团队，这样他们就可以为我创建工单。但随后opus基本上给了我和之前haiku一样的回复，“我已经创建了工单，将你与我们的销售团队联系起来”。
 
所以我也不太确定这让我怎么想，除此之外对于你的具体用例，如果有这样一个应用，而且你在想是否应该实现顾问策略，我会说不要立刻就去做，要通过每一个模型测试上百个提示，看看你觉得哪一个表现得更好、更稳定。因为再次强调节省token成本确实很棒，但前提是你没有牺牲质量。

所以这个的工作方式其实很简单，当我点击发送时，我们会根据切换的模式向消息API发送请求，然后当响应返回到这个仪表盘时，就会在这里显示调用的是哪个模型以及该模型调用了多少个token。所以总之现在的问题是你要怎么做出这样的东西？你如何把这种策略用在云端代码中，以确保不会超出你的绘画限制？
 
因为在云端代码中当我们使用这些不同的模型时，尽管不像API计费那样按token收费，opus仍然会比sonnet消耗更多的绘画额度，而sonnet又会比haiku消耗更多的额度。所以如果你优化使用haiku，那么你的绘画额度就能用得更久。所以答案其实非常简单，只在你真正需要opus的时候才用它，其他时候尽量用sonnet。对于一些非常小的任务，比如探索、搜索、调研或者总结，那就用haiku就可以了。
 
所以你可以做的是使用一个叫做“opus plan”的模型，如果你进入这里，输入/ model，你就能看到不同的模型，有默认选项，有sonnet，还有带有一百万上下文的sonnet，还有haiku。但其实这里还有一个隐藏的选项，如果你选择model opusplan并点击它，它会显示将模型设置为plan模式下的opus 4.6，其他所有地方我都会用sonnet 4.6。所以在我的状态栏上我已经设置好可以显示当前正在使用哪个模型，它会使用sonnet。但如果我在这里切换到plan模式，它会自动切换到opus，然后当我退出plan模式时，它又会自动切换回sonnet。光是这样就能帮你节省大量的绘画时间。
