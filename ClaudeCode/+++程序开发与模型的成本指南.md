# 程序开发与模型的成本指南

> 面向"根据反馈不断迭代开发"的场景,汇总debug方法、context操作策略、以及用subagent+Haiku降本的具体做法。

---

## 一、Debug:怎么看到实际发生了什么

### 1.1 想看System prompt/内置工具的实际内容

`/context`能看到各分类占多少token,但对**内置的System tools**(Bash、Read、Edit、Grep、Glob等)不提供逐项展开——这部分固定不可配置,想看实际内容要走debug这条路:

```bash
claude --debug api          # 只看API请求相关日志,能看到实际发给模型的system prompt和工具定义
claude --debug-file ~/claude-debug.log   # 直接写到文件,方便回头翻
claude --debug "api,hooks"  # 逗号分隔,只看指定分类
claude --debug "!1p,!file"  # 排除某些分类
```

### 1.2 原始session记录在哪

每个session存成JSONL格式,路径:

```
~/.claude/projects/<项目对应的hash目录>/
```

Windows下类似`~\.claude\projects\...`。里面记录完整的会话细节,包括工具调用、thinking步骤,但原始文件是转义过的JSON,直接看比较费劲,需要格式化工具辅助。

### 1.3 `/agents`不再是查看清单的命令

**从v2.1.198版本起,`/agents`的交互式面板已被移除**,现在运行它只会打印一句提示,不会列出你现有的subagent清单。想确认某个subagent"是否被识别"或"是否真的运行了",要用下面第三章的方法,不能再靠`/agents`。

## 二、Context操作:怎么用compact/clear,尤其是"根据反馈不断改"这种场景

### 2.1 核心判断标准:不是看时间长短,是看"下一件事是不是同一块地方"

| 情况 | 怎么做 |
|---|---|
| 连着几条反馈都是**同一模块/同一片代码** | 用`/compact`,不要清。带上聚焦指令,比如`/compact 保留表单校验模块目前的改动和还没解决的XX问题` |
| 下一条反馈**跳到完全不相关的模块** | `/clear`。旧上下文对新任务是噪音,清之前先把关键状态写进日志文件(见2.3) |

### 2.2 什么时候主动处理,不要等自动触发

- 盯`/context`或status line,**Free space掉到30%以下**就该主动处理,不要等系统自动压缩(自动压缩用通用逻辑总结,不一定抓得住你真正关心的重点)。
- **别攒到context爆满才`/compact`**——`/compact`本身要读一遍全部对话,在一个巨大又早已过了缓存有效期的context上跑,本身就是一次很贵的请求。"频繁小步压缩"通常比"攒到最后一次性压缩"更省钱。
- `/compact`本身也在"会打破缓存"的操作清单里,即便压缩后重新注入的内容跟压缩前一字不差,也要按写入价(1.25倍)重新算,不是免费延续。

### 2.3 具体落地流程(针对反馈驱动的迭代开发)

1. 维护一份"反馈跟踪表"(`FEEDBACK.md`或项目管理工具里的list),每条记录:状态、涉及文件、是否已改完——进度不靠对话记忆撑着,靠这份文件撑着。
2. 每次开始一条新反馈前问自己:这条跟刚才那条是不是同一片代码/同一个上下文?
   - 是 → 继续在当前session,视context增长适时`/compact`。
   - 不是 → 先把收尾总结写进反馈表,再`/clear`。
3. 每改完一条就commit一次——会让下次session的git快照变化、缓存前缀对不上,但换来代码历史清晰可追溯,值得。
4. 反馈列表很长很杂时,可以按模块分别开session(比如"前端表单session""后端API session"),用`/rename`命名,`/resume`切换,而不是硬挤在一个session里跳来跳去。

### 2.4 写HANDOFF.md/log不会明显增加token消耗

写一次总结是很小的一次性开销,换来的是下次开新session时,Claude只需要**读这一份文件**(几百token)就拿到关键信息,而不是重新探索代码库(可能读几千甚至上万token)。这也是让你能放心`/clear`的前提——项目状态不依赖脆弱的对话记忆,而是持久化在磁盘上。

## 三、用Subagent + Haiku降本:配置、调用、验证

### 3.1 先分清:Subagent不是Skill

| | Skill | Subagent |
|---|---|---|
| 存放位置 | `.claude/skills/` | `.claude/agents/` |
| 执行者 | 还是主对话本身执行,只是临时多懂了一些东西 | **另开一个独立对话**,有自己的context窗口 |
| 对主对话context的影响 | 会占用主对话context | **不占用**——它的探索过程留在自己的窗口里,只把摘要传回来 |
| 能否换模型 | 不能 | **可以**,这是配置`model: haiku`的基础 |

一句话:skill是"给Sonnet递一本参考手册,它自己接着干";subagent是"喊另一个人(可以是便宜的Haiku)单独干活,干完只汇报结果"。**想用Haiku省钱,必须走subagent这条路。**

### 3.2 存放位置:项目级 vs 用户级

| 类型 | 路径 | 作用范围 |
|---|---|---|
| 项目级 | `.claude/agents/*.md` | 只在当前项目生效,优先级最高 |
| 用户级 | `~/.claude/agents/*.md` | 对所有项目生效 |

`.claude/`目录下同时存在`settings.local.json`(本地设置)、`scheduled_tasks.lock`(定时任务锁文件)这类东西,跟`agents/`子目录互不干扰,可以放心新增。**还不确定好不好用时,先放项目级,试用期间不影响其他项目,想反悔直接删文件即可。**

### 3.3 默认行为的一个坑:Subagent不会自动变成Haiku

**如果不显式配置,subagent会直接继承主对话的模型**——主对话是Sonnet,派出去的subagent默认也是Sonnet,不会自动降级。必须在subagent的frontmatter里显式写`model: haiku`才会真正跑在Haiku上。

文件结构示例:

```yaml
---
name: code-explorer
description: 只读的代码/项目探索助手。用于查找定义、总结逻辑,不涉及修改文件的任务。遇到需要架构判断的情况,交回主对话。
tools: Read, Grep, Glob
model: haiku
---

(正文:这个subagent被调用时的专属系统提示,写清楚该怎么干活、有什么边界规矩)
```

四个关键字段:
- `name`:小写加短横线,调用时用这个名字
- `description`:**最关键**,Claude靠这段话判断"该不该自动派给它"——写得越具体("什么情况用/不用"),自动匹配越准
- `tools`:按需给,权限收紧,比如纯探索类的就别给Edit
- `model`:想省钱写`haiku`,不写就继承主对话模型

### 3.4 怎么创建

- **最省事**:直接跟Sonnet说"帮我建一个专门做XX的subagent,权限只给YY,用haiku模型",它会自动生成文件存进`.claude/agents/`。
- **自己手写**:照上面结构起一个`.md`文件放进去即可。

### 3.5 怎么调用

- **明说(推荐,尤其是还在验证阶段时)**:"用code-explorer这个subagent帮我看看XX在哪定义的"——最保险,能亲眼确认是否被调用。
- **不点名,让Claude自动判断**:只描述任务,Claude对照每个subagent的`description`字段自动匹配决定要不要派发。description写得越精确,自动匹配越准;这个阶段不建议完全依赖它,容易"以为省了钱但其实没走通"。

### 3.6 怎么验证真的启动了(`/agents`已经不能用来查看清单)

1. **直接问Claude**:"你现在能看到哪些subagent?列出名字和用途。"——确认文件被正常识别。
2. **看`/context`里有没有"Custom agents"这一类**——出现且有token数,说明识别到了(但还不能证明"真的被调用过")。
3. **明确点名调用一次,盯着界面看**——正常情况下界面上会出现一个跟平时主对话不一样的"分派"提示(带subagent名字,执行过程单独展示)。如果调用了却完全看不出任何分派迹象,大概率是Sonnet自己顺手处理了,没真正走subagent。
4. **事后查`/usage`**——"claude-haiku-4-5"这一行token有没有新增,是最终判定标准。方式3看到分派提示、方式4里Haiku token也确实涨了,两者互相印证,才算彻底确认配置生效。

### 3.7 Haiku作为主对话模型的限制(为什么明确不建议这么用)

**Auto mode(减少权限确认弹窗的智能模式)官方明确只支持Sonnet及以上级别模型,Haiku不支持。** 这不是bug,是官方设计决定的——用Haiku当主驱动模型,你没法用Auto mode那套"由独立安全分类器自动审核低风险操作"的机制,只能每个操作手动批准,或者退而求其次用`acceptEdits`/`--dangerously-skip-permissions`这类跳过部分或全部检查的模式,但后者放弃了安全审核这层保护,官方建议只在隔离容器/虚拟机里这么干。

**正确用法是**:主对话保持Sonnet(享受Auto mode、保留判断力),把边界明确、不需要临场判断的重复性任务(批量替换、只读探索、日志摘要)派给配置成Haiku的subagent去做——这样既省钱又不用你逐条确认权限。

### 3.8 验证效果的基线记录方法

放subagent文件之前(或刚放好、还没真正用过时),先记一份基准数据,方便几天后对比:

- `/context`:总token占比、有没有"Custom agents"这一行及具体token数。
- `/usage`(切Week视图):当前"Subagents"表格里各项占比;按模型的花费占比(Sonnet/Haiku/Opus分别多少)。
- 如果能看到组织后台"Daily spend by model"报表,单独记一下Haiku那一行的具体金额和占比。

用了几天之后回来对比:
- Subagent表格里这几个新名字的占比和cost per use。
- Haiku花费涨幅,配合大致用了多少次估算单次成本。
- **关键判断标准**:理想情况是"总花费差不多,但Haiku占比上去了、Sonnet占比相应降下来"——这才说明真的把活分流出去了,而不是单纯多花了钱。

## 四、其他要点

- **Context和Cache不是一回事**:Context是这一轮发送的全部内容;Cache是针对"没变的那部分"给的计费折扣机制。命中缓存按10%计费,新内容按全价(或1.25倍写入价)计费,Output token永远不受cache影响、按标准价全额计费。
- **缓存靠前缀匹配**,前面任何一处变化(切模型、改effort level、连接/断开MCP、执行`/compact`等),从那个点往后都会被当新内容重新计算。
- **Session不等于"关掉的窗口"**,是否真正终止取决于是主动退出还是被中断后恢复;判断缓存还在不在,时间是第一决定因素(你们这边Enterprise走Claude订阅登录,大概率是1小时TTL),其次才是git状态是否一致。

*本指南基于当前Claude Code文档整理,版本更新可能带来细节变化(比如`/agents`这次的改动),建议定期用`/context`、`/usage`核对实际情况。*
