Palantir AIP Agent与Ontology的交互机制
 
0. 核心结论
 
在Palantir体系里，Agent不直接访问底层数据库表，也不自由扫描完整的Ontology schema，它是在一个被配置和授权的权限范围之内，通过Ontology暴露的对象、关系、上下文、函数、动作等等来完成跟业务的交互。
 
可以简单理解为Ontology就是企业业务世界受制理的语义接口，Agent就是通过自然语言使用这些接口的操作员。可以把Ontology理解为就是Agent的操作系统。
 
1. Ontology在Agent眼里是什么？
 
很多人一听到Ontology或者看过之前Ontology介绍的视频之后第一反应就说Ontology不就是一个知识图谱或者数据结构的一种形式是吗？但它其实是一个operational layer，是一个操作层，是坐在数据库虚拟表模型之上，把底层技术资产翻译成业务语言的操作层。
 
编程器官方把它分为了两种能力：
 
- 第一种叫semantic elements，描述世界的能力：比如像shipments、order、warehouse、customer这些object type实体的类型，还有像status、eta、priority等等这些属性，还有像shipment归属于哪个order，order又归属于哪个customer这些links关系层面。这部分其实是解决了Agent怎么知道企业里面有什么东西，谁跟谁关联这个问题。
- 第二种叫改变世界kinetic elements，这种动态的一些元素分为两个大的类型：
- 第一个叫actions：比如像update shipment、eta这种动作，它其实是一个函数形式存在的，它去动态的更新运输的一个预估到达时间。
- 第二种叫functions：直接来说就是函数可以帮我们去计算这一些实际的东西，比如像计算一些延时的风险或者直接有一些优化的函数去优化调度，这部分其实是解决的。
 
Agent如何从一个回答问题的工具变成了真正能够帮助我们去执行业务，产生业务的价值，比如帮助我们去做一些仿真的决策。所以Palantir的Ontology的核心不是简单把一个表换了一个名字叫做本质而已，而是把企业的名词、关系、规则、动作、权限都放到了受制理的语义层里面，所以这点非常重要，后面也会反复用到。
 
2. Agent与Ontology的交互分层
 
Agent与Ontology的交互可以分成五层来理解：
 
- 第一层叫context layer：每次当你发消息，系统自动会把相关的背景知识都准备好了，注意这里是自动准备好而不是等LLM自己来决定要不要查。
- 第二层叫query layer：LLM自己判断需要查什么，主动去查支持像过滤、聚合，沿着关系链整个去逐层探索。
- 第三层叫logic layer：调用分装的一些业务函数关键的一些设计而不是让LLM自己拍脑袋进行计算，是把专业计算交给一些专业的函数。
- 第四层叫action layer：执行一些受控的业务变更。到这里Agent就从问答的一些助手变成了业务的操作员。当然像高风险的一些操作还是要确认，像低风险的一些操作就可以让Agent自动执行。
- 第五层叫governance layer：这也是非常重要的一层，像权限、审计、安全约束都要贯穿到前面的四层，这也是Palantir跟普通Agent的框架最核心的一些差异。
 
之后都会把这五层层层剖析给大家看一下。
 
3. Layer 1·Context Layer（Retrieval Context）
 
Context Layer的作用是：在用户每次提问时，系统自动给Agent提供相关背景。关键特征：确定性触发——每条用户消息到达时自动执行，不依赖LLM自己判断要不要检索。
 
它其实有三种准备的方式，分别是Ontology context、document context还有function backed context。
 
3.1 Ontology Context
 
从对象类型里面进行检索，可以绑定一些固定的对象。比如在页面上选中了某个仓，比如华南仓，Agent自动会拿到华南仓相关的信息，比如它的库存、整体的面积还有对应的负责人等等。
 
当然在这个过程中也可以用一些语义搜索，比如问华南仓有没有冷链断链的一些投诉，系统也可以进行自动的向量化搜索一些历史的投诉embedding到里面返回最相关的五条给到你。
 
第一种就打个比方，比如像秘书在老板走进会议室之前就是把所有相关的档案关于客户的档案都放到桌上了。
 
3.2 Document Context
 
第二种叫document context，直观看这个名词就知道它是跟文档相关的，它是从文档里面去捞全书的模式，把整份合同比如给到LLM片段模式只返回最相关的几个文档块。比如问承运商A关于延误赔偿条款是什么？系统自动会从三份合同里面去筛选相关的段落，而不是把这个合同都丢给你。
 
打个比方就是图书馆员听到你的问题之后就是把最相关的五本书放到你面前，这看起来跟语义检索类似，只是它变成了一种文档的形式，用的方法也是类似的，它也是用了vector embedding的方式去找最相关的一个变量，有可能是文档片段和相关段落，有可能是整份文档加进来。
 
3.3 Function-backed Context
 
第三种叫function backed context，前面两种不够用的时候写一个typescript或者python的函数去做制定的检索。比如客户360的试图会同时拉取crm的记录、活跃的订单、投诉了工单、拼成一个综合情报给到LLM。打个比方就是秘书在老板开会之前同时打电话给销售部、客服部、法务部，把各方的信息汇总成的一个信息给教你。
 
针对于function backed的context可以理解为就是针对于企业高频检索的场景，预先会设置一些函数把相关的信息一次性拉起，再交给LLM总监的回答。比如关于客户的问题，不管他会问什么，所有关于客户的信息都会写成一个函数。只要问了客户的问题，就会把所有客户的信息都产生出来喂给LLM做成它的上下文。
 
4. Layer 2·Query Layer（Object Query Tool）
 
刚才的context是系统自动帮你准备的，这一层就是让LLM自己决定要去查一点东西，它能干什么？像过滤、聚合、检查或者顺着关系链进行搜索往下追都可以做。注意一个关键的区别，它查的是Ontology语义对象和关系，而不是去写一个SQL。
 
Agent面对的是订单、承运商、仓库，而不是直接的表和字段。这里是一个核心的区别，它查的是这些东西，它有三种典型的查询模式。
 
4.1 多条件过滤加聚合
 
比如我问你一个问题，今天的华南仓有多少个延误的高优先级的订单？那么它就会做几个操作：
 
- 第一个做filter session加一个count，然后返回来的比如有七个用户，可能追问哪些是vip客户的。
- 接下来会沿着整个Ontology的link从shipment到order再到customer，service level等于vip。
- 然后接着回了三个。打个比方就是老板在开会自己翻资料的时候，他会先按地区筛选订单，然后再追问哪些大客户。资料都是在桌上，具体要筛选哪些类型？就是老板自己来决定。
 
4.2 Link遍历追溯根因
 
比如有一个订单8832订单去问他延误是在哪一个环节出了问题的，它就会沿着Ontology的网络状的结构沿着link去逐层去追溯。当然这里有个超参数，就是会去设置它到底最深去追溯多少层。
 
比如像这里迅猛的追溯到carrier，履约率是百分之七十二，然后中转枢纽的拥堵。综合判断是因为车辆故障加枢纽拥堵导致的延误，所以这就给出了一些实际上的一些原因。
 
然后简单对比下就是，比如像侦探会沿着线索链逐步追查从案件到嫌疑人，从嫌疑人到同伙，从同伙到据点，每一步都是顺着关系链渐渐的往下查的。
 
4.3 聚合出运营概览
 
第三个就是聚合，聚合出运营的概念，比如各区域仓库、GR聚合起来，比如管理层要一张各区域的红绿灯看板，它不是看具体每单数字，只看一个汇总数字，通过这种方式就可以一眼判断出来。
 
5. Retrieval Context与Object Query的关键区别
 
这里直接提下来就是retrieve contact和query之间的关键区别，因为特别容易搞混。比如必须让Agent知道的一些信息就是放到retrieve context里面，比如当前的仓库信息、今天的kpi信息、权限等级等等。因为每一个人对话都需要有这些信息输入，所以这些就放到retrieve context里面。只要Agent给出回答之前，我都会作为context给到Agent。
 
如果有一些东西可以让Agent自己去探索、自己去判断的，就可以放到object query里面。比如帮我对比一下两个仓的情况，存易仓过去三四天的表现等等。这些是临时提出的，没办法完全提前预测的，就把它放到object query里面。
 
放错了有什么后果？后果其实就是context里面会塞很多的信息，token会浪费，噪声也会干扰，就需要上下文处理能力非常强的模型来制作，自身成本也会上升。如果内容要太多，如果用搜索，object query的配置又会太窄，LLM有可能就查不到想要的信息，有可能就会开始编了。
 
所以简单来说就可以记住一条原则：确定性的走context，允许Agent进行一些探索的就走query layer。
 
6. Layer 3·Logic Layer（Function Tool + AIP Logic）
 
Agent查到了对象有了相关的信息之后，很多场景要调用封装好的业务逻辑。
 
为什么不让LLM自己算？比如可以举个例子，用户如果问了一个问题，比如这批延误的订单的风险等级怎么样？如果没有对应的function的时候，LLM只能说看起来有风险，但这不是企业用户能够接受的答案。
 
有function之后，Agent就能够调用，比如像calculate delay这种类似的函数，它会去计算出来风险的影响范围，会去查过去九十天同路线延误的数据，比如陈玉山当前的履约评分、调天气的app、看目的地未来二十四小时有没有暴雨等等一些恶劣天气，甚至跑一些已经训练好的预测模型，最后输出一个结果。
 
比如订单有高风险原因是什么？原因是仓库积压加目的地暴雨预警这样一个具体的答案。LLM拿到的是结构化的结果，而不是原始数据。它的工作是理解意图，选择合适的函数，用自然语言解释结果、业务规则还有模型交给function。
 
不要让LLM直接做一些专业的判断，除了像风险评分以外，比如像跨对象业务逻辑，它去给你做一些推荐，还有像做一些优化类的计算，让它去做一些算法，比如像最优的分配方案等等。不需要会运筹帷幄，是看懂结果，能够做决策就行了。LLM知道调用哪个函数解决问题就行了。
 
7. Layer 4·Action Layer
 
到这里Agent会从问答助手变成了一个业务操作员。action tool就是让Agent能够做Ontology的一些变更，有两种场景。
 
7.1 高风险操作
 
首先LLM会生成一个action，它需要用户进行确认，比如供应商b单价比a高百分之十二，预计增加运费三百四十元，但是时效可以提升百分之十，需要点击确认才知行。
 
7.2 低风险操作
 
就会自动检测出发，比如天气原因延误了两小时，系统会自动更新eta，自动给客户。还有三个辅助的工具，比如像update application variable，就是让Agent能够改应用的一些状态，只看滑动页面就会联动进行刷新。
 
- 第二个叫command tool，它可以触发一些其他应用操作，比如在地图上标出五个延误的订单。
- 第三个叫request clarification，执行前向用户去确认一些模糊的指令，比如指的是哪个订单等等。
 
8. Layer 5·Governance Layer
 
第五层呢，它不是单纯的一步，而是贯穿前面全部四层的约束机制。
 
比如有一个运营助手的Agent，和区域经理登录，context只注入3条线路的shipment，他只能查这个三条，不能调利润查询函数，但是不能计算利润，但是不能指派承运商。那区域经理呢，query呢可以查所有的线路加，可以优化分配的函数去分配承运商换承运商等等。同一栋楼呢，总经理有全楼的门禁。
 
8.1 防幻觉的Governance约束
 
用户问公司今年总营收是多少？没有Governance的Agent可能会编一个数字，幻觉。但Palantir的做法不是写一条prompt说你不要编造数据就ok了，而是它有好几层：
 
- 第一层是没有配置财务的context
- 第二层就是它没有这个financial report object type
- 那第三个呢就是没授权财务function，Agent只能诚实回答：我没有权限访问公司财务数据。
 
这是从架构层面解决的问题，所以他最终给出了你的答案就是。
 
9. Tool Calling Mode：工具如何暴露给LLM？
 
简单说一下这些工具它是怎么暴露给Agent的。
 
9.1 Prompt Tool Calling
 
第一种叫prompt tool calling，所有模型、所有工具类型，调用方式是一次一个tool，适合场景是模型兼容性优先。
 
9.2 Native Tool Calling
 
第二种叫native tool calling，用模型原生的一些tool calling的能力，部分Palantir + Action/Object Query/Function/Update App Var，调用方式是可并行调用多个tool，适合场景是性能优先、token效率优先。
 
关键理解：Palantir不是把整个Ontology schema全量塞进system prompt，更准确的理解是——在具体Chatbot/Application/Workflow中，根据配置、被授权、和当前任务相关的Ontology能力，以工具片段、函数签名、动作定义等形式暴露给LLM。
 
10. 一次端到端交互链路
 
我们用一个端到端的交互链路来看一下这个端到端的流程图。
 
比如说我有个问题，有哪些订单有延误风险，它会作为一个系统级的确定性触发，语义搜索呢，会返回top十最相关的shipment注入这个LM。那第二步呢，它会过滤华南仓在途加延误的东西，筛选出32个结果，沿着link可能会搜索到order和customer。那第三步呢，23个里面呢，再调用这个recommend resolution，就会给出一个建议的方案。那第四步呢，就是让LM去生成回答，那第五步呢就是点击确认之后呢，去创建一个异常的case，那Ontology呢，同步呢会有审计日志来保存下来。
 
这个是一个交互链路的一个总结。
 
11. 内部Agent与外部Agent
 
上面五层架构主要描述内部Agent（AIP Chatbot Studio / Workshop / AIP Logic），外部Agent接入时需区分两个机制：
 
11.1 Palantir MCP
 
- 面向：开发者/Ontology Builder
- 能力：修改Ontology类型定义（读/写）
- 不做：写入Ontology数据（硬约束）
- 约束：所有修改需proposal review + 人工审批
 
11.2 Ontology MCP（OMCP）
 
- 面向：外部业务Agent / Headless Agent
- 能力：读取对象、执行action、写入数据
- 不做：修改Ontology类型定义
- 约束：application restrictions + OAuth 2.0
 
核心原则不变：Agent通过受治理的Ontology接口访问对象、关系、函数和动作，而非绕过Ontology直接访问底层数据。

13. Demo展示
 
OK接下来呢，我做了一个简单demo，让大家有更加直观的认识Agent，我们会有一个简单的介绍，去导入Ontology或者做模型配置，就是你先要去做Ontology的导入，然后再选择LM进行对话和交互了。
 
我们导入Ontology呢，一些示例的Ontology，我也会尝试把我之前创建本体的那部分跟这部分结合到一起，就是那边创建完成之后呢，完成本体的搭建之后呢，啊你可以自己去添加模型，接下来你可以作为用户的管理，这也是governance。
 
我们可以进入这个对话的功能，就是你可以问他相关的问题，你是什么样的一个角色，函数调用业务操作等等，对于决策者来说，去对比不同的方案，它的metrics到底是怎么样，所有订单的一个情况，它就把12个订单的总览都告诉我了，然后其中呢，其中这两个呢，风险的评分已达到百分百，你有什么建议能够给到我一些建议的方案嘛，会去做一些建议的方案的输出，进行啊承运商的更换，延误时长可能会缩短多少，但是他可能会额外成本增加多少，然后他会给你一个综合的建议，针对这种情况，他会给你以这种实际性的建议，帮你去做决策。
 
呃做了一个功能叫推理过程，它在这个过程当中，它调用哪些工具去跟本体做了交互，那去加入哪些的上下文给到LLM，去查询哪些本体，比如说像查询customer顾客，以及呢查询完之后，还可以去做决策的仿真模拟，那这就是一个比较具象化的实际对我们业务决策能够产生的一个例子。
