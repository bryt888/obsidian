开篇：AI代码率提升与核心问题
 
- 主题：AI代码率从25%到90%，一周搭建Harness体系，不换模型，只加约束。
- 核心问题：如何让AI写出来的代码真的能上线？
- 现实痛点：在企业级项目中，AI写的代码语法完美但业务逻辑有微妙错误，编译没问题但实际运行漏洞百出，修复错误形成恶性循环，还让代码仓库臃肿。
- 典型错误：模型不知道没写下来的规矩，例如价格字段用double而非long导致单位错、改了主链路但漏了国际化链路同步修改、调用外部服务没设超时和降级等。
 
阿里团队实践：Harness体系
 
- 实践成果：在存量Java项目上，一周搭建Harness体系，AI代码率从25%拉到90%，未更换更强模型，仅通过Harness Engineering（外部约束和反馈系统）实现。
 
AI工程三次范式跃迁
 
- 第一次：Prompt Engineering，核心是写好指令，如Few-shot、Chain-of-Thought、角色设定，优化单次交互。
- 第二次：Context Engineering，2025年核心是给Agent看什么，动态构建上下文窗口、Agentic RAG检索、工具定义等，如同给邮件附上所有正确附件。
- 第三次：Harness Engineering，2026年核心是Agent角色、多个执行阶段的完整系统架构，通过工程化消除错误，将约束变成文件、规则、自动化检查，成为系统的一部分，而非修改Prompt或口头叮嘱。
 
Agent四种典型失败模式
 
1. 试图一步到位：上下文填充>40%后质量快速衰退，出现幻觉、循环输出、格式错误的工具调用。
2. 过早宣布胜利：说“编码完成”但编译都过不了。
3. 没做端到端验证：部署后发现关键路径不通。
4. 冷启动问题：大量token花在重新理解项目结构，真正用于编码的预算被严重挤压。
 
- 共同根源：Agent缺乏外部的结构化约束和反馈机制，无法准确评估自身产出质量，不能自己审查自己。
 
Harness目录与Agent角色定义
 
- Harness目录包含四部分：规则（Rules）、技能（Skills）、知识库（Wiki）、变更记录（Changes）。
- 规则体系：三份文件（工程结构、开发流程规范、项目编码规范），告知Agent“标准是什么”，是不随需求变化的稳定约束，将口头传承的规矩写成文件让Agent知晓。
- 技能体系：九个Skill，每个是结构化的SOP。核心如coding-skill（八份分层编码规范，从Controller到Adapter每层有明确模板和约束）、expert-reviewer（定义计划评审和执行评审，每条评审意见包含问题描述、修改建议和优先级分级）、unit-test-write（体现“改驱动测”原则，改了哪个接口就测哪个，优先用线上真实请求出入参构造测试数据）。
- 知识库（Wiki）：存放链路梳理、数据模型、核心业务流程等，Agent按需自主查阅，而非主动加载。
- 变更管理：每个需求创建独立目录，记录从需求分析到部署验证的全流程，评审文件版本递增且旧版本不删。
- Agent角色定义文件（约400行）：是整体系的编排中枢，包含五个模块——角色和项目背景（20-30行，提供项目视野）、配置中枢索引（列出Rules/Skills/Wiki/MCP的路径和触发场景）、七项核心职责（需求理解、任务拆解等）、十阶段工作流调度指令、沟通原则和硬性约束（必须做和禁止做的清单）。本质是将资深开发者的工作习惯和决策逻辑编码化，Agent只需严格执行指令。
 
十阶段开发流水线与关键设计
 
- 十阶段：需求分析、需求评审、编码实现、编码评审、单测编写、单测评审、代码推送、CI验证、部署验证、用户确认。
- 每个阶段三要素：触发条件、Skill加载、质量门禁，阶段间有精确回退路径（如CI失败但测试为零回退到单测编写，编译错误回退到编码实现等）。
- 关键设计：分离执行和评判（编码Agent和评审Agent分开），评审环节有循环上限（需求评审最多三轮，编码评审最多两轮，超出升级人工决策），防止Agent陷入无限自我修改循环；流程嵌入五个人工确认点（需求待决议、计划评审后、编码评审后、部署环境参数、最终交付），人始终掌握关键决策权。
 
上下文三层加载策略
 
- 第一层（会话常驻）：Agent定义文件+Rules，提供全局视野和基本约束，严格控制总量。
- 第二层（阶段触发）：进入对应阶段加载相关Skill（如编码阶段加载coding-skill，评审阶段加载expert-reviewer），每个阶段只加载当前需要的知识。
- 第三层（按需查询）：Wiki不主动加载，Agent根据任务需要自主查阅，实现“刚好够用的上下文”。
 
关键经验
 
1. 先用虚拟需求空跑全流程，暴露缺陷（如CI门禁忽略测试用例数为零、评审报告在简单需求下不生成文件等问题）。
2. 质量门禁必须可程序化验证（如将“检查CI是否通过”细化为status=SUCCESS、total_tests>0、passed=total三个可程序化条件）。
3. 流程一致性优先于效率，小需求也走完整流程，避免“小改动大事故”。
4. 规范是活文档，需持续迭代，每次实战发现新问题立即Patch到Harness中，规范的每一行都对应一个历史失败案例。
 
效果与收益
 
- AI代码率：项目维度从24.86%跃升到90.54%，个人维度从14.24%跃升到87.85%，且是包含多个不同复杂度需求的常态化产出，代码经过完整的需求分析、编码评审、单元测试和CI验证流程。
- 核心收益：返工大幅减少，以往人工Review返工3-5轮，现在Agent评审闭环内纠错，人工只需1轮。
- 意外副产品：知识沉淀，.harness目录下的规范文档、编码Spec、评审记录和变更历史构成活的项目开发手册，新人与Agent可通过相同路径快速理解项目全貌。
 
最小可行方案
 
- 三步开始搭建：
1. 写编码规范文件，把项目里“所有人都知道但从没写下来”的规矩写下来。
2. 写评审Skill，让Agent在提交前自己审一遍。
3. 加CI门禁，用程序化验证的条件卡质量。
- 价值：不是让Agent更聪明，而是让其错误变得可控、可发现、可修复，与传统软件质量保障思路一致，只是拦截对象从程序员变成AI Agent。
