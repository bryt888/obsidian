高德 Agent 高频面试题全汇总文字稿
 
第一题：办公场景下 Agent 如何优雅管理复杂多轮对话
 
各位同学听到“在办公场景下，你的 Agent 是如何优雅管理复杂的多轮对话的？”这个问题，可千万别直接回答说“我就把聊天记录拼到 prompt 里发给模型”，要是这么说，面试官心里基本就给你画叉了。
 
大家好，我是彭宇。办公场景的 Agent 是要干活的，不是陪你闲聊的。今天就对着这张架构图，把大模型领域最顶尖的多轮对话管理方案彻底拆解掉。
 
先看大逻辑，办公 Agent 的核心是要把散漫的闲聊转化为状态驱动的业务流。意思就是，它得像个真正的秘书，脑子里得有 4 个底座。
 
- 分层记忆机制
大家想一想，你跟秘书说话，秘书是不是得有记性？这里分三层：
- 第一层是短期窗口，保留最近几轮的原声对话，保证当下的语境是连贯的。
- 第二层是长期外脑，得接向量数据库。比如老板上次说他喜欢在哪个会议室开会，Agent 得从库里翻出来，这叫沉淀用户习惯。
- 第三层是实体提取，Agent 聊着聊着得能自动拎出来谁是谁，什么项目名称、哪天截止等信息。
这三层让 Agent 有了“鱼的记忆”（形象比喻其记忆结构）。
- 对话状态追踪（DST）
有了记忆，接下来要防止 Agent 答非所问，就得靠对话状态追踪。在业务中，Agent 内部必须维护一个 JSON 状态表，比如定会议室的时间、地点、人数就是 3 个槽位。用户说“定明早的会”，Agent 提取出时间、地点后，不能乱猜，得主动反问“老板，请问几个人参加？要带投影仪吗？”。发现状态缺失就生成引导语话术，直到所有槽位填满才会去调用接口，任务完成了还得自动清理状态，这才叫专业。
- 动态上下文压缩
这时候问题来了，如果聊了三五十轮，Token 炸了怎么办？或者大模型看花眼了怎么办？这就要靠动态上下文压缩。这里有两个“神操作”：
- 一个是摘要生成，当对话超长时触发小模型，生成历史摘要替换长文本。
- 另一个绝招是查询重写（Query Rewrite）。比如用户说“把它发给他”，模型哪知道是谁？Agent 会根据历史消除指代不明，把“那个文件”替换成具体文件名，这样理解的准确率直接翻倍，还能防止注意力稀释。
- 状态机语流编排
最后，怎么让 Agent 像个老司机一样稳不跑偏？这就是状态机语流编排。现在不用简单的线性结构了，得把对话抽象为“意图→工具→人工确认→最后输出”的图结构，每一个步骤都是一个节点。要是 API 调用失败了，Agent 得能记住停滞节点，避免对话流崩溃，还能引导用户重试。甚至要是聊一半想换个任务，它还得支持子任务被打断后的挂起与恢复。
 
刚才讲的是理想状态，但在真实的办公场景里坑可太多了。面试官最喜欢问的就是“万一遇到话题漂移怎么办？”比如正在走请假流程，用户突然问“对了，我年假剩几天？”这时候 Agent 是不是就懵了？
 
解法是引入上下文案管理，把当前请假任务“入站”，解答完新问题后“pop 出站”，主动引导用户回到主流程，比如“老板，刚才假请到一半，继续”。这种对话体验，面试官听了绝对眼前一亮。
 
还有办公场景最敏感的是权限。万一用户顺着前两轮语境诱导 Agent 去查未经授权的内部数据怎么办？记住，在检索和工具调用层必须前置原数据过滤和 RBAC 健全，每轮流转都要强制校验当前用户的 Token 权限，越权直接阻断。
 
再比如聊久了模型出现幻觉或者忘了最初的人设，“骚操作”是动态 system prompt 注入，不论聊了多深，始终将核心约束条件固化在最新请求的顶部，配合历史摘要机制降低噪音，这叫“物理唤醒”，让模型时刻保持清醒。
 
最后，模型容易忘工具参数，比如第一轮给了发件人，第三轮调用工具时丢了发件人。千万别指望模型自然记住，得在外部代码层维护一个参数变量字典，拼接请求时强行注入已获取的状态，脱离语言模型本体的记忆限制，这就叫工程化的稳健性。
 
总结：
 
- 第一，告别简单拼接。办公场景不只是闲聊，必须用状态机和图结构规划对话路径。
- 第二，空间换取准确度。通过“重写 + 摘要 + 外挂数据库”的三板斧，解决多轮带来的注意力稀释问题。
- 第三，守住业务底线。对话管理不仅要懂算法，更要在工程侧把控好权限健全与任务中断恢复。如果能把这套架构给面试官讲清楚，拿下的就不只是一个 offer，而是作为 AI 架构师的专业高度。
 
第二题：垂直业务场景中 Multi - Agent 的适用场景与禁用场景
 
同学们遇到“在垂直业务场景中，Multi - Agent 的适用场景与禁用场景分别是什么？”这个问题，如果只会背概念，基本就凉了一半了。面试官真正想听的是你到底有没有真实落地的工程经验，有没有踩过坑，又懂得怎么权衡。
 
大家好，我是彭宇。今天看着屏幕上的架构图，我带你彻底拿下这道大厂高频面试题。首先得跟面试官亮明态度，抛出第一法则：严格界定适用边界。大家先想一个现实问题，什么时候需要组建团队？是不是一个人干不完或者干不好的时候？Agent 也是一样。
 
黄金适用场景（ROI 高）
 
- 长链路、多角色的复杂工作流（SOP）：常说的 SOP 场景。想让一个单体大模型又写代码又做测试，肯定得“精分”。但如果把它拆解开，变成 Coder 和 QA 两个 Agent 各司其职，这就极大缓解了单模型的上下文遗忘和能力瓶颈。
- 多视角验证与对抗博弈：比如写金融研报或者疑难病例分析。大模型最大的毛病是爱产生幻觉。没关系，引入红蓝对抗机制，一个专家“看多”，一个专家“看空”，互相挑刺辩论，最后让主管来交叉验证汇总，幻觉瞬间就压下来了。
- 多源异构工具的复杂调度：如果一个任务既要查数据库，又要搜网页，还要调 API，全都扔给单个 Agent，很容易把工具弄混。这时候分发给底层的专职 Agent，专人专事效率最高。
 
绝对禁用/慎用场景（灾难区）
 
- 对实时性（Real - time）要求极高的场景：绝对慎用。比如一线实时客服或者高频交易。要是用 Multi - Agent，内部好几个 Agent 搁那互相聊天反思，首字延迟直接成指数级爆炸，等他想明白，客户早挂电话了。
- 逻辑高度确定、规则死板的场景：比如从固定格式的表单里提取几个字段。这叫“杀鸡用牛刀”，写几行正则表达式或者调一次大模型，输出个 JSON 就搞定的事。上多智能体纯粹是增加系统的脆弱性，还白白浪费成本。
- 容错率为 0 且无人在环（HTI）的高危场景：“人类在环”就是关键节点得有真人拍板，像医疗器械的底层操控，大模型的涌现能力万一不可控，高危场景绝对不能让它全权自主闭环。
 
搞清楚了边界，面试官顺势就会问“那他们在系统里是怎么排兵布阵的？” 看屏幕中间的拓扑图，最核心的两种架构：
 
- 串行流水线（Sequential）：适用于标准 SOP。用户给需求，先扔给 Coder Agent 写代码，然后交给 QA Agent 找 bug，最后输出，就跟工厂的流水线一模一样。
- 层级主管分发（Hierarchical）：适用于复杂工具调度。上面坐着 Supervisor 主管，他负责理解用户意图，然后把任务拆解，分别派发给下面平行的 SQL 专家、搜索专家、图表专家去干活，干完之后再由主管汇总交差。
 
讲到这其实你只拿到了一半的分数，想要拿高分拿 SP offer，必须得讲出工程落地深水区的难点和破解之道，告诉面试官你踩过什么坑。
 
工程落地难点与破解
 
- 状态迷失与无限死循环：跑过开源项目的肯定见过两个 Agent 遇到一个 bug，互相推诿或者偏题，开始互相夸奖死循环。破解方法是放弃纯对话驱动，引入图状态机框架，画死条件路由，并且在系统层设置最大迭代次数，到了次数强制熔断。
- Token 成本与延迟爆炸：多轮交互让历史记录越来越长，API 账单报表响应还巨慢。破解方案是大小模型混排 + 状态压缩，核心的 Supervisor 主管用云端强推理大模型，保证“脑子好使”；底层的专职 Worker 用本地部署的端侧小模型，省钱。而且传递上下文时千万别传全量对话历史，用 JSON 把关键状态抽出来传下去就行。
- 角色边界模糊（越权操作）：设定好的测试员跑去乱改代码，或者分析师乱调爬虫工具怎么管？
- 第一，prompt 里不但要说能干啥，还要明确写死绝对不能干啥。
- 第二，最硬核的物理级权限隔离，在系统底层做工具访问控制，不属于的 API 系统直接拦截。
- 系统黑盒，调试溯源困难：最后结果出错了，根本不知道是哪个 Agent 抽风还是哪个工具坏了。所以上线前必须接入专业的观测平台，做到 trace 级的可观测性，每一个输入输出和耗时都得记录，还要针对单个 Agent 做黄金数据集的单独单元测试。
 
结案陈词（高分金句）：面试官您好，总而言之，Multi - Agent 只是解决复杂问题的手段，绝对不是目的。在真实的垂直业务里，我始终推崇大道至简，能用 Prompt 工程搞定的绝不用 Agent，不行再加单 Agent 和工具。只有当单体能力真的触及天花板了，并且业务带来的价值足以覆盖掉增加的延迟和成本时，我才会果断采用基于图结构的 Multi - Agent 架构。业务导向、成本权衡、人类在环，这就是大厂最看重的高阶架构思维。
 
第三题：保证 Agent 稳定输出结构化数据，系统底层架构的核心兜底手段
 
面试官问“除了仅靠 Prompt 炼丹，要保证 Agent 稳定输出结构化数据，系统底层架构还有哪些核心的兜底手段？”这道题是高级 AI 研发和架构师面试的分水岭。如果脑子里想的还是在提示词里多加几句“必须输出 JSON”或者“请严格遵守格式”，那这只是初级玩法，在真正的企业级复杂业务里，这种方法分分钟被模型幻觉击穿。
 
大家好，我是彭宇。今天就对着这张全站架构图，从上到下把这个问题彻底扒个底朝天。大家先想一个问题，就算大模型抽风了，给咱们输出了一堆乱码或者缺胳膊少腿的 JSON，在代码层面难道就只能两手一摊束手无策了吗？
 
工程流程层
 
- 强类型校验与自纠错（Parse & Retry Loop）
为了应对模型输出的错误格式，得引入强类型校验与自纠错，也就是大家常听到的“pass and retry loop”。当输入内容校验失败时，会启动一轮新的交互，直接将错误信息“甩锅”给大模型让其反思并重试。一旦解析发现不对劲，咱们把报错信息直接抓起来，比如“哥们你漏了字段”，这就触发了模型的反思重试。
- 范式转换 - 代码生成代检（Code - Gen Agent）
如果你觉得生成几百行嵌套 JSON 太复杂，还可以用范式转换。因为大模型写代码的逻辑严密性远高于自由输出，所以可以让大模型生成一段 Python 脚本，在沙箱中执行来实现格式的范式转换。
 
原生接口层
 
- 工具调用机制（Function Calling）
厂商推出的工具调用机制很有用。咱们把想要的 JSON 格式，用 JSON Schema 的形式传给模型，头部的模型一看到这玩意儿，Token 格式立马就规矩了。
- 强制结构化模式（Structured Outputs）
厂商直接推出了强制结构化模式。在这种模式下，人家服务端推理的时候，能做到 100% 自断不缺（格式完整正确）。
 
底层解码层
 
- 受限解码（Constrained Decoding）
这里的核心技术叫受限解码，它本质上是一个字一个字往外“蹦”。受限解码会干预模型的每一步生成，比如通过前缀树（Trie）或有限状态机进行强行拦截。哪怕模型想说某个词的概率是 99%，只要不在允许的范围内，就绝对出不来。这就叫从物理层面保证格式，它是目前确定性最高的一招。
- 高性能状态机编译
如果在模型每次“蹦”一个字的时候都做检查，推理速度得多慢啊。于是有了高性能状态机编译，把那些复杂的业务逻辑提前编译成状态机，直接实现 DS 级干预（底层数据结构级别的高效干预），在推理时快速判断和控制。
 
模型训练层
 
如果拿了一个比较基础的开源底座模型，它看不懂 JSON 怎么办？这就进入模型训练层。我们给它喂大量的“自然语言指令 + 结构化 JSON 输出”的数据，将这种格式烙印在它的权重网络里。但这里有个巨大的坑，如果天天只让它做格式化输出，它的通用推理能力会退化。所以咱们在训练的时候，要把 30% 的格式化数据和 70% 的通用逻辑数据混着练，这样才能守护住底座模型的能力。
 
面试高分总结：
单纯写 Prompt 只能决定 Agent 输出的下限，而引入底层的受限解码算法与上层的代码级自动纠偏，才真正决定了企业级 Agent 落地的上限可用性。在真实的工业级场景中，我们从不依赖单一手段，而是通过一套组合拳：先用思维链理清逻辑再做内容沉淀，再用受限解码卡死格式，最后接入 Agent 级的单元测试与黄金数据集，同时采用轻量级 proxy 数据集进行预筛。同学们这一套逻辑讲下来，面试官绝对会对你刮目相看，因为这体现了你对 Agent 系统架构的深度思考，架构图记得保存。
