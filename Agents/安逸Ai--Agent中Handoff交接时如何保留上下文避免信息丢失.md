Agent中Handoff交接时如何保留上下文，避免信息丢失
 
我是安逸，agent交接时怎么保留上下文？这题我当年也翻过车，不是不会，是答不到点上。这期我把三个核心方案掰开了讲，搞懂这三个，面试遇到这题直接背完走人。
 
先说个事，我之前面试被问懵过，面试官问多agent协作时，一个agent的交接任务给另一个agent时怎么保留上下文？我想都没想就说直接把输出传给下一个，结果他笑了，追问三个问题我一个都没答上来。
 
第一种方案：依赖注入
 
这是最简单的方案，思路是前序agent的产出结构化，后续agent直接按结构化数据读取。
举个例子，a审查完合同输出一个JSON，里面有 risk level 和 key issues ，b直接读这些字段做下一步。
实现分三步：
 
- a结构化输出；
- 编排器注入上下文；
- b按字段解析。
好处是简单直接，延迟低，适合线性链式场景。
 
第二种方案：Workspace（工作空间）
 
适合更复杂的场景。依赖注入是一条链往下传，但有时多个agent需要并行读同一个数据，或者数据是动态产生的，这时候依赖注入就不够用了。
Workspace的思路是将数据存到共享存储，按主题组织，每个agent按需读写。
好处是支持多消费者并行和增量读取，用序列号追踪上次读到哪了。
但要注意数据一致性问题，比如a写了一条数据，b还没读到，a又更新了，b可能读到不完整的状态。解决方案是将所有record设计成不可变的，写新record而不是修改旧record。
 
第三种方案：P2P消息系统
 
适合需要动态协商的场景。比如a是调度agent，需要先问问b和c谁比较空闲，再决定把任务给谁，这不是单向传数据，而是来回对话。
P2P消息的核心是Mailbox（邮箱）和Protocol（协议），每个agent有自己的邮箱收消息，协议定义消息类型和协商流程。
流程大概是：
 
- a发请求问b能不能接；
- b回可以并给预计时间；
- a确认提交；
- b确认接收。
坑点在于消息可能丢失，需要持久化重试；还可能超时，需要超时检测。
 
三种方案怎么选？
 
记住一个原则：从简单开始，按需升级。
 
- 依赖注入：复杂度低，延迟低，适合线性链式场景。
- Workspace：复杂度中，延迟中，适合多消费者和增量数据场景。
- P2P消息：复杂度高，延迟高，只有在确实需要双向协商时才用。简单场景用P2P是过度工程，会暴露工程判断力不足。
 
面试答题模板
 
- 入门版：多agent交接保留上下文有3种方案。依赖注入把前序产出作为 previous_results 字段注入后续上下文，实现简单延迟低，适合线性链式；Workspace将数据存共享存储，多agent按需读写，适合主题共享和增量数据；P2P消息通过邮箱协议双向协商，适合动态委派。
- 进阶版：这三种是渐进式选择，从简单到复杂，按需升级。
- 高手版：结合场景讲Schema约定和关键节点持久化。
 
常见追问及回答
 
1. 前序agent还没产出结果，后续agent要等吗？
可以等，但要用指数退避轮询，开始快查（比如100毫秒），逐渐放慢，最长等5秒，不要固定间隔空转。
2. 上下文太长导致Token爆炸怎么办？
在交接点做上下文压缩，结构化输出，优先提取关键字段，对长文本做摘要，必要时持久化状态到外部存储。
3. 交接时怎么保证数据一致性？
通过Schema约定保证格式理解一致，加上不可变record设计，写新record而不是修改旧record。
 
四个大坑要避开
 
1. 直接传文本：前序agent输出自然语言，后续agent自己理解易产生歧义，正确做法是结构化输出JSON。
2. 所有场景都用P2P消息：引入复杂度远超实际需求，属于过度工程。
3. 交接完就不管了：交接只是开始不是结束，后续处理失败前序不知情，前序改数据后续可能还用旧的。正确做法是双向确认机制和超时告警。
4. 认为Workspace可以完全替代依赖注入：简单链式场景中，Workspace的额外存储和读取延迟反而是负担，要根据场景选择，不要盲目追“技术明星”。
 
实际场景案例
 
- 电商客服多Agent：用户进线后，意图识别Agent分析需求，再分配给退换货、投诉等Agent处理。早期意图识别输出自然语言，业务Agent解析准确率仅70%；后来改成结构化输出（含 intent 、 reason 、 order ID 字段），准确率提升到95%以上。
- 金融风控多Agent：数据采集Agent并行执行，规则引擎执行，人工审核疑难case，最终决策。用Workspace解决数据共享问题，数据采集Agent写到 risk data topic ，其他Agent按需读取。所有record设计成不可变的，提前设计数据一致性，避免出问题后再修改。
 
总结
 
Agent交接保留上下文的本质是在信息完整性和系统复杂度之间找平衡，核心原则有三：
 
- Schema约定优于隐式传递；
- 关键节点要持久化；
- 不要过度工程。
 
三种方案是渐进式选择，从依赖注入到Workspace再到P2P消息，从简单到复杂，按需升级。面试时能说出这些，面试官就知道你不是在背八股文，而是真做过系统。
